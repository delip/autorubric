## Key Conventions

- All graders return `EnsembleEvaluationReport` for consistent interface — including decision-model judges, which plug into `CriterionGrader` as one more judge kind rather than a second grader hierarchy (per-judge dispatch, one request per item: [Grading Flow](grading-flow.md))
- **`judge_model_config` is the canonical single-judge keyword; `llm_config` is its deprecated alias** (the codebase's first deprecation; removal no earlier than the next major version). `CriterionGrader(llm_config=...)` builds the identical single judge (`judge_id="default"`) and emits `warnings.warn("llm_config is deprecated; use judge_model_config", DeprecationWarning, stacklevel=_INIT_CALLER_STACKLEVEL)`, attributed to the caller's line (shown in scripts/notebooks per PEP 565, reported by pytest); the stack level is 3, not 2, because `__init__` runs inside its keyword-recording wrapper `_records_passed_keywords` (see [Grading Flow](grading-flow.md)). `llm_config` is the **last** keyword-only parameter; a non-`None` value for both → `ValueError` (raised before any warning); the "exactly one of single config / `judges`" `ValueError`s now read "Must provide either judge_model_config or judges" / "Cannot provide both judge_model_config and judges". `JudgeSpec` takes `judge_model_config=` as a keyword alias and exposes it as a read/write property, but keeps `llm_config` as its stored field and accepts `llm_config=` **without** a warning (details: [Type Catalog](types.md)); existing readers (`eval.py`'s `_serialize_grader_config`, `meta/_improve.py`'s `_get_eval_llm_config`) keep reading `spec.llm_config`. Every internal construction (`CriterionGrader`'s own `JudgeSpec`, `meta/_evaluate.py`, `meta/_improve.py`) and every `src/` docstring example uses `judge_model_config=`, and the library never triggers its own deprecation. Two guards enforce this: `tests/conftest.py`'s `pytest_configure` adds the ini filter `error::DeprecationWarning:autorubric` for the whole suite (the module field is a start-anchored regex, so every `autorubric.*` module is covered; a caller's own deprecated call is attributed by its stack level to the caller and only warns, and `pytest.warns` still captures it; a run's own `-W` options are applied after ini filters and take precedence, so `TestSuiteWideDeprecationGuard` checks the configured filters in isolation, via pytest's `apply_warning_filters`, independent of the run's filters), and `tests/graders/test_judge_model_config.py` records warnings on the meta-evaluation and improvement-loop paths and asserts none has a filename inside the package. The meta API's own `llm_config` *parameters* (`evaluate_rubric_standalone(rubric, llm_config)`, ...) are a different API and are not renamed. The judge-config keywords and `JudgeSpec`'s stored field take `LLMConfig | DecisionModelConfig` — the config's type is the judge's kind — while meta-rubric evaluation and the improvement loop stay LLM-only (next bullet); the meta API's own `llm_config` parameters stay typed `LLMConfig`
- **Roles a decision model cannot fill: meta-rubric evaluation and rubric improvement.** Both work from generated text — the meta-judge's explanations (and `affected_criteria`), the evaluation judges' explanations of their verdicts, the revised rubric — and a decision model returns probabilities, not text. Every entry point that takes a judge configuration for these roles therefore rejects a `DecisionModelConfig`, or a `JudgeSpec` wrapping one, with **`ValueError`** (as these APIs validate their other arguments, including type-shaped ones such as "eval_llm must be list[JudgeSpec] ..."), **before** it builds a client or makes any call. One message builder, `_not_an_llm(what)` in `meta/_evaluate.py`, words every rejection: "`<what>` must be an LLM, not a decision model (DecisionModelConfig): meta-rubric evaluation and rubric improvement work from generated text (judges' explanations, revised rubrics), which a decision model does not produce"; `_reject_decision_model_judges(judges, what)` applies it to `JudgeSpec` lists, naming the offending `judge_id`. The entry points (pinned by `tests/decision/test_decision_roles.py`; the LLM-only *settings* inside `CriterionGrader` itself — few-shot examples, the system prompts, `shuffle_options`, custom response formats — are in [Grading Flow](grading-flow.md)):
  - `evaluate_rubric_standalone` / `evaluate_rubric_in_context`: their `llm_config` (`what="llm_config"`), checked first, before the `CriterionGrader` (and its meta response formats) is built.
  - `ImprovementConfig.__post_init__` → `_reject_decision_models()`: `eval_llm` via `_check_eval_llm` (a `DecisionModelConfig`, or any `JudgeSpec` of one in the list, named as "ImprovementConfig.eval_llm judge '<id>'") and `revision_llm` via `_check_revision_llm`. `__post_init__` also runs under `dataclasses.replace`, so `improve_rubric(...)`'s `eval_llm=`/`revision_llm=` keywords and its config overrides are covered.
  - `ImprovementRunner.run()` calls `config._reject_decision_models()` again before anything else, because a dataclass field can be reassigned after `__post_init__`; `_get_eval_llm_config` keeps the same guard (via `_check_eval_llm`, which also narrows its return type to `LLMConfig`).
  - The building blocks: `validate_agreement` (its `judges`), `validate_ground_truth` / `validate_held_out` (the grader's judges, read from its `_judges` list as `_serialize_grader_config` reads them, via `_reject_decision_model_grader`; a grader without one is left alone), and `revise_rubric` / `revise_rubric_held_out` (`config.revision_llm`, before the `LLMClient` is built).
- **Rubric guidelines reach every judge, and change nothing when absent.** `Rubric.grade` passes `guidelines=` only when the rubric has guidelines; `Grader.grade(..., *, guidelines=None)` forwards them only to a `judge` that accepts the keyword (or `**kwargs`), so the abstract `judge`/`aggregate` signatures and every existing subclass are unchanged; a grader that cannot take them grades without them and warns `"<GraderClass> ignores rubric guidelines"` once per instance (a `grade` override with the old signature likewise). Blank guidelines are none everywhere (`_normalize_guidelines`). LLM judges get `GUIDELINES_BLOCK` at the start of every user prompt (system prompts untouched); decision models get `state["guidelines"]` first, plus `DECISION_MODEL_GUIDELINES_INSTRUCTION` in framed binary instructions. Without guidelines every LLM prompt and decision-model request is byte-identical, so response caches stay valid; with them, both judge kinds' cache keys change with the text. Details: [Grading Flow](grading-flow.md)
- `raw_score` always populated regardless of `normalize` setting
- Judge-call failures classified via `classify_grading_error()`: `infrastructure`/`parse` → CANNOT_ASSESS / `na=True` (excluded under default SKIP); `unknown` → conservative worst case (forced-choice no-NA infra/parse abstain → `na=True`, `selected_index=None`/`selected_label=None`). One helper, `_failed_judgment_result`, builds every failure report for both judge kinds; a decision model's failed request fails each criterion posed in it that way, never re-sending criteria one at a time. Full routing and failure scope: see [Grading Flow](grading-flow.md)
- **Report serialization is uniformly pydantic-native.** `EnsembleCriterionReport` / `JudgeVote` / `MultiChoiceJudgeVote` are **frozen pydantic models** (not dataclasses), so the ensemble checkpoint path collapses onto `model_dump(mode="json")` / `model_validate` exactly like the single-report `CriterionReport` path — no hand-rolled per-field plumbing. `ItemResult.to_dict` keeps its envelope (`report_type` discriminator, `criterion_reports`, `judge_scores`, nested `token_usage`); `_serialize_ensemble_criterion_report` is now a thin `ecr.model_dump(mode="json")` wrapper (shared with the meta improvement-loop artifacts), and `_deserialize_ensemble_report` rebuilds only the envelope around `[EnsembleCriterionReport.model_validate(...)]`. Adding a field to any report/vote type now round-trips for free. `EnsembleCriterionReport.agreement` is computed by a `model_validator(mode="after")` (via `object.__setattr__`, frozen-safe) — the prior `__post_init__` semantics, idempotent on reload.
- `JudgeVote.error` / `MultiChoiceJudgeVote.error` / `EnsembleCriterionReport.error` carry category-prefixed messages; serialization round-trips `error` on ensemble reports, binary judge votes, and multi-choice judge votes — automatically, via the pydantic dump/validate above
- **`reason is None` means "this judge gives no explanation".** `CriterionReport.reason`, `JudgeVote.reason`, `MultiChoiceJudgeVote.reason` and `EnsembleCriterionReport.final_reason` are `str | None` (still required). `None` is reserved for judges that return probabilities instead of text; an LLM judge always sets a string, possibly empty — enforced by `_require_llm_reason`, which turns a null `explanation` from a custom response format into a `parse` failure, as before the widening, unless an `[Affects: ...]` tag is appended: the stored reason is then the tagged string `"None [Affects: ...]"` and the verdict stands, as it always has (see [Grading Flow](grading-flow.md)) — and the synthetic reports built with `reason=""` (`rubric.py`) are unchanged — `""` is never used to mean "no explanation". Vote-reason joins skip `None` by identity (see [Grading Flow](grading-flow.md)), so `final_reason is None` only when no vote carried a reason. Consumers are `None`-safe without changing output for strings: `extract_issues` fills `IssueDetail.feedback` (stays `str`) with `final_reason or ""`, `_format_error_criteria` omits the `": reason"` suffix, `validate_held_out` already filled `CriterionExemplar.llm_reason` with `final_reason or ""`, and `meta/_display.py` guards on truthiness
- **Probabilistic-judge vote fields are additive.** `probabilities`/`confidence` (on `CriterionReport`, `JudgeVote`, `MultiChoiceJudgeVote`), `superseded` (votes) and `escalated` (`EnsembleCriterionReport`) default to `None`/`False` — the LLM shape — and live on the base vote types, so the `votes`/`multi_choice_votes` lists serialize them; `EnsembleEvaluationReport.judge_scores` values are `float | None`. Semantics: [Type Catalog](types.md)
- `CriterionReport.reasoning` / `JudgeVote.reasoning` / `MultiChoiceJudgeVote.reasoning` carry the extended-thinking deliberation trace (see [Grading Flow](grading-flow.md)); serialization round-trips it symmetrically with `error` via pydantic `model_dump`/`model_validate` on **both** the single-report and ensemble paths, with field defaults tolerating legacy checkpoints (missing `reasoning`/`error`/`weight`/`na`/`votes`/`agreement`/`probabilities`/`confidence`/`superseded`/`escalated` → field default; a missing/0.0 `agreement` recomputes from the non-`superseded` votes). A checkpoint written before the probabilistic-judge fields existed (fixture `tests/golden/legacy/checkpoint_items.json`) loads, and re-serializing it only *adds* those keys at their defaults (`tests/eval/test_checkpoint_vote_fields.py`)
- Filter `error is not None` results in training pipelines
- Rate limiting via `LLMConfig.max_parallel_requests` (per-provider semaphore); decision models use a per-host bucket (next bullet). `RateLimitPool` keeps **one semaphore per provider key per event loop** (`_semaphores: dict[key, WeakKeyDictionary[loop, Semaphore]]`, guarded by the thread lock `_maps_lock`; the key's limit `_limits[key]` is shared, strictest wins, and a stricter limit replaces every loop's semaphore, holders finishing under the old one). An asyncio semaphore binds to the loop on which it first makes a task wait; one shared across loops made a waiting request on a later `asyncio.run` raise `RuntimeError`, which `classify_grading_error` routes as `unknown`, i.e. a silent worst-case verdict. A semaphore that made a task wait references its loop, so `get_semaphore` drops closed loops' entries explicitly and the pool never keeps a finished loop alive. The limit applies within one loop; requests on different loops never wait for each other. The lookup is by the running loop, not merely "the one live entry": closed-loop cleanup alone would empty the map between successive `asyncio.run` calls, so `TestRateLimitPoolEventLoops` also pins a loop left open (`run_until_complete` on a kept loop, then `asyncio.run`, then the kept loop again) and two loops running at once in different threads, each limited through its own semaphore
- **Decision-model client (`DecisionModelClient` in `decision.py`, internal).** The counterpart of `LLMClient` for `DecisionModelConfig` judges (field reference: [Type Catalog](types.md)).
  - *Packaging.* The transport is the official `typesafe-sdk`, the optional extra `autorubric[typesafe]` (`typesafe-sdk>=0.7.1` and `httpx2>=2.0.0`, the first `[project.optional-dependencies]` entry; pinned by tests reading `pyproject.toml`). `httpx2` is the SDK's HTTP stack and part of its public API (`http_client`, `transport`, `httpx2.Timeout`); the extra declares it because the client imports it directly, to parse base URLs (*Resolution* below) and to build each SDK client's HTTP client (*Connections* below). 0.7.1 is the first SDK release that validates the API key when it builds a client and redacts credentials from transport errors: under 0.7.0 a key with a line break reached the HTTP layer, whose error (`Illegal header value b'Bearer …'`) `_failed_judgment_result` recorded in every report's `error`/`reason`, and so in checkpoints and logs. The dev dependency group self-references `autorubric[typesafe]`, so the test suite always runs against the real SDK types. `_import_typesafe_sdk()` imports it when a client is built (`DecisionModelClient.__init__`) or a question object is built (`build_question`, hence `build_questions`, so the framing helpers need the SDK too) and turns a missing SDK into an `ImportError` saying `pip install 'autorubric[typesafe]'`; `import autorubric`, `DecisionModelConfig` and `classify_grading_error` never import it (pinned by a fresh-interpreter test).
  - *Resolution, once, at construction, the way the SDK resolves:* API key = explicit `api_key`, else `TYPESAFE_API_KEY` (which the `.env` loaded by `llm.py`'s `load_dotenv()` may set), stripped; blank → `ValueError`, so a grader fails at construction instead of abstaining per item. A key the SDK would reject is as unusable as a missing one, so `_is_valid_api_key` applies the SDK's own rule (printable ASCII, no whitespace — `isascii() and isprintable() and " " not in key`; the SDK checks it only when it builds a client, i.e. on a request) and a failing key → `ValueError` naming its source (`DecisionModelConfig.api_key` or the environment variable) and never repeating the key; the rule is pinned against the installed SDK's `TypeSafeClient` constructor, and it also keeps a control character from ever reaching an HTTP error message. Base URL = explicit `api_base`, else `TYPESAFE_BASE_URL` (stripped), else the SDK's `DEFAULT_BASE_URL`; trailing `/` removed; then checked in two steps, so a base URL no request could use fails at construction, never as a worst case or an abstention on every criterion of every item. (1) `_check_base_url` (stdlib only, which `DecisionModelConfig` also applies to `api_base`, so a config never needs the SDK): not an absolute http(s) URL with a host and a valid port, or containing whitespace or a control character, a query or fragment, or credentials → `ValueError`. Whitespace and control characters are checked before `urlsplit`, which silently drops tabs and line breaks (and leading spaces and control characters) and would pass, say, a URL read with its trailing newline, which `httpx2` then refuses on every request as an `unknown` error, the worst case on every criterion of every item. The SDK builds each request URL as the string `base_url + "/v1/systemone"` (`_SYSTEM_ONE_PATH`, pinned by the wire test), so after a query (`https://h/api?tenant=a` → path `/api`, query `tenant=a/v1/systemone`), even an empty one, or a fragment (dropped with the path) the endpoint path is never reached: every request fails (typically a 404, i.e. `infrastructure`), an abstention on every criterion of every item; a `?` or `#` anywhere is rejected, since neither appears unescaped in any other part of a URL. `httpx2` turns URL credentials (`user:password@`, any `@` in the netloc) into Basic authentication, which replaces the SDK's `Bearer <api_key>`, so the key the config insists on would never be sent (typically a 401 on every request) and the SDK would log the credentials with the request URL at `INFO`: rejected, pointing to `api_key`. No error message repeats a URL holding an `@` anywhere (`_shown_url`), since it may hold credentials. (2) `_check_request_url`, when the client is built (the SDK already imported): `httpx2.URL(base_url + _SYSTEM_ONE_PATH)` parses the exact request URL with the SDK's own HTTP stack, and `httpx2.InvalidURL` → `ValueError` naming the source. It catches what only the HTTP stack knows, chiefly hosts it cannot encode: a non-ASCII host that is not a valid IDNA 2008 name (fullwidth letters pasted from a document, `☃☃.com`) or an impossible dotted-decimal IPv4 address. `InvalidURL` subclasses `Exception`, not `httpx2.RequestError`, so the SDK does not wrap it in a `TypeSafeError`; raised inside every request, it would route as `unknown`, the conservative worst case (UNMET for positive weights, MET for negative) on every criterion of every item. Both steps apply to `api_base` and `TYPESAFE_BASE_URL` alike. The SDK's public `typesafe_sdk.constants` (`API_KEY_ENV`, `BASE_URL_ENV`, `DEFAULT_BASE_URL`) are reused, not copied.
  - *HTTP environment.* `httpx2` reads the environment whenever it builds an `httpx2.AsyncClient`: TLS trust (`SSL_CERT_FILE`, else `SSL_CERT_DIR`, else the system store) and proxies (`HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`/`NO_PROXY` in either letter case, else the system's proxy settings, via `urllib.request.getproxies`), outside the SDK's error handling; and every loop's SDK client gets a new one (`_new_http_client`). Its failures are no SDK errors: `FileNotFoundError` for an `SSL_CERT_FILE` naming a missing file, `ImportError` for a SOCKS proxy without `socksio`, `ValueError` for a proxy URL whose scheme no proxy has. Raised inside every request they would route as `unknown`, the conservative worst case on every criterion of every item (flipping mixed-ensemble majorities), or, for a `ValueError`, as a `parse` abstention, although they say nothing about any submission; the LLM path, where litellm wraps them, abstains as `infrastructure`. So `__init__` builds one HTTP client and drops it (it opens no connection): an environment in which none can be built fails construction, with `httpx2`'s own exception plus an `add_note` naming the model and the settings to check. Should the environment change later (a proxy set mid-run, a CA file removed) so that a lease cannot build one, `_lease_sdk_client` raises `TypeSafeAPIConnectionError` ("Request not sent: ...", chained from the cause) before any SDK client exists: the request is not sent, routes as `infrastructure` (an abstention, as for an unreachable endpoint), and leaves no lease behind. Pinned by `TestHttpEnvironment` and the grader tests over the parametrized `http_environment` fixture (`HttpEnvironment`, `HTTP_ENVIRONMENT_FAILURES`: missing CA file, SOCKS proxy without `socksio`, unknown proxy scheme).
  - *Transport.* `AsyncTypeSafeClient(api_key=, base_url=, model=config.model, headers=extra_headers, retry=RetryPolicy(max_retries=max_retries - 1, timeout=max_retries * (timeout + backoff_max)), http_client=httpx2.AsyncClient(limits=httpx2.Limits(max_connections=...), timeout=httpx2.Timeout(config.timeout, pool=None)))`, with `backoff_max` read from the SDK's default `RetryPolicy()` (5 s); the SDK takes its per-request timeout from the HTTP client and closes the HTTP client when it closes (*Connections* below). `max_retries` counts attempts as in `LLMConfig` (the SDK counts retries after the first); retries, backoff and `Retry-After` are the SDK's (429, 408, 5xx, connection errors, timeouts). The SDK honours `Retry-After` with no cap of its own; the only bound on its waits is `RetryPolicy.timeout`, a total budget from the first attempt (tenacity `stop_before_delay`: a retry whose wait would end at or past it is not made and the last error is raised). The budget, `max_retries * (timeout + backoff_max)`, has room for every attempt's full timeout plus the longest exponential-backoff wait before each, so it never cuts backoff retries short, even with a timeout shorter than the backoff (the SDK default of 30 s would, against a 60 s per-request timeout), while a `Retry-After` that would end past it (an exhausted quota's `3600`) fails the request at once, as `infrastructure`, instead of sleeping for hours inside the `RateLimitPool` slot. It is the counterpart of `LLMConfig`'s per-wait cap `retry_max_wait` (tenacity `wait_exponential`, which ignores `Retry-After`). `DecisionModelConfig` requires `max_retries * timeout` to be finite. One request per `system_one(state, questions)` call, carrying exactly those arguments. `extra_headers` goes out as given, except the headers the SDK sets itself (below), so `DecisionModelConfig.__post_init__` admits only what HTTP allows (RFC 9110): names that are tokens (`_HTTP_FIELD_NAME`) and values of visible ASCII with spaces or tabs only between characters (`_HTTP_FIELD_VALUE`; obs-text is left out because clients encode header values as ASCII). Anything else — typically a secret read from a file with its trailing newline — fails at construction, naming the header but never its value, instead of on every request after every retry with an error that repeats the value (the SDK redacts only a fixed set of credential header names) into every failed report's `error`. The accepted and refused cases are pinned against the SDK's HTTP stack (`httpx2` encoding, `h11` validation). Headers the SDK sets itself are rejected too, case-insensitively (`_SDK_OWNED_HEADERS`: `Authorization`, which carries the bearer `api_key`, `Accept`, `Content-Type`, `User-Agent`, `X-TypeSafe-SDK`, `X-TypeSafe-Runtime`, `X-TypeSafe-Retry-Count`): the SDK's request preparation merges the given headers first, then overwrites these (and drops a given retry count, which it sets on retries only), so a value given for one would never be sent. A gateway expecting its own `Authorization` scheme, say, would refuse every request, an abstention on every criterion of every item with nothing pointing at the dropped header; the `ValueError` names the header (never its value) and, for `Authorization`, points to `api_key`. This is where `extra_headers` departs from `LLMConfig`'s, which override the provider SDK's defaults. `TestHeadersTheSdkSets` pins both halves against the installed SDK: the set equals the headers a System One request carries, on its first attempt or a retry, that plain `httpx2` would not send with that value, and the SDK replaces any value given for each.
  - *Event loops.* An SDK client's connections belong to the loop that opened them and can be neither used nor closed from another. `_lease_sdk_client()` keeps one SDK client per running loop, with its connection slots (*Connections* below), in a `WeakKeyDictionary[loop, (client, connection_slots, in_flight)]`: requests in flight together share it (connection reuse), and the last one to finish closes it on that loop (a close failure is logged, never raised). Successive `asyncio.run` calls therefore each get a fresh client, and no connection outlives its loop. `close()` only closes the disk cache.
  - *Rate limiting.* Through `RateLimitPool` under `rate_limit_key` = `decision-model@<host>` (`host`: the resolved base URL's host, lowercased, a non-default port kept, credentials dropped) — not `_normalize_to_provider`, which would split `"jev-latest"` and `"my-org/x"` on one endpoint into unrelated buckets. Every model on a host shares the bucket and the strictest `max_parallel_requests` wins; like the SDK client, the semaphore is per event loop (the `RateLimitPool` bullet above), so successive `asyncio.run` batches under a limit grade exactly alike. The SDK client is leased before waiting on the semaphore, so queued requests keep it alive; a request holding the semaphore then waits for a connection slot (*Connections*).
  - *Connections.* A request is handed to the SDK only when its SDK client has a free connection. Each SDK client gets a new `httpx2.AsyncClient` (`_new_http_client`) holding `max_parallel_requests` connections, or `_DEFAULT_CONNECTIONS` (100, httpx's default pool, the one the SDK's own HTTP client has) when it is `None`; `_lease_sdk_client` pairs it with an `asyncio.Semaphore` of as many slots, per loop, and `system_one` acquires the host's `RateLimitPool` semaphore (if any) and then a slot before calling the SDK. `None` therefore means no *shared* limit, not unbounded connections: each judge keeps at most 100 requests in flight per loop, and a limit sizes the pool instead, so one above 100 is honoured (the SDK's own client would cap every limit at 100). Why the wait is outside the SDK: time spent inside it counts against the request's `timeout` and its retry budget (both from the first attempt), although the endpoint is not involved. Left to the SDK's own client, requests beyond its 100 connections would queue in httpx's pool, whose wait is bounded by the client's `timeout` (`httpx2.PoolTimeout` → `TypeSafeAPITimeoutError` → `infrastructure`): with the default `None` and `EvalRunner`'s default `max_concurrent_items=None`, every item beyond about `100 * max_retries * timeout / latency` would abstain on every criterion without its request ever reaching the endpoint, and a request that had waited longer than the budget would get no retry after a transient failure. The HTTP client's timeout is `httpx2.Timeout(timeout, pool=None)`: each HTTP operation (connect, read, write) is timed, a wait for a connection is not, so a spurious timeout cannot come back even if a request ever waited for a connection. Unbounded connections for `None` were rejected: one socket per in-flight item exhausts the process's file descriptors (a soft limit of 256 on macOS, 1024 on Linux by default) and floods the endpoint, the same failure (abstentions the endpoint never caused) at a lower count. The HTTP client is passed as `http_client`, not a `transport`, so `httpx2` still sets up proxies from the environment. Pinned by `TestConnections` on the whole HTTP stack, connection pool included, over the in-memory network of the `http_network` fixture (`InMemoryNetwork`): without a limit, requests beyond 100 wait four timeouts and none fails; a limit of 150 puts 150 at the endpoint at once; and requests queued behind 100 slow ones for longer than the retry budget still retry a 503.
  - *Cache.* The same diskcache store as `LLMClient`: both open it through `_open_response_cache(cache_dir)` in `llm.py`. One entry per request; key = SHA-256 of `_canonical_json([model, base_url, state, questions])` — question objects in their wire form and any mapping/sequence normalized, so equivalent representations share a key, but key order kept, because the endpoint sees it (a Choice question's option order). `decision_threshold`, the framings (already expressed in the questions), the price, timeouts, retries, headers and API key are not in the key, so re-thresholding re-reads cached answers instead of re-querying. The value is `response.model_dump_json()`, re-validated with `SystemOneResponse.model_validate_json` on a hit — lossless, usage included; the raw HTTP response and request id are not stored (they carry the request headers, bearer token included). An unreadable entry is a miss (warning logged) and is replaced; failed requests are never cached; `use_cache=` overrides `cache_enabled` per call.
  - *Usage and cost.* `token_usage(response)` maps `input_tokens` → `prompt_tokens` and `output_tokens` → `completion_tokens` (an unreported count is 0, as for LLM usage). `completion_cost(response)` = input tokens × `input_cost_per_token`; `None` (unknown, never a fabricated `0.0`) when the price is unset or input tokens are unreported. A cache hit carries the stored usage, so a re-run reports the same cost at the configured price. `CriterionGrader` attaches a request's usage and cost to the item's first `CriterionResult`, so per-item totals are exact; an unpriced decision model adds nothing to `completion_cost`, which stays `None` when nothing priced contributed ([Grading Flow](grading-flow.md))
  - *Manifest.* `_serialize_grader_config` records a decision-model judge's `judge_kind`, framings, `decision_threshold` and `api_base_host` (the client's resolved host), never its key, the rest of its URL or `extra_headers` ([Reproducibility & Seed Coordination](reproducibility.md))
- **Temperature is sent only when set.** `LLMConfig.temperature=None` (default) omits `temperature` from the litellm request so the provider default applies (GPT-5.x-style reasoning models accept only their default; Gemini 3 recommends its default of 1.0; Anthropic extended thinking requires 1). Any explicit value, including `0.0`, is sent unchanged. A per-call `LLMClient.generate(temperature=...)` kwarg overrides the config (`None` = omit for that call). The response cache key (`LLMClient._cache_key`) embeds the effective temperature (per-call override, else config): explicit values keep the pre-change key format (existing entries still hit), while unset renders as `temp=None`, a separate key. The default was `0.0` (always sent) up to and including v1.5.3; `temperature=0.0` restores that behaviour. `0.0` reduces variance but is not guaranteed deterministic on most providers
- Multi-choice criteria get a guaranteed abstain option by default (`CriterionGrader(auto_na_option=True)`, auto-injected NA — binary-CANNOT_ASSESS parity; see [Multi-Choice Criteria](multi-choice.md)); set `auto_na_option=False` for forced-choice. Never strips an author NA option
- **Single-source metric-redundancy notes.** The conflation / cluster / different-geometry / κ−φ-gap notes are rendered **only** in `MetricsResult.summary()` / `to_dataframe()` and the metric field docstrings (`metrics/_types.py`); they are never copied into the Rich/HTML report paths (`meta/_display.py`). On binary/nominal data Krippendorff's α is the single primary inter-judge statistic and the bare Fleiss column is dropped (they coincide up to a finite-sample correction); ordinal keeps both with a different-geometry note.
