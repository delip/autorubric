### Reproducibility & Seed Coordination
`CriterionGrader(seed=...)` controls all non-LLM randomness (option shuffling, few-shot example selection). Auto-generated when `None` so shuffles are always pinned.

- Per-call shuffle RNGs derived from `(master_seed, content_hash, criterion_idx, judge_id)` via SHA-256 — concurrency-safe (no shared mutable state). Helper: `_derive_shuffle_rng()` in `criterion_grader.py`.
- If `FewShotConfig.seed` is unset, it is coordinated from the master seed.
- Few-shot example selection RNGs are derived per `(few_shot_seed, criterion_idx, judge_id)` via the same `_derive_shuffle_rng` helper (a constant `FEW_SHOT_DOMAIN` sits in the item-key slot — few-shot examples are a fixed property of criterion+judge, not item-specific), de-correlating selected examples and their ordering across both judges and criteria. Mirrors option shuffling and supports the ensemble-independence assumption behind the inter-judge agreement metrics; selection stays fully reproducible. An example's reason (`DataItem.ground_truth_reasons`, shown under `FewShotConfig.include_reason=True`) rides along with its item and draws no randomness, so a seed draws the same examples in the same order whether or not the training data has reasons ([Grading Flow](grading-flow.md)).
- `CriterionReport.shuffle_order` records the permutation per multi-choice criterion.
- `ExperimentManifest.grader_config` persists `master_seed`, `shuffle_options`, `auto_na_option` for checkpoint reproducibility (via `_serialize_grader_config` in `eval.py`). Its `judges` list records per judge `judge_id`, `judge_kind` (`"llm"` / `"decision_model"`), `model`, `weight`, `max_parallel_requests`; an LLM judge adds `temperature` (`null` = provider default) — its entry is its pre-decision-model entry plus `judge_kind`, every other key and value unchanged — and a decision-model judge (built by `_decision_model_judge_entry`) adds `binary_framing`, `ordinal_framing`, `decision_threshold` and `api_base_host`: the host, with any non-default port, of the base URL its client resolved at construction (`api_base`, else `TYPESAFE_BASE_URL`, else the SDK default), falling back to an explicit `api_base`'s host, else `null`, for a grader without such a client. It has no `temperature` key, an LLM-only setting. The API key, the rest of the base URL (its path) and `extra_headers` are never recorded. The base URL is not a secret, though: it cannot hold credentials (`_check_base_url` rejects them), and a failed request's `error`, recorded in every report the request fails and so in checkpoints, shows the request URL with its path, as the SDK reports it and logs it; secrets belong in `api_key` (pinned by `test_the_base_url_is_no_secret_the_manifest_records_its_host`). Known gap, deliberately left as is: `normalize` is never recorded for a `CriterionGrader`, because `_serialize_grader_config` reads `grader._normalize` while `Grader` stores `normalize`. A cascade adds the key `escalation` (absent for every other grader, so LLM-only manifests are unchanged): `{"judges": [...], "threshold": ..., "per_criterion": {...} or null}`, each escalation judge an LLM entry exactly as in `judges` (the shared `_llm_judge_entry`: `judge_id`, `judge_kind`, `model`, `temperature`, `weight`, `max_parallel_requests`); the `judges` list holds the decision model alone. It is read from the grader's own validated copy of the config (`grader._escalation`), so it records the escalation judges and thresholds the grader uses even when the caller changes its `EscalationConfig`'s list or dict in place afterwards.
- Few-shot selection applies to LLM judges only: a decision-model judge gets no examples, and its request does not depend on the few-shot seed.
- **Cascades.** An escalation judge (`EscalationConfig.judges`) judges an escalated criterion through `_judge_single_criterion` under the criterion's original `criterion_idx`, so its shuffle and few-shot RNG keys — `(master_seed, item key, criterion_idx, judge_id)` and `(few_shot_seed, criterion_idx, judge_id)` — and hence its prompt are those of a non-cascade grader with the same `seed` and `judge_id`. A bare `LLMConfig` escalation judge is named `"escalation"` (while `judge_model_config=` names its judge `"default"`), so an LLM run meant to be compared criterion for criterion with a cascade — e.g. replayed against it with `replay_escalation` ([Offline Cascade Replay, Diagnostics and Calibration](grading-flow.md)) — is built as `CriterionGrader(judges=[JudgeSpec(llm, "escalation")], seed=S)` (i.e. `judges=escalation.judges`) and the cascade deployed with `seed=S`; otherwise the prompts differ on shuffled multi-choice criteria and few-shot runs. The RNG keys are only part of it: the prompts are equal only when the run also has the cascade's other LLM settings (`shuffle_options`, system prompts, few-shot settings, `auto_na_option`; the full condition is under *Exactness* in [Offline Cascade Replay, Diagnostics and Calibration](grading-flow.md)). Which criteria escalate depends on the decision model's answers, so it is as reproducible as they are (the response cache, next bullet).
- Decision-model answers (`DecisionModelConfig` judges) are also outside the seed's control and are not bit-deterministic: an identical request can return slightly different probabilities, so a verdict near `decision_threshold` can flip between runs. With `cache_enabled=True` a re-run is served from the response cache (one entry per request, and per judge in an ensemble or cascade, stored losslessly, usage included) and returns identical answers; `decision_threshold` is not in the cache key, so re-thresholding re-reads cached answers instead of re-querying (see [Key Conventions](conventions.md)).
- LLM sampling is outside the seed's control. `temperature` is omitted from requests unless set (see [Key Conventions](conventions.md)), so run-to-run behaviour of LLM outputs depends on the provider's default temperature unless you pin it; even `0.0` is not guaranteed deterministic on most providers.
- With `auto_na_option=True`, a multi-choice criterion previously lacking an NA option gains one (appended at end), so its shuffle permutation spans one more index and `shuffle_order` grows by one; criteria that already had an NA option are unaffected.
