### Reproducibility & Seed Coordination
`CriterionGrader(seed=...)` controls all non-LLM randomness (option shuffling, few-shot example selection). Auto-generated when `None` so shuffles are always pinned.

- Per-call shuffle RNGs derived from `(master_seed, content_hash, criterion_idx, judge_id)` via SHA-256 — concurrency-safe (no shared mutable state). Helper: `_derive_shuffle_rng()` in `criterion_grader.py`. The content hash is the first 16 hex digits of the submission's SHA-256 (computed only when options are shuffled). Both ways of calling an LLM judge present a criterion through the one helper `_presented_criterion`, so under `llm_calls="per_item"` a multi-choice criterion's option permutation — and its `shuffle_order` — is identical to the one a per-criterion call with the same `seed`, `judge_id` and `criterion_idx` shows: the key never depends on how the judge is called or on the other criteria.
- If `FewShotConfig.seed` is unset, it is coordinated from the master seed.
- For a judge called per criterion (the default `llm_calls`), few-shot example selection RNGs are derived per `(few_shot_seed, criterion_idx, judge_id)` via the same `_derive_shuffle_rng` helper (a constant `FEW_SHOT_DOMAIN` sits in the item-key slot — few-shot examples are a fixed property of the judge, here per criterion, never of the item being graded), de-correlating selected examples and their ordering across both judges and criteria. Mirrors option shuffling and supports the ensemble-independence assumption behind the inter-judge agreement metrics; selection stays fully reproducible. An example's reason (`DataItem.ground_truth_reasons`, shown under `FewShotConfig.include_reason=True`) rides along with its item and draws no randomness, so a seed draws the same examples in the same order whether or not the training data has reasons ([Grading Flow](grading-flow.md)).
- **Item-level few-shot (`llm_calls="per_item"`).** A judge draws whole training items once, not examples per criterion: `_select_item_examples(judge_id)` shuffles the eligible items (in dataset order) with `_derive_shuffle_rng(few_shot_seed, FEW_SHOT_DOMAIN, -1, judge_id)` — `-1` fills the criterion slot, standing for the whole rubric, and is no criterion's index — then takes the first `n_examples` of that order (`balance_verdicts=False`) or picks by greedy label coverage with ties broken by it (`balance_verdicts=True`; rule: [Type Catalog](types.md)). The selection is deterministic for a seed and judge, each judge draws its own (keyed on its `judge_id`, escalation judges included), reasons draw nothing, and it is made once at construction into `_item_examples`, each item taken as it then was (`(submission, labels, reasons)`, so a later change to a training item changes no prompt, as with per-criterion examples), so every item's call is given the same examples in the same order (an example with no judgment to show for the graded rubric is left out of the call); each multi-choice label is renumbered to the option's position in that call's shuffled order.
- `CriterionReport.shuffle_order` records the permutation per multi-choice criterion.
- `ExperimentManifest.grader_config` persists `master_seed`, `shuffle_options`, `auto_na_option` for checkpoint reproducibility (via `_serialize_grader_config` in `eval.py`). A grader whose `_llm_calls` is `"per_item"` (read with `getattr`, so a grader without the attribute records nothing) adds `"llm_calls": "per_item"`, right after `auto_na_option`, even when every judge is a decision model; a `"per_criterion"` grader (the default, or given explicitly) has no such key, so its manifest is byte-identical to one written before the setting existed, as the cascade-only `escalation` key below leaves other manifests unchanged. Per-judge entries are unchanged, and a cascade's `escalation` key is the same in both modes (`TestManifest` in `tests/graders/test_per_item_calls.py` and `tests/escalation/test_per_item_cascade.py`). Its `judges` list records per judge `judge_id`, `judge_kind` (`"llm"` / `"decision_model"`), `model`, `weight`, `max_parallel_requests`; an LLM judge adds `temperature` (`null` = provider default) — its entry is its pre-decision-model entry plus `judge_kind`, every other key and value unchanged — and a decision-model judge (built by `_decision_model_judge_entry`) adds `binary_framing`, `ordinal_framing`, `decision_threshold` and `api_base_host`: the host, with any non-default port, of the base URL its client resolved at construction (`api_base`, else `TYPESAFE_BASE_URL`, else the SDK default), falling back to an explicit `api_base`'s host, else `null`, for a grader without such a client. It has no `temperature` key, an LLM-only setting. The API key, the rest of the base URL (its path) and `extra_headers` are never recorded. The base URL is not a secret, though: it cannot hold credentials (`_check_base_url` rejects them), and a failed request's `error`, recorded in every report the request fails and so in checkpoints, shows the request URL with its path, as the SDK reports it and logs it; secrets belong in `api_key` (pinned by `test_the_base_url_is_no_secret_the_manifest_records_its_host`). Known gap, deliberately left as is: `normalize` is never recorded for a `CriterionGrader`, because `_serialize_grader_config` reads `grader._normalize` while `Grader` stores `normalize`. A cascade adds the key `escalation` (absent for every other grader, so LLM-only manifests are unchanged): `{"judges": [...], "threshold": ..., "per_criterion": {...} or null}`, each escalation judge an LLM entry exactly as in `judges` (the shared `_llm_judge_entry`: `judge_id`, `judge_kind`, `model`, `temperature`, `weight`, `max_parallel_requests`); the `judges` list holds the decision model alone. It is read from the grader's own validated copy of the config (`grader._escalation`), so it records the escalation judges and thresholds the grader uses even when the caller changes its `EscalationConfig`'s list or dict in place afterwards.
- Few-shot selection applies to LLM judges only: a decision-model judge gets no examples, and its request does not depend on the few-shot seed.
- **Cascades.** Called per criterion (the default `llm_calls`), an escalation judge (`EscalationConfig.judges`) judges an escalated criterion through `_judge_single_criterion` under the criterion's original `criterion_idx`, so its shuffle and few-shot RNG keys — `(master_seed, item key, criterion_idx, judge_id)` and `(few_shot_seed, criterion_idx, judge_id)` — and hence its prompt are those of a non-cascade grader with the same `seed` and `judge_id`. Under `llm_calls="per_item"` it makes, for an item with any escalated criterion (no call otherwise), exactly the full-rubric call `_judge_rubric_in_one_call` that a non-cascade `per_item` grader with the same `seed` and `judge_id` makes — every criterion in rubric order, the same option permutations and the same item-level examples (`_item_examples[judge_id]`, keyed `(few_shot_seed, FEW_SHOT_DOMAIN, -1, judge_id)`) — and keeps the escalated criteria's results only; with the same `LLMConfig` and its cache enabled it therefore shares that grader's response-cache entries (same prompts, same `judge_id` namespace). The two modes' prompts differ, so an LLM run meant to match a cascade needs the cascade's `llm_calls` as well, and so does the replay's `llm_calls` keyword, which sets its cost and time estimates. A bare `LLMConfig` escalation judge is named `"escalation"` (while `judge_model_config=` names its judge `"default"`), so an LLM run meant to be compared criterion for criterion with a cascade — e.g. replayed against it with `replay_escalation` ([Offline Cascade Replay, Diagnostics and Calibration](grading-flow.md)) — is built as `CriterionGrader(judges=[JudgeSpec(llm, "escalation")], seed=S)` (i.e. `judges=escalation.judges`; with `llm_calls="per_item"` added for a `per_item` cascade, replayed with `replay_escalation(..., llm_calls="per_item")`) and the cascade deployed with `seed=S`; otherwise the prompts differ on shuffled multi-choice criteria and few-shot runs. The RNG keys are only part of it: the prompts are equal only when the run also has the cascade's other LLM settings (`llm_calls`, `shuffle_options`, system prompts, few-shot settings, `auto_na_option`; the full condition is under *Exactness* in [Offline Cascade Replay, Diagnostics and Calibration](grading-flow.md)). Which criteria escalate depends on the decision model's answers, so it is as reproducible as they are (the response cache, next bullet).
- Decision-model answers (`DecisionModelConfig` judges) are also outside the seed's control and are not bit-deterministic: an identical request can return slightly different probabilities, so a verdict near `decision_threshold` can flip between runs. With `cache_enabled=True` a re-run is served from the response cache (one entry per request, and per judge in an ensemble or cascade, stored losslessly, usage included) and returns identical answers; `decision_threshold` is not in the cache key, so re-thresholding re-reads cached answers instead of re-querying (see [Key Conventions](conventions.md)).
- LLM sampling is outside the seed's control. `temperature` is omitted from requests unless set (see [Key Conventions](conventions.md)), so run-to-run behaviour of LLM outputs depends on the provider's default temperature unless you pin it; even `0.0` is not guaranteed deterministic on most providers.
- **Response cache under `llm_calls="per_item"`.** A `per_item` judge's call is one `LLMClient.generate` request per (item, judge), so the response cache (`LLMClient._cache_key`: model, both prompts, the response format's `__name__`, the sampling settings and the judge's `cache_namespace`) holds one entry per (item, judge). The key names `RubricJudgment` where a per-criterion call's names `CriterionJudgment` or `MultiChoiceJudgment` (and the prompts differ too), so `per_item` and `per_criterion` entries never collide and switching modes never reads the other mode's answers. The cached value is the parsed `RubricJudgment`, pickled with its `_unusable` entries, so a re-run maps a cached reply exactly as the original, per-criterion failures included (a reply that parses but lacks a criterion's judgment is cached like any parsed reply; one that does not parse is never cached) (`TestEndToEnd` in `tests/graders/test_per_item_calls.py`).
- **Resume does not check `llm_calls`.** `EvalRunner` resumes on the dataset hash alone ([Key Conventions](conventions.md)), so resuming a run with a grader of the other `llm_calls` grades the remaining items in that mode and mixes both in one run, silently, as changing any other grader setting does. Neither a resumed run nor `replay_escalation` can tell which mode a run used.
- With `auto_na_option=True`, a multi-choice criterion previously lacking an NA option gains one (appended at end), so its shuffle permutation spans one more index and `shuffle_order` grows by one; criteria that already had an NA option are unaffected.
