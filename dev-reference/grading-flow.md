### Grading Flow
1. `Rubric.grade()` delegates to grader's `grade()` method, adding `guidelines=self.guidelines` only when the rubric has guidelines (see *Rubric guidelines* below)
2. `CriterionGrader` treats a single judge (`judge_model_config=`, or its deprecated alias `llm_config=` — see [Key Conventions](conventions.md)) as an "ensemble of 1" with `judge_id="default"`. At the start of `judge()` the rubric is normalized **once** to an *effective rubric*: with `auto_na_option=True` (default) every multi-choice criterion is guaranteed an NA abstain option via `Criterion.with_guaranteed_na_option()` (structural analog of binary CANNOT_ASSESS; see [Multi-Choice Criteria](multi-choice.md)). Normalization is pure (no RNG), same length/order (so `criterion_idx` and the shuffle RNG key stay aligned), never mutates the user's rubric. Effective options ride through `CriterionReport.options`, shared by prompt building, verdict mapping, scoring, and aggregation. `auto_na_option=False` ⇒ forced-choice (no injection); never strips an author NA option.
   - **Judge identity: repeated `judge_id`s warn.** A `judge_id` keys the client maps (`_clients`/`_decision_clients`, last write wins), the few-shot examples (`_criterion_examples`/`_multi_choice_examples`), the shuffle and few-shot RNGs (`_derive_shuffle_rng`), `judge_scores` and the per-judge metrics, so `judges=` with a repeated id conflates those judges: same-kind judges all call the model of the last of them (two kinds keep separate clients), and all share one `judge_scores` key and per-judge metrics entry and identical option shuffles and few-shot examples; `replay_escalation` refuses such a run as `llm_result` (its votes outnumber its `judge_scores` keys). Construction still accepts it and grades exactly as before, but warns `FutureWarning("judge_ids should be unique; repeated: 'x'. ...")` naming each repeat once, sorted (`_repeated_judge_ids`, shared with the cascade's `ValueError`), `stacklevel=2`, after the cascade checks (a cascade's primary is one judge, so a cascade never warns). A repeat becomes a `ValueError` in the next major version, as in a cascade. Why `FutureWarning` rather than `DeprecationWarning`: [Key Conventions](conventions.md). Tests: `tests/graders/test_duplicate_judge_ids.py` (the warning, and grading unchanged as it describes) and `tests/decision/test_decision_ensemble.py` (a repeat across kinds).
3. `judge()` gathers one `_judge_all_criteria_for_judge` per judge (parallel across judges), which dispatches in three branches: a decision-model judge (`isinstance(judge.llm_config, DecisionModelConfig)`, tested first, so `llm_calls` never reaches one) makes **one request per item** for the whole rubric (see *Decision-Model Judges in `CriterionGrader`* below); an LLM judge under the grader's default `llm_calls="per_criterion"` makes concurrent calls, one per criterion, via `asyncio.gather()` over `_judge_single_criterion` (unchanged); an LLM judge under `llm_calls="per_item"` makes **one call per item** for the whole rubric via `_judge_rubric_in_one_call`, and the branch puts that call's usage and cost on `results[0]` with `dataclasses.replace` (see *One call per item (`llm_calls="per_item"`)* below). Whichever branch, the judge returns one `CriterionResult` per criterion of the effective rubric, in order, and everything downstream (`aggregate`, `score_reports`, `judge_scores`, the length penalty in `Grader.grade`) is shared. A cascade then runs its escalation judges on the escalated criteria only (see *Confidence Cascade* below)
4. Binary criteria use `binary_response_format` (default: `CriterionJudgment`); multi-choice criteria use the symmetric `multi_choice_response_format` (default: `MultiChoiceJudgment`). Meta-rubric evals override both — `MetaCriterionJudgment` (binary) and `MultiChoiceMetaJudgment` (multi-choice) — each adding a structured `affected_criteria` field. Both formats are LLM-only: either one with any decision-model judge → `ValueError` at construction (see *Decision-Model Judges in `CriterionGrader`* below). Both describe one criterion's judgment, so under `llm_calls="per_item"`, whose one call per item is always answered as `RubricJudgment`, either one → `ValueError` too (*One call per item (`llm_calls="per_item"`)* below)
5. If the response includes a non-empty `affected_criteria`, grader injects `[Affects: #1, #3]` into the reason string. Applied symmetrically to binary and multi-choice success paths via the shared `_inject_affected_criteria()` helper (error paths never inject). Both success paths then pass the tagged reason through the shared `_require_llm_reason()`, which enforces that an LLM judge's reason is a string: a null `explanation` (possible only with a custom response format that makes it optional) raises `ValueError`, which `classify_grading_error()` routes as `parse` (→ `CANNOT_ASSESS` / the NA option, see *Judge-call failure routing* below), exactly as the report's own `str` validation did before `reason` widened to `str | None`. Like that validation it checks the reason as stored, after tagging, so a tagged null explanation stays the accepted string `"None [Affects: ...]"`. The read order matches the code before the widening, where the null check was the report's own validation and so ran after every read: the binary path reads `explanation` (and tags it), then `criterion_status`, then runs the null check; the multi-choice path reads and range-checks `selected_option`, then reads `explanation`, then runs the check. A custom-format judgment missing a field therefore fails as `unknown` on the first missing field in that order (its recorded `error` text names that field), and a null `explanation` is a `parse` failure only when the verdict field is readable; the binary order is pinned by `test_binary_judgment_missing_a_field_fails_on_the_first_one_read` in `tests/graders/test_error_routing.py`. Both paths now build their report through helpers shared with the one-call-per-item mapping — `_binary_report(criterion, verdict, reason, reasoning)` after the binary reads, and `_multi_choice_report(criterion, selected_option, judgment, reply, shuffled_indices)`, which does the multi-choice reads itself in this order (range check, `explanation`, then the trace from `reply` last) — so the read order, and every per-criterion report, failure reports included, are unchanged (`TestPerCriterionReadOrder` in `tests/graders/test_per_item_calls.py`; *One call per item (`llm_calls="per_item"`)* below).
6. Aggregates votes using strategy (majority/weighted/unanimous/any). For binary criteria `majority` is an **unweighted head-count** (> 50% of judges), distinct from `weighted` (summed judge weights). Multi-choice criteria aggregate via two **independent** knobs — `ordinal_aggregation` and `nominal_aggregation` — that binary `aggregation` never touches (values + axis in [Multi-Choice Criteria](multi-choice.md)). Each vote is built from its judge's `CriterionReport`, copying `reason`, `error`, `reasoning`, `probabilities` and `confidence` (and `superseded=True` for a cascade's decision-model vote on an escalated criterion; only non-superseded votes are aggregated, see *Confidence Cascade* below). `EnsembleCriterionReport.final_reason` comes from the shared `_join_vote_reasons(votes)` (binary `_aggregate_votes` and both multi-choice returns of `_aggregate_multi_choice_votes`, including the all-NA path): each vote renders as `"judge_id: reason"`, joined with `" | "`, **skipping votes whose `reason is None`** by an identity check (not truthiness), so an LLM vote with an empty explanation still renders as `"judge_id: "` exactly as before; the result is `None` when no vote carried a reason. The fixed reasons are unchanged and returned whatever the votes' reasons: `"No votes"` (empty vote list, binary and multi-choice) and the binary `"All judges could not assess"` (every vote `CANNOT_ASSESS`), so `final_reason is None` only when no vote carried a reason, not whenever none did.
7. Returns `EnsembleEvaluationReport`

**Rubric guidelines.** `Rubric.guidelines` (free text for every criterion; [Type Catalog](types.md)) reaches every judge without touching the abstract `Grader` API. Every grading path goes through `Rubric.grade` — `EvalRunner._grade_item` and `fill_ground_truth` via `get_item_rubric(idx).grade(...)`, so a per-item rubric brings its own guidelines (or none) and never inherits the dataset rubric's; the improvement loop via `rubric.grade(...)`.
- **Absent means `None`.** Blank text means no guidelines everywhere: `_normalize_guidelines` (`utils.py`: `None`/blank → `None`, other text verbatim, non-`str` → `TypeError`) is applied by `Rubric`, `Grader.grade`, `CriterionGrader.judge`, the four user-prompt builders (via `_guidelines_block`) and `build_state`.
- **`Rubric.grade`** calls `grader.grade(to_grade=, rubric=, query=, reference_submission=)` exactly as before when the rubric has no guidelines, and adds `guidelines=` only when it has them — and only if `grader.grade` accepts it; a `grade` override with the old signature is called without them, and warns (below), as a legacy `judge` does.
- **`Grader.grade(..., *, guidelines=None)`** (keyword-only) forwards them to `judge` as `guidelines=` only if `judge` accepts that keyword — a `guidelines` parameter that can be passed by keyword, or `**kwargs` (`_accepts_guidelines`; positional-only does not count, an unreadable signature counts as not accepting). Otherwise, and whenever there are none, `judge(to_grade, rubric, query, reference_submission)` is called positionally exactly as before (the call goes through a `cast` to `Callable[..., Awaitable[Any]]`, since the abstract signature does not declare the keyword). The abstract `judge`/`aggregate` signatures are unchanged, so existing subclasses (e.g. the experiments' decision-model grader, the stub in `tests/eval/test_error_report_none_score.py`) keep working. The length-penalty path rebuilds the report exactly as before — no new report fields.
- **Checked once per grader instance** by `_takes_guidelines(grader, method_name)` (`graders/base.py`, shared by both levels): `inspect.signature` runs once and the result is cached **on the instance, not the class**, because the method is looked up through the instance (an instance attribute — wrapper, test double — can replace the class's) and the warning is per instance too. The entry (`_guidelines_support`, keyed by method name) remembers the implementation it describes (`__func__` of a bound method), so a method replaced later is re-inspected. It lives in the instance `__dict__` (`_instance_dict`: only a writable `dict`), which works without a `Grader.__init__` call and bypasses any `__setattr__` override; an object without one is inspected on every call.
- **Legacy warning.** `_warn_ignores_guidelines` issues `UserWarning("<GraderClass> ignores rubric guidelines")` **once per grader instance** (flag `_guidelines_warned` in the instance `__dict__`), and never when the rubric has no guidelines. The flag is set only after `warnings.warn` returns, so under a warnings-as-errors filter (`-W error`, `filterwarnings = error`) the warning raises on every call, as Python's own warning registry makes it, rather than once and then grading without the guidelines unannounced. `_caller_stacklevel()` attributes it to the first frame outside `_INTERNAL_DIRS` — the autorubric package and asyncio: the user's `rubric.grade`/`grader.grade` line, or, for items graded in `evaluate`'s tasks (no user frame above the event loop), the line that started the loop (e.g. `asyncio.run(...)`); `warnings.warn`'s `skip_file_prefixes` does this only from Python 3.12.
- **`CriterionGrader.judge(..., *, guidelines=None)`** normalizes once, then threads them (keyword-only) through `_judge_all_criteria_for_judge` to both judge kinds. **LLM judges:** `build_user_prompt`, `build_few_shot_user_prompt`, `build_multi_choice_user_prompt` and `build_multi_choice_few_shot_user_prompt` take a keyword-only `guidelines: str | None = None`; when set, the user prompt **starts** with `GUIDELINES_BLOCK` (`prompts.py`: `<guidelines>\n{guidelines}\n\nThese guidelines apply to every criterion. The criterion text governs; the guidelines clarify how to apply it.\n</guidelines>`), then a blank line — how the builders separate every block — then the unchanged prompt (embedded as `guidelines_text`, like `query_text`/`reference_text`). Identical for every criterion of an item, it extends the prefix a provider's automatic prompt caching reuses; the precedence rule lives in the block, not the system prompts, so system prompts are untouched, prompts without guidelines stay byte-identical (response caches valid), and a custom `system_prompt` still gets the rule. **Decision models:** the state's first field (*Decision-Model Framing* below).

**Judge-call failure routing.** On a failed judge call the grader calls `classify_grading_error()`. `infrastructure`/`parse` failures → `CANNOT_ASSESS` (binary) or `na=True` (multi-choice), so under the default `CannotAssessStrategy.SKIP` they leave the scoring denominator and do NOT penalize the submission. Only `unknown` errors keep the conservative worst-case verdict: UNMET for positive weight, MET for negative; for multi-choice, the score-minimizing scored (non-NA) option via `Criterion.worst_scored_option()`, never an NA option. An infra/parse abstain points `na=True` at a **genuine** NA option (`criterion.na_option_index`, guaranteed by default auto-injection). With `auto_na_option=False` and no author NA option there is none to point at, so it is a **genuine no-option abstain**: `na=True` with `selected_index=None`/`selected_label=None` — never `na=True` against a scored option, still excluded under SKIP. A stand-in keeps its criterion routed but is no judgment: an item every criterion of which stands in for failed calls has no score, under any strategy (*Score Calculation* below). Decision-model (TypeSafe SDK) failures are classified by the SDK's own exception types, ahead of the `ValueError` rule, by `_classify_typesafe_error` in `llm.py`: `TypeSafeAPIResponseValidationError` (the answer did not validate), `TypeSafeBadRequestError` (400) and `TypeSafeUnprocessableEntityError` (422, e.g. a state over the model's input limit) → `parse`; every other `TypeSafeError` — authentication, permission, not found, rate limit, 5xx, and `TypeSafeAPIConnectionError` / `TypeSafeAPITimeoutError`, which subclass `TypeSafeError` directly, not `TypeSafeAPIError` → `infrastructure`. Both abstain; only the recorded prefix differs. The branch looks `typesafe_sdk` up in `sys.modules` and never imports it: an SDK exception can only exist once the SDK was imported, so a core install without the SDK pays nothing. The category-prefixed message (`"infrastructure: ..."`) is stored on `JudgeVote.error` (binary) / `MultiChoiceJudgeVote.error` (multi-choice). `EnsembleCriterionReport.error` is set only when EVERY contributing vote errored (mixed → genuine verdict, `error is None`), derived via the shared helper `_aggregate_error(votes)` used by both paths (per-vote `.error` is the single source). The `is_error` property on `CriterionReport`/`EnsembleCriterionReport`/`JudgeVote`/`MultiChoiceJudgeVote` distinguishes error-induced from genuine verdicts without string-matching `reason`. Every failure report, for either judge kind, comes from the single module helper `_failed_judgment_result(criterion, judge_id, error, *, shuffle_order=None)`: it classifies, logs the warning (`"Error evaluating criterion ..."` / `"Error evaluating multi-choice criterion ..."`, naming the judge and category), picks the verdict above, and builds the report with `reason="Judge call failed (<category>): <error>"`, the category-prefixed `error`, `usage`/`cost` `None`, and, for multi-choice, the `shuffle_order` the judge was shown. Each criterion kind's report is built with exactly the fields the LLM paths always passed (pydantic's fields-set included), so the LLM path is unchanged; a decision model's failure reports are therefore identical to an LLM judge's for the same exception (pinned by `tests/decision/test_decision_grader.py`).

**Extended-thinking trace preservation.** `LLMClient.generate()` injects the judge's verbose deliberation trace into `judgment.reasoning` (only when thinking is enabled). The grader copies `judgment.explanation` → `CriterionReport.reason` (concise conclusion) **and** `judgment.reasoning` → `CriterionReport.reasoning` (the deliberation it was distilled from) at both binary and multi-choice success constructions, via `getattr(judgment, "reasoning", None)` (tolerates custom `binary_response_format` models lacking the field; the multi-choice path's `_multi_choice_report` reads `getattr(reply, "reasoning", None)`, the reply being the judgment itself for a call of its own). Under `llm_calls="per_item"` the call's one trace, `RubricJudgment.reasoning`, is copied onto every criterion judged from a usable judgment (*One call per item (`llm_calls="per_item"`)* below). Ensemble aggregation forwards each judge's `cr.report.reasoning` → `JudgeVote.reasoning` / `MultiChoiceJudgeVote.reasoning` (alongside the `error` copy). Error-path reports carry `reasoning=None`. There is **no** top-level `EvaluationReport`/`EnsembleEvaluationReport.reasoning` and **no** aggregated `EnsembleCriterionReport.reasoning` — concatenating per-judge traces has no clean semantics, so per-vote granularity is the carrier (unlike `error`, whose all-failed aggregation transfers).

**Provider schema vs parsing schema (`reasoning`-strip).** Because `judgment.reasoning` is *injected* from the provider's separate thinking channel and never read from the model's JSON output, the `reasoning` field is dead weight in the schema sent over the wire. Under OpenAI/Groq **strict** structured output, every property is forced into `required`, so leaving `reasoning` in the provider schema makes models that follow the prompt (which only asks for `criterion_status`/`selected_option` + `explanation`) — e.g. **Llama and Qwen on Groq** — fail schema validation and collapse every verdict to `CANNOT_ASSESS`. `LLMClient.generate()` therefore routes `response_format` through `_provider_response_format()` (in `llm.py`), which, for any response model carrying a `reasoning` field, sends litellm a json-schema dict with `reasoning` removed from `properties`/`required` (built via `litellm.utils.type_to_response_format_param`); **parsing still uses the full Pydantic model**, so reasoning injection when thinking is enabled is unaffected. Models without a `reasoning` field (custom `binary_response_format`s) and any unexpected litellm shape fall through unchanged — no behavior change for OpenAI/Anthropic/Gemini (verdicts identical with and without the strip). The strip works on the top level only, which is why the whole-rubric `RubricJudgment` carries `reasoning` there and its per-criterion entries carry none (*One call per item (`llm_calls="per_item"`)* below).

**Few-shot examples and their reasons (LLM judges).** This paragraph describes LLM judges called per criterion (the default `llm_calls`); under `llm_calls="per_item"` `_prepare_examples` instead draws whole training items per judge and the per-criterion example dicts stay empty (*Item-level few-shot examples* in *One call per item (`llm_calls="per_item"`)* below). With `training_data`, `_prepare_examples` draws every criterion's examples once per LLM judge at construction, each draw from `_derive_shuffle_rng(few_shot_seed, FEW_SHOT_DOMAIN, criterion_idx, judge_id)` ([Reproducibility & Seed Coordination](reproducibility.md)). Binary criteria: `_select_examples_for_criterion` groups the training items by verdict and, with `FewShotConfig.balance_verdicts` and more than one verdict present, picks across the groups (`_balanced_selection` → `_balanced_pick`), else takes the first `n_examples` of one shuffle; it returns `FewShotExample`s. Multi-choice criteria: `_select_multi_choice_examples` groups by option index (labels mapped by `_label_to_option_index`) and picks the same way, returning `(submission, selected_index, reason)` tuples, which each call re-indexes to its shuffled option order. On all four paths an example's reason is its item's `DataItem.ground_truth_reasons[criterion_idx]`, read by `_ground_truth_reason(item, criterion_idx)` (`None` when the item has no reasons); reading it draws no randomness, so reasons never change which items are drawn or in what order. `build_few_shot_user_prompt` / `build_multi_choice_few_shot_user_prompt` add `<reason>...</reason>` after an example's `<verdict>` / `<selected_label>` only when `include_reason=True` and the reason is non-empty (an example's judgment tags come from `_example_judgment_lines`, which `_format_few_shot_examples`, `_format_multi_choice_examples` and the whole-rubric `_format_rubric_examples` share, so the two modes' examples cannot drift apart): with `include_reason=False`, or with no reasons in the training data, every prompt (and so every response-cache key) is byte-identical to one built without reasons. Pinned through the prompts the grader sends by `tests/graders/test_few_shot_reasons.py`; the few-shot grader golden (`include_reason=True`, a pool without reasons) is unchanged.

**Prompt text: one source, byte-identical.** The binary verdict definitions are named constants in `prompts.py` — `MET_DEFINITION`, `UNMET_DEFINITION`, `CANNOT_ASSESS_DEFINITION`, and for negative criteria `NEGATIVE_MET_DEFINITION` / `NEGATIVE_UNMET_DEFINITION` — and `GRADER_SYSTEM_PROMPT_DEFAULT` is built from them (an f-string for the instructions, concatenated with a plain string for the brace-bearing response format and examples), so any other framing of a binary criterion reuses the exact LLM wording. Prompts must stay byte-identical when a feature is unused, because `LLMClient._cache_key` hashes both prompts (and providers cache prefixes). `tests/test_prompt_goldens.py` pins this against goldens captured from the pre-refactor library in `tests/golden/prompts/`: every prompt constant, every user-prompt builder over representative inputs (binary ±weight, ordinal/nominal with NA, few-shot, reference, thinking/output, query present/absent), and the exact calls a fixed-seed `CriterionGrader` sends (single judge, ensemble, few-shot, forced-choice unshuffled — which also pins shuffling and few-shot selection). Run the module as a script with `--write` to regenerate deliberately. The four user-prompt builders now pose their criterion through `_binary_criterion_block` / `_multi_choice_criterion_block`, the blocks the whole-rubric user prompt shares; these goldens, none of which changed, prove the builders byte-identical. The whole-rubric prompts of `llm_calls="per_item"` have goldens of their own, which leave this module and `tests/golden/prompts/` untouched (*One call per item (`llm_calls="per_item"`)* below). The same module pins rubric guidelines against those goldens, with no files of their own: with guidelines, every builder case and every captured grader call (graded through `Rubric.grade`) must be a literal `GUIDELINES_BLOCK` followed by the golden prompt, with the golden system prompt; with `guidelines=None` or blank text, exactly the golden. The decision-model framing text (next section) is separate constants — `DECISION_MODEL_TASK_INSTRUCTION`, `DECISION_MODEL_THINKING_OUTPUT_TASK_INSTRUCTION`, `DECISION_MODEL_GUIDELINES_INSTRUCTION`, `DECISION_MODEL_REFERENCE_INSTRUCTION`, `DECISION_MODEL_CRITERION_PREFIX` — that no LLM prompt uses, so adding them left every LLM prompt byte-identical; its binary outcomes reuse the verdict-definition constants above, so the two judge kinds cannot drift.

### Decision-Model Framing and Answer Mapping
A decision model (`DecisionModelConfig`, see [Type Catalog](types.md)) grades an item with **one request for the whole rubric**: a shared `state` plus one typed question per criterion of the *effective rubric*. The pure, synchronous helpers in `decision.py` build the request and map the response; `CriterionGrader` sends it (next section).

- **State (`build_state(to_grade, *, query=None, reference_submission=None, guidelines=None)`).** Field names mirror the LLM user prompt's XML tags; optional fields appear only when present — non-empty, the rule `build_user_prompt` applies; for `guidelines`, not blank (`_normalize_guidelines`) — in the order `guidelines`, `input`, `reference_submission`, then `submission`. The guidelines go verbatim, once per request whatever the criterion count (billed once), and, being state, into the response cache key; a rubric without guidelines sends exactly the state it did before guidelines existed. When `to_grade` holds a `<thinking>`/`<output>` **section** (an opening marker followed by its closing marker, case-insensitive; `Grader.grade` flattens a `{"thinking", "output"}` dict into such sections), `thinking` and `output` from `parse_thinking_output` replace `submission`, both always (`thinking` possibly `""`). Detection is `_has_thinking_output_sections` in `utils.py`, which shares the compiled `_THINKING_SECTION`/`_OUTPUT_SECTION` patterns with `parse_thinking_output`, so "has a section" means exactly "`parse_thinking_output` recovers one"; plain text (stray or unclosed markers included) goes out unchanged as `submission`.
- **Questions (`build_questions(rubric, config, state) -> (questions, errors)`; single criterion: `build_question`).** One question per criterion of the effective rubric (NA options already guaranteed by `_effective_criterion`), id `question_id(criterion_idx)` = `"c{criterion_idx}"` — the index that also keys shuffling and few-shot selection, so ids are unique for unnamed or duplicate-named criteria. The question type is `_question_kind(criterion, config)`, the single source that `answer_to_report` checks answers against. Requirement and labels are **verbatim**; only structure differs:

| Criterion | Framing | Question |
| --- | --- | --- |
| binary | `binary_framing="noul"` | `Noul(instructions=requirement)` |
| binary | `"noul_framed"` (default) | `Noul(instructions=framed, criteria={"true": MET_DEFINITION, "false": UNMET_DEFINITION})` |
| binary | `"choice"` | `Choice(instructions=framed, criteria={"MET": MET_DEFINITION, "UNMET": UNMET_DEFINITION, "CANNOT_ASSESS": CANNOT_ASSESS_DEFINITION})` |
| multi-choice | nominal, or ordinal with `ordinal_framing="choice"` (default) | `Choice(instructions=requirement, criteria={label: None ...})`, NA option included |
| multi-choice | ordinal with `ordinal_framing="score"` | `Score(instructions=requirement, criteria=[non-NA labels, in order])` |

A negative weight selects `NEGATIVE_MET_DEFINITION`/`NEGATIVE_UNMET_DEFINITION` (the `"true"`/MET outcome is still "the thing is present"). The **framed** instructions (`_framed_instructions`) are a task sentence, then one context sentence per optional state field the judgment depends on, then `DECISION_MODEL_CRITERION_PREFIX` + the requirement, which always comes **last**, so no fixed text follows (and blurs into) a requirement that has no guaranteed terminal punctuation. With no optional field this is exactly the template the motivating experiments used: ``"Determine whether this criterion is satisfied by the `submission`. Criterion: {requirement}"``. Context sentences follow the state-field order: `guidelines` adds `DECISION_MODEL_GUIDELINES_INSTRUCTION` (``"Apply the `guidelines`; the criterion text governs."``, the precedence rule of `GUIDELINES_BLOCK`), then a `reference_submission` its sentence — e.g. ``"<task> Apply the `guidelines`; the criterion text governs. Use the `reference_submission` ... Criterion: {requirement}"``. A `thinking`/`output` state swaps in `DECISION_MODEL_THINKING_OUTPUT_TASK_INSTRUCTION` (``"...satisfied by the `output`; the `thinking` is context only."`` — approximating the LLM rule "evaluate only `<output>` unless the criterion is about reasoning"); a `reference_submission` adds `DECISION_MODEL_REFERENCE_INSTRUCTION` with `{judged}` = `submission` or `output` (the LLM judge's calibrate-don't-compare rule). Clauses apply **only to framed binary questions**: bare `noul` and multi-choice questions see extra fields only through the state. Only which state keys exist shapes a question, never their values; every backticked name in framed instructions is a state key (both pinned by tests). Question objects are the SDK's `Noul`/`Choice`/`Score`, built through `_import_typesafe_sdk()`.

- **Inexpressible criteria.** Questions are built before anything is sent. A criterion a question cannot express — repeated `Choice` labels (keys are labels; the message names them, e.g. an author label equal to the auto-injected `CANONICAL_NA_OPTION` label), more than 255 `Choice` options (`_MAX_CHOICE_OPTIONS`), or outside 2–10 non-NA `Score` levels (`_MIN_SCORE_LEVELS`/`_MAX_SCORE_LEVELS`) — is **left out of `questions`** and gets its own `ValueError` in `errors` (keyed by criterion index, message naming `c{idx}` and the criterion name); `classify_grading_error` routes it as `parse`. The rest still go out in the single request under their original ids; an empty `questions` means no request. These limits are the System One API's; the SDK itself only validates non-empty questions and Score criteria, which they subsume.
- **Answers (`answer_to_report(criterion, criterion_idx, answers, config) -> CriterionReport`).** Reads the answer under `question_id(criterion_idx)`:
  - **Noul** `p`: `p > decision_threshold` → MET, `p < t` → UNMET, **`p == t` → `_binary_worst_verdict(weight)`** (the ensemble tie rule: UNMET for weight ≥ 0, MET for < 0; now defined in `types.py` beside `CriterionVerdict` and imported by `criterion_grader`, so the two cannot drift). `probabilities = {"MET": p, "UNMET": 1 - p}`.
  - **Binary Choice**: `CriterionVerdict(choice)`; `CANNOT_ASSESS` is an abstention. Keys `"MET"`, `"UNMET"`, `"CANNOT_ASSESS"` in that order, whatever order the endpoint used.
  - **Multi-choice Choice**: the option whose label **equals** the choice (exact match); the NA option → `na=True`. Keys `str(i)` for every option, NA included.
  - **Score** `s`: level `round(s)` clamped to `[0, K−1]` (`_snapped_level`: `min(max(round(s), 0), K - 1)`), mapped to its original option index. `round` is Python's half-to-even with **no tolerance band** — 0.5 → 0, 1.5 → 2, 2.5 → 2, and 1.5000000001 → 2 — whatever the criterion's weight sign: this is not an ensemble tie, and the ensemble tie rule (`worst_option_among`) is deliberately not applied. Half-to-even rounds halves down as often as up, so it adds no systematic bias toward either end of the scale, where the worst case would always round down on a positive-weight ladder; it is also exactly how the recorded decision-model runs snapped (see *Fidelity* below). Keys `str(i)` for the non-NA options only (NA absent, not `0.0`). Never `na`.
  - The report copies the criterion's fields and sets `reason=None`, `reasoning=None` (no explanation, see [Key Conventions](conventions.md)), `shuffle_order=None`; a multi-choice `value` is always `options[selected_index].value`, never the fractional score. Probabilities are the endpoint's own (not renormalized; they sum to 1 only approximately when rounded).
  - `confidence = selection_confidence(p_selected, K)` = `clamp((K·p − 1)/(K − 1), 0, 1)` for the **selected** outcome, `K` = 2 (Noul), 3 (binary Choice), the option count incl. NA (multi-choice Choice), the non-NA level count (Score). For a Choice's most probable option it equals TypeSafe's reported confidence (within the two-decimal rounding of the reported probabilities); at `decision_threshold=0.5` a Noul's is `2·|p − 0.5|`; a snapped Score level or a Noul verdict under another threshold can fall to `0.0` ("no support for the verdict issued").
  - A missing answer id, an answer of the wrong type, a choice not offered, probabilities that do not cover exactly the offered outcomes or are not numbers in [0, 1], a non-finite `noul`/`score` → `ValueError` naming the criterion → `parse`, for that criterion only.
- **Fidelity to recorded decision-model runs.** `tests/decision/test_decision_recorded.py` pins the builders and the mapping against `tests/decision/fixtures/recorded_jev.json`, derived offline from recorded Jev runs of a reference grader: its questions for two rubrics (binary criteria, and ordinal criteria that carry their NA option) under all six framing combinations with a state of `input` + `submission`, and raw answers with the outcomes it recorded (pytest ids name the rubric, framing and criterion, e.g. `fed_turn-score-interesting-1`). **On those rubrics and that state** the grader differed from the library only at an exact Noul tie — `p == threshold` was MET — which the library resolves by the worst-case rule above; it snapped Score answers with Python's `round`, as the library does, so every recorded Score outcome is reproduced, halves included (the fixture holds halves that round down, 0.5, and up, 1.5). Beyond them its requests differed, so a re-run of such a run through the library would send different questions: under `ordinal_framing="score"` it posed a **nominal** criterion as a `Score` over the non-NA labels too (the library always poses a nominal criterion as a `Choice`, NA option included); it sent a criterion's options as given, where the library's effective rubric adds the NA option under `auto_na_option=True`; its framed instructions had no reference-submission sentence (the library adds `DECISION_MODEL_REFERENCE_INSTRUCTION` when the state has a `reference_submission`); it sent a structured submission flattened into `submission` (the library sends `thinking` + `output`, with `DECISION_MODEL_THINKING_OUTPUT_TASK_INSTRUCTION`); and it had no rubric guidelines (the library sends them as the first state field, with `DECISION_MODEL_GUIDELINES_INSTRUCTION` in framed instructions).

### Decision-Model Judges in `CriterionGrader`
A `DecisionModelConfig` is accepted wherever a judge config is — `CriterionGrader(judge_model_config=...)`, its deprecated alias `llm_config=`, and `JudgeSpec(...)` in `judges=` — alone or mixed with LLM judges in one ensemble (types: [Type Catalog](types.md)).

- **Clients.** Construction builds each judge's client into one of two maps keyed by `judge_id`: `_clients` (`LLMClient`, LLM judges only) and `_decision_clients` (`DecisionModelClient`). Building a `DecisionModelClient` imports the SDK and resolves and checks the API key, base URL and extra headers, so a missing SDK (`ImportError`), a missing key or one the SDK would reject, a resolved base URL (`api_base` or `TYPESAFE_BASE_URL`) no request could use (`_check_base_url`: whitespace, not absolute http(s), credentials, query or fragment, or a request URL the SDK's HTTP stack refuses, e.g. an invalid IDNA name), an `extra_headers` name or value the HTTP/1.1 layer refuses or a header the SDK sets itself (`_check_extra_headers`, `_SDK_OWNED_HEADERS`), or an environment in which `httpx2` cannot build an HTTP client (TLS or proxy settings such as a missing `SSL_CERT_FILE`) fails at construction with `ValueError`, never as a per-item abstention or worst case. An environment that breaks only after construction fails each request as `TypeSafeAPIConnectionError`, an `infrastructure` abstention, never the `unknown` worst case ([Key Conventions](conventions.md)).
- **One request per item (`_judge_all_criteria_with_decision_model`).** `build_state(to_grade, query=, reference_submission=, guidelines=)` once (the rubric's guidelines, from `judge(..., guidelines=)`, as the state's first field) — `to_grade` is the string `judge()` receives, which `Grader.grade` has already flattened from a `{"thinking", "output"}` dict into `<thinking>`/`<output>` sections, so such a submission goes out as `state["thinking"]` + `state["output"]` and a plain one unchanged as `state["submission"]` — then `build_questions(effective_rubric, client.config, state)` once, then **exactly one** `client.system_one(state, questions)`, carrying every expressible criterion under `c{criterion_idx}`; **none** when no criterion is expressible. Answers map back through `answer_to_report`, one `CriterionResult` per criterion, in rubric order. No `shuffle_options`, no system prompt, no few-shot examples, no response format reach the request.
- **Failure scope.** Each failed criterion gets its report from `_failed_judgment_result` (above), so routing is the LLM judge's: `infrastructure`/`parse` abstain (`CANNOT_ASSESS` / `na=True`, category-prefixed `error`), `unknown` → the conservative worst case.
  - An **inexpressible** criterion (its `build_questions` error) is left out of the request and fails alone as `parse` — with its own error even when the request itself fails.
  - A **failed request** (any exception from `system_one`, e.g. a `TypeSafeError` routed by `_classify_typesafe_error`, or an unknown exception) fails every criterion posed in it with the request's exception; criteria are **never re-sent one at a time**, and the SDK's own retries (`max_retries`) are the only retries. With no other judge answering on the item, every criterion is then `is_error` and the item has no score (`"Every criterion's judgment failed: ..."`, *Score Calculation* below), exactly as for an LLM grader whose every call failed; so does a request that was answered (and billed) with no usable answer for any criterion.
  - A **missing or unusable answer** (`answer_to_report` raises) fails only its criterion (`parse` for its `ValueError`; any other exception is `unknown`, as for an LLM judgment).
- **Billing.** The request's `token_usage(response)` and `completion_cost(response)` ride on the item's **first** `CriterionResult` (index 0, whatever its outcome); the rest carry `None`, so `JudgeCriterionResults.total_usage`/`total_cost` — and hence `aggregate`'s `token_usage`/`completion_cost` — are exact per-item totals. The state is billed once per request whatever the criterion count. With no `input_cost_per_token` the cost is unknown (`None`): `aggregate` adds nothing for it, as for an LLM whose price litellm does not know, so a report whose judges are all unpriced decision models has `completion_cost=None` (never a fabricated `0.0`); a mixed ensemble reports only the priced part. A cache hit reports the stored usage and the cost at the configured price.
- **Votes.** A decision model's `CriterionReport` carries `probabilities`/`confidence` and `reason=None`, which `aggregate` copies onto its `JudgeVote`/`MultiChoiceJudgeVote` like any field; `_join_vote_reasons` skips its `None` reason, so a decision-model-only criterion has `final_reason=None`. `judge_scores[judge_id]` is its own `score_reports` score: `None` on an item where its request failed (every vote failed, so it judged nothing), as for any judge every vote of which failed, or where none of its verdicts is left to score.
- **Mixed ensembles.** Decision-model and LLM `JudgeSpec`s mix freely in `judges=`: per item, each decision model makes one request and each LLM judge one call per criterion (`tests/decision/test_decision_ensemble.py` counts both over an `evaluate()` run), or one call for the whole rubric under `llm_calls="per_item"`, which leaves the decision model's request byte-identical to a default grader's (`TestMixedPanel` in `tests/graders/test_per_item_calls.py`). Downstream a decision-model vote is one more vote: it aggregates exactly as an LLM vote with the same verdict under every `aggregation` (`majority`/`weighted`/`unanimous`/`any`) and every `ordinal_aggregation`/`nominal_aggregation`; its abstentions (a Choice `CANNOT_ASSESS`, a multi-choice NA) are set aside by the same assessable-vote filters; `judge_scores` has an entry per judge; `agreement` and `mean_agreement` count every vote; and in the metrics layer the panel is an ordinary full panel (Fleiss' κ, Krippendorff's α, per-judge metrics). The test pins all of this by comparing each mixed panel with an all-LLM *mirror* panel whose LLM stands in for the decision model with the same verdicts: every aggregation outcome, score, `judge_scores`/`agreement` value and the whole `compute_metrics` result (bootstrap included) are equal; only `probabilities`/`confidence` (present on the decision model's votes) and `final_reason` (its `None` reason skipped) differ. A `judge_id` repeated in any panel, mixed or not, warns (`FutureWarning`, *Judge identity* under item 2 of *Grading Flow* above): across kinds each judge keeps its own client, but `judge_scores` and the per-judge metrics still conflate them; a cascade refuses repeats (*Confidence Cascade* below).
- **Settings checked at construction, before any client is built** (so a configuration error is reported as one, even where no client could be built):
  - **Few-shot examples are LLM-only.** `few_shot_config` or `training_data` when every judge is a decision model → `ValueError` ("few-shot examples apply to LLM judges only"). With at least one LLM judge, `_prepare_examples` selects examples for the LLM judges alone (each judge's selection is keyed on its own `judge_id`, so leaving decision models out changes no LLM judge's examples; per criterion, or whole training items under `llm_calls="per_item"`), and the decision-model request is byte-identical to one from a grader without few-shot.
  - **Response formats need a generative judge.** `binary_response_format` or `multi_choice_response_format` (any non-`None` value) with **any** decision-model judge → `ValueError` naming the decision-model `judge_id`s ("... cannot be combined with decision-model judges ('jev'): a response format describes a generated judgment, which only an LLM judge produces"). LLM-only graders accept them as before, except under `llm_calls="per_item"`, which refuses them after this check (so with a decision-model judge this message, unchanged, wins; *One call per item (`llm_calls="per_item"`)* below). Meta-rubric evaluation, which passes `MetaCriterionJudgment`/`MultiChoiceMetaJudgment`, rejects a decision model itself, earlier and with its own message ([Key Conventions](conventions.md)).
  - **LLM-only prompt settings.** `system_prompt`, `multi_choice_system_prompt` and `shuffle_options` shape LLM prompts only, and `llm_calls` how LLM judges are called; a decision model's request has no system prompt and keeps the rubric's option order, and is one per item whatever `llm_calls` says. In a mixed ensemble the LLM judges use them unchanged, and the decision-model request is identical with and without them. When **every** judge is a decision model, each setting that **differs from its default** issues one `UserWarning` ("<name> applies to LLM judges only; this grader has none (every judge is a decision model), so it has no effect", attributed to the caller's line with `stacklevel=2`), in the order `system_prompt`, `multi_choice_system_prompt`, `shuffle_options`, `llm_calls`; a grader with any LLM judge — a mixed ensemble, or a cascade, whose escalation judges are LLMs — never warns. "Differs from its default" means a non-`None` `system_prompt`/`multi_choice_system_prompt` (`None` means no prompt), `shuffle_options=False`, or `llm_calls="per_item"` (`tests/decision/test_decision_settings.py`: `DEFAULT_SETTINGS`/`CHANGED_SETTINGS`). `shuffle_options=True`, passed or not, never warns: it is the default and what a decision model does anyway (its question keeps the rubric's order), so the rule needs no record of which arguments were passed and `CriterionGrader.__init__` is a plain method (`inspect.signature`, `inspect.getfullargspec`, `__kwdefaults__` all read its own keyword-only parameters and plain `True` default). `_shuffle_options` (`is True` by default) and the manifest's `shuffle_options` are exactly as before.

### One call per item (`llm_calls="per_item"`)
`CriterionGrader(..., llm_calls="per_item")` makes every LLM judge of the grader — the `judge_model_config` judge, each LLM `JudgeSpec` of `judges`, and a cascade's escalation judges — grade an item's whole effective rubric in **one call** instead of one call per criterion, with a decision model's unit of work (one request per item, the submission, input, reference submission and guidelines sent once), id scheme (`c{idx}`), failure scoping and billing convention, while reading exactly the guidance and criterion text a per-criterion judge reads. Decision-model judges are unaffected. `LLMCalls = Literal["per_criterion", "per_item"]` (`types.py`, exported next to `AggregationStrategy`; [Type Catalog](types.md)); the name counts LLM calls per item and is unrelated to `compute_metrics(per_item_metrics=...)` and to per-item rubrics. The default `"per_criterion"` is the code path, prompts, requests, response-cache keys, manifests and reports as before (`test_explicit_per_criterion_equals_the_default`); votes, aggregation, scoring, metrics, checkpoints and the cascade carrier are shared by both modes. Tests: `tests/graders/test_per_item_calls.py` unless noted.

- **Parameter and validation.** Keyword-only, between `escalation` and the deprecated `llm_config` (which stays last); stored as `self._llm_calls` before the clients are built, with the class-level default `_llm_calls = "per_criterion"` beside `_escalation`, so a grader whose `__init__` never ran (a subclass that skips it, one unpickled from an earlier version) grades per criterion (`TestPerCriterionUnchanged`). Checked at construction, before any client is built, after the cascade checks and the repeated-`judge_id` warning: first `_check_llm_calls(llm_calls)` — the one check, shared with `replay_escalation` and `calibrate_escalation` — refuses a value outside `LLMCalls` (`typing.get_args`, the wording `DecisionModelConfig` uses for its literals: `ValueError("llm_calls must be one of ('per_criterion', 'per_item'); got 'x'")`); then the few-shot and decision-model response-format refusals, unchanged; then `per_item` with `binary_response_format` and/or `multi_choice_response_format` → `ValueError("<names> cannot be combined with llm_calls='per_item': a response format describes one criterion's judgment, and a per_item call answers every criterion at once")` (a `per_item` call is always answered as `RubricJudgment`); then, for an all-decision-model grader, the LLM-only-settings `UserWarning` for `llm_calls`, fourth and last (*Decision-Model Judges in `CriterionGrader`* above). No combination is refused otherwise: a cascade and training data work under `per_item`. The manifest records `"llm_calls": "per_item"` only under `per_item` ([Reproducibility & Seed Coordination](reproducibility.md); `TestManifest`).
- **The call (`_judge_rubric_in_one_call(judge, rubric, to_grade, query, reference_submission, *, guidelines)` → `(results, usage, cost)`).** The LLM counterpart of `_judge_all_criteria_with_decision_model`. An empty rubric makes **no call** and returns `([], None, None)` (the item has no score, as any item graded against an empty rubric; *Score Calculation* below). Otherwise it presents every criterion under its id, renders the judge's examples (*Item-level few-shot examples* below) and builds both prompts **before** the call, outside its failure handling, so a configuration or rendering error raises instead of failing the criteria (`test_an_error_rendering_the_examples_raises_before_the_call` in `tests/graders/test_per_item_few_shot.py`); then exactly one `client.generate(system_prompt=, user_prompt=, response_format=RubricJudgment, return_result=True)`. It maps the reply to one `CriterionResult` per criterion of the effective rubric, in order, none carrying usage or cost; the call's usage and cost are returned separately (`None` when no call was made or it failed). A criterion is never re-sent in a call of its own; `generate`'s retries are the only retries.
- **System prompt (`_rubric_system_prompt(rubric, *, with_examples)`, `with_examples` required so a call showing examples cannot leave out how to read them → `build_rubric_system_prompt(binary_guide, multi_choice_guide, *, with_examples=False)`).** The grader's two per-criterion system prompts as they stand (`_system_prompt`, `_multi_choice_system_prompt`: the default, the default with its few-shot addition when there is training data, or a custom one) are embedded **verbatim** as guides, each only when the rubric has a criterion of its kind (`is_binary`/`is_multi_choice`; `None` otherwise; both `None` → `ValueError`), so a binary-only rubric's call never carries the multi-choice guide, as a per-criterion binary call never does. Blocks one blank line apart: `RUBRIC_JUDGMENT_PREAMBLE` — the role sentence; each criterion is a `<rubric_criterion>` with an id (c0, c1, ...), with a `RUBRIC_JUDGMENT_BINARY_KIND` / `RUBRIC_JUDGMENT_MULTI_CHOICE_KIND` line for each kind present; the independence paragraph (each guide is written for one criterion at a time: apply it to each criterion of its kind separately, as if that criterion were the only one, never letting one judgment influence another; `<submission>` and any `<guidelines>`, `<input>`, `<reference_submission>` apply to every criterion); `RUBRIC_JUDGMENT_EXAMPLES` after it when `with_examples`; and "A guide's RESPONSE FORMAT and EXAMPLES show the fields of one criterion's judgment ..." — then the guides, binary first, wrapped by `RUBRIC_JUDGMENT_BINARY_GUIDE` (`<binary_criterion_guide>`) and `RUBRIC_JUDGMENT_MULTI_CHOICE_GUIDE` (`<multi_choice_criterion_guide>`), then `RUBRIC_JUDGMENT_RESPONSE_FORMAT` **last**: each guide ends with its own one-object format and "Return only raw JSON starting with {", and where decoding is not constrained by the schema the last instruction tends to win. The format's one-line JSON skeleton (`json.dumps` of `_RUBRIC_JUDGMENT_BINARY_SKELETON` / `_RUBRIC_JUDGMENT_MULTI_CHOICE_SKELETON` for the kinds present, ids `c0`, `c1` in that order) and its rules (`RUBRIC_JUDGMENT_BINARY_RULE` / `RUBRIC_JUDGMENT_MULTI_CHOICE_RULE`) also cover only the kinds present. No existing prompt constant changed and custom system prompts keep working; the system prompt is the same for every item graded against one rubric, so provider prompt caching applies.
- **User prompt (`build_rubric_user_prompt(criteria, to_grade, query=None, reference_submission=None, *, examples_text="", guidelines=None)`).** `GUIDELINES_BLOCK` first when there are guidelines (`_guidelines_block`, as in every LLM user prompt), then `<criteria>` holding a `<rubric_criterion id="c{idx}">` per criterion in rubric order (one blank line apart; criteria are never shuffled), each holding exactly the block a per-criterion prompt poses its criterion with: `_binary_criterion_block` (`<criterion_type>` — `negative` for a negative weight, else `positive`, zero included — and `<criterion>`) or `_multi_choice_criterion_block` (`<question>` and `<options>` numbered by `_render_options` with its NA marking; `ValueError` for a criterion without options), the helpers the four per-criterion builders now call. Then the examples block (when `examples_text` is non-empty), `<input>`, `<reference_submission>` and `<submission>`, in a per-criterion prompt's order and wording. Empty `criteria` → `ValueError`. Criterion names and weights stay out of the prompt. `criteria` pairs each id with the criterion as the judge is shown it: `prompts.py` cannot import `question_id`, since `decision.py` imports `prompts.py`. A structured `{"thinking", "output"}` submission arrives flattened to tagged sections by `Grader.grade`, once, and the guides' thinking/output rule applies to each criterion.
- **Ids and option shuffles.** Each id is `question_id(criterion_idx)` on the effective rubric, the decision model's question id, unique and stable for unnamed or duplicate-named criteria. `_presented_criterion(criterion, criterion_idx, judge_id, to_grade) -> (criterion as shown, shuffled_indices)`, shared with `_judge_multi_choice_criterion`, permutes a multi-choice criterion's options by `_derive_shuffle_rng(seed, item_key, criterion_idx, judge_id)` (`item_key` = the first 16 hex digits of the submission's SHA-256, hashed only when `shuffle_options` is on; the identity and the criterion unchanged otherwise), so a criterion's option order is the same in both modes (`test_each_criterion_is_posed_as_a_per_criterion_call_poses_it`, `TestTheShuffleKey`). `shuffle_order` is recorded when `shuffle_options` is on, on a multi-choice criterion's failure reports too.
- **Response models (`RubricJudgment`, `RubricCriterionJudgment`; `types.py`, after `MultiChoiceJudgment`, not exported; fields: [Type Catalog](types.md)).** Frozen. `RubricJudgment` holds `judgments: list[RubricCriterionJudgment]`, `reasoning: str | None` and the private `_unusable: list[tuple[str, str]]` (`(criterion_id, error)`); an entry holds `criterion_id`, `criterion_status: CriterionVerdict | None`, `selected_option: int | None` (1-indexed in the call's option order) and `explanation`, verdict fields before `explanation` as in `CriterionJudgment`/`MultiChoiceJudgment`. The two verdict fields default to `None`, so an entry may leave the other kind's field out where decoding is unconstrained; one entry type serves both kinds, and one list keeps the answers in order. Their docstrings and field descriptions go to the provider in the schema, so they are written for the judge (the notes for readers are comments). **Static, not built per rubric:** `LLMClient.generate` pickles its result, parsed model included, into the response cache, and an instance of a `pydantic.create_model` class does not pickle (`PicklingError` → `unknown` → every criterion's worst case); the cache key names the format by `__name__`, so a static class gives one stable name distinct from the per-criterion formats, and a `per_item` key never matches a per-criterion call's. **`reasoning` at the top level only:** `_provider_response_format` strips `reasoning` from the top level of the provider schema and `generate` injects the trace only there (*Provider schema vs parsing schema* above); a per-entry `reasoning` would stay in the strict schema and be required — the Groq Llama/Qwen failure the strip exists to prevent. The provider schema (a strict `json_schema` named `RubricJudgment` whose top level requires only `judgments`, `additionalProperties: false`, the entry under `$defs` with every field required and live `$ref`s in `judgments.items` and in `criterion_status`'s `anyOf`) is pinned by `TestRubricJudgmentResponseFormat` in `tests/llm/test_llm_client.py`, which also checks that a transport-level trace lands on the top-level `reasoning`. **`_keep_usable_entries`** (a `mode="wrap"` model validator) makes one unusable entry fail only its criterion instead of the whole reply: when the data is an object whose `judgments` is a list, each entry is validated alone (`RubricCriterionJudgment.model_validate`); valid entries are kept in order; an invalid entry whose `criterion_id` is a `str` is recorded in `_unusable` with `_validation_message(exc)` (`"loc: msg"` per error, joined with `"; "`; just the message for an empty `loc`); one without a readable id is dropped, and its criterion counts as unanswered. Anything else — a reply that is not an object, or whose `judgments` is missing or not a list — goes to the handler unchanged and fails validation as a whole, and an instance validates as it is, `_unusable` included. `_unusable` is set after construction (`frozen` covers fields only) and pickles with the instance, so a cached reply maps exactly as the original did (`TestEndToEnd`: a rerun makes no call and gives an identical report).
- **Mapping (`_rubric_judgment_report(criterion, criterion_idx, answers, reply, shuffled_indices)`).** The reply's entries are indexed by `criterion_id`, usable entries and unusable ones (their messages) alike; entries whose id is no criterion's of the call are ignored, and so is a usable entry's field of the other kind. For each criterion, named by `_describe(criterion, criterion_idx)` (`criterion c3 ('name')`, or `criterion c3` when unnamed, as decision-model messages name it), each outcome below raises `ValueError` → `parse`, for that criterion alone:

| Answers with the criterion's id | Error |
| --- | --- |
| none | `no usable judgment for {describe}: the reply has no judgment with its id` |
| one, unusable | `no usable judgment for {describe}: {message}` (the entry's condensed validation error) |
| two or more, usable or not | `no usable judgment for {describe}: the reply has {n} judgments with its id` |
| one binary, `criterion_status` null | `no usable judgment for {describe}: a binary criterion needs a criterion_status, got null` |
| one multi-choice, `selected_option` null | `no usable judgment for {describe}: a multi-choice criterion needs a selected_option, got null` |
| one multi-choice, option out of range | `Selected option {n} out of range [1, {N}]`, the per-criterion text, from `_multi_choice_report` |

- **Mapped answers.** Otherwise a binary criterion's report is `_binary_report(criterion, entry.criterion_status, _require_llm_reason(_inject_affected_criteria(entry.explanation, entry)), reply.reasoning)`, and a multi-choice criterion's `_multi_choice_report(criterion, entry.selected_option, entry, reply, shuffled_indices)`: range check, mapping back through the permutation to the original option (`selected_index`, `selected_label`, `value`, `na`), the entry's tagged and checked `explanation`, and the reply's trace last — the per-criterion read order these shared helpers preserve (*Grading Flow* item 5 above).
- **Failure scope.** Every failure report comes from `_failed_judgment_result`, routed by `classify_grading_error` (`infrastructure`/`parse` abstain, `unknown` → the worst case; [Abstention Handling](abstention.md)).
  - A **failed call** — any exception from `generate`: an API or network error, a timeout or a rate limit after retries (`infrastructure`); a reply that is not JSON (e.g. cut off at `max_tokens`) or not a `RubricJudgment` (not an object, `judgments` missing or not a list: its `ValidationError`) (`parse`) — fails **every** criterion of the call with that exception, each multi-choice criterion with its `shuffle_order`. With no other judge answering, the item has no score and `error` `"Every criterion's judgment failed: ..."` (*Score Calculation* below), so `EvalRunner` fails the item and `fill_ground_truth` leaves it out; per criterion the same takes every call failing. In a panel the other judges still grade the item (the failed judge's `judge_scores` entry is `None`). A reply that does not parse is lost with its usage and never cached, so a rerun calls again.
  - Two **pre-existing** behaviours of `LLMClient.generate`, unchanged here and shared with per-criterion calls, route as `unknown` (the worst case): a reply with no content (`content=None`) raises `TypeError` in `json.loads`; and with thinking on, a JSON reply that is not an object (an array, string, number or `null`) raises `TypeError` when the trace is injected, where without thinking it fails validation as `parse` (`TestNonObjectReplies` in `tests/llm/test_llm_client.py`). Under `per_item` one such reply hits every criterion of the item.
  - A **criterion failing alone** (the table above) inside a call that succeeded; the other criteria are judged. The reply parsed, so it is cached, `_unusable` included, and a rerun reproduces the same per-criterion failures.
- **Usage and cost.** The `per_item` branch of `_judge_all_criteria_for_judge` puts the call's usage and cost on `results[0]` (`dataclasses.replace`), even when that criterion failed alone in a call that succeeded; the other results carry `None`, so `JudgeCriterionResults.total_usage`/`total_cost` and `aggregate`'s `token_usage`/`completion_cost` are the per-item totals, the decision model's convention (*Billing* above). A failed call carries none. In a cascade the call's usage and cost ride on the first **escalated** result (*Confidence Cascade* below).
- **Extended thinking.** A call returns one trace, which `generate` injects into `RubricJudgment.reasoning`; every criterion judged from a usable judgment copies it into its report's `reasoning`, and so onto its vote: a vote's `reasoning` is still the deliberation behind its verdict, here the whole call's. A checkpoint therefore stores it once per criterion. A criterion that fails alone gets `_failed_judgment_result`'s report, **without** the trace, as a failed per-criterion call's report has none, and so does every criterion of a failed call (`test_the_thinking_trace_is_on_every_report_and_vote`, `test_a_criterion_that_fails_alone_has_no_trace`).
- **Operational limits.** One reply generates every criterion's judgment, one after another, so `max_tokens` and `timeout` must allow for the whole rubric's answer (and any thinking budget): a reply cut off at `max_tokens` fails every criterion as `parse`, and a timeout is retried and then fails the call as `infrastructure`. Per-item wall-clock time can rise even as requests fall N-fold; `max_parallel_requests` still bounds concurrent calls per provider.
- **Item-level few-shot examples.** With `training_data`, a call shows whole training items, each once with its label for every criterion, instead of examples drawn per criterion (which would put N × k example submissions in one call). `_prepare_examples` (which needs the training data's global rubric, as per criterion: `num_criteria` raises without one) takes its `per_item` branch: for every LLM judge, escalation judges included (decision models get none), `self._item_examples[judge_id]` holds the items `_select_item_examples(judge_id)` picks, in the order the call shows them, each taken at construction as `(submission, labels, reasons)` — its `_item_labels` and its `_ground_truth_reason` for each criterion — so the examples are a fixed property of the judge, as per-criterion examples are, and a later change to a training item changes no prompt (`test_changing_the_training_items_afterwards_changes_no_prompt`); the per-criterion `_criterion_examples`/`_multi_choice_examples` stay empty. It needs no class-level default: only `per_item` graders read it.
  - **Eligibility (`_item_labels(item)`).** An item with `ground_truth` whose every label is usable for its criterion's kind, the kind taken from the training rubric (`training_data.rubric.rubric[idx]`; an index it lacks counts as binary): a binary label must be a `CriterionVerdict` or its value (`CriterionVerdict(label)`, e.g. `"MET"`, as `resolve_ground_truth` reads it; `"met"` is none); a multi-choice label a `str` that `find_option_by_label` resolves, or an `int` (not a `bool`) in `[0, len(options))`, kept as the 0-based option index — both among the options of `_effective_criterion(training criterion)`, the options the judge is shown, so under `auto_na_option` the label of the NA option the grader adds (`CANONICAL_NA_OPTION`, the label `fill_ground_truth` records when a judge chose it) and its index resolve too, and not without it. Anything else → `None`: not eligible. (Per criterion, `_select_multi_choice_examples` resolves labels against the training rubric's own criterion through `_label_to_option_index`, unchanged, so such a label drops only that criterion's example there.)
  - **Order.** The eligible items, in dataset order, shuffled by `_derive_shuffle_rng(few_shot_seed, FEW_SHOT_DOMAIN, -1, judge_id)`: `-1` fills the criterion slot for the whole rubric and is no criterion's index, and each judge draws its own ([Reproducibility & Seed Coordination](reproducibility.md)). Reasons never affect the draw.
  - **`balance_verdicts=False`**: the first `n_examples` items of that order (no submission dedup, as per criterion). **`balance_verdicts=True`** (the default): greedy label coverage over `(criterion_idx, label)` pairs. Repeatedly pick, among the items whose submission was not picked yet, the one adding the most pairs no picked item shows, the earliest in the seeded order on a tie; once the best gain is 0, fill the remaining slots with the other items in seeded order, still skipping picked submissions; stop at `n_examples`. No submission is shown twice. Balancing each criterion's labels is impossible when k shared items carry every criterion's label; coverage gives each criterion as many of its labels as k items allow (e.g. an `UNMET` example for a mostly-`MET` criterion), deterministically, at the price of less decorrelated examples across judges. `FewShotConfig`'s docstring states both `per_item` meanings (`n_examples` per call, `balance_verdicts` as coverage). Tests: `TestGreedyCoverage`, `TestCoverageIdentifiesOptionsByIndex`, `TestEligibility`, `TestSelectionIsSeededPerJudge`.
  - **Per call (`_rubric_examples(judge_id, rubric, presented, shuffles)`).** For each of the judge's examples, a judgment for each criterion index both the training rubric and the graded effective rubric have, with a criterion of the same kind and, for multi-choice, an option index the graded criterion has, renumbered to its position in this call's permutation (`shuffled_indices.index(label)`), with the example's reason for that criterion. An example with no judgment is left out. As per criterion, this assumes the graded rubric is the training data's (`TestGradedRubricDiffersFromTraining`). The same items are shown for every graded item; only the option numbering follows each call's shuffle.
  - **Rendering (`_format_rubric_examples(examples, include_reason)`, `prompts.py`).** `<examples>`, then per example `<example_N>`, `<example_submission>...</example_submission>` and a `<judgment id="c{idx}">` per judgment holding the per-criterion example tags, rendered by the helper the per-criterion formatters use, `_example_judgment_lines(label, options, reason, include_reason)` — `<verdict>` for binary; the 1-based `<selected_option>` and its `<selected_label>` for multi-choice — then `<reason>` only when `include_reason` and the reason is non-empty (`test_a_judgment_is_rendered_as_a_per_criterion_example_renders_it`); `""` without examples; `ValueError` (`"option index {n} given for a criterion without options"`) for an option index given for a criterion without options. The block goes to `build_rubric_user_prompt` as `examples_text`, between `</criteria>` and the input, where a per-criterion prompt has its examples.
  - **System prompt.** With an examples block the system prompt is built `with_examples=True`, adding `RUBRIC_JUDGMENT_EXAMPLES` ("The <examples> show earlier submissions with the correct judgment of each criterion, each under the criterion's id; use them as the guides describe.") after the independence paragraph. With none left (no eligible item, or no judgment to show), the call has no examples block and no such sentence, while the guides keep their few-shot additions (`FEW_SHOT_SYSTEM_PROMPT_ADDITION`, `MULTI_CHOICE_FEW_SHOT_ADDITION`), which come with the training data, as in a per-criterion call without examples.
  - Each call carries k example submissions, where a judge called per criterion sends k with each criterion, N × k per item (`TestCost`). A cascade's escalation judge draws the examples a non-cascade grader with its `judge_id` draws, so its prompt, and the replay, stay exact (`TestCascade`). Tests: `tests/graders/test_per_item_few_shot.py`.
- **Goldens.** `tests/test_per_item_prompt_goldens.py` pins the whole-rubric prompts against `tests/golden/prompts_per_item/`, independently of `tests/test_prompt_goldens.py`, whose goldens and `_RecordingClient` (which accepts only the two per-criterion formats) it leaves untouched: `constants/<NAME>.txt` for every `RUBRIC_JUDGMENT_*` constant (the explicit `PROMPT_CONSTANT_NAMES`); `builders/<case>.txt` for `build_rubric_system_prompt` (binary-only, multi-choice-only and mixed rubrics, with and without `with_examples`, custom guides), `build_rubric_user_prompt` (the three rubric shapes, forced choice, query and reference, an opaque and a rendered `examples_text`, negative and zero weights) and `_format_rubric_examples` (binary-only, shuffled multi-choice, mixed, with and without `include_reason`, a missing reason); and `grader_calls.json`, the (system prompt, user prompt, response format) triples a fixed-seed `CriterionGrader(llm_calls="per_item")` sends for a single judge and a two-judge panel over a mixed rubric, without and with item-level training data. With guidelines, every user-prompt case must be the literal guidelines block followed by its golden. Literal-text tests (`test_spec_*`) write the reviewed prompt text out by hand instead of reading the constants or goldens, so they check the text where the goldens check only that it is stable; a deliberate prompt change updates them together with the goldens. Regenerate deliberately by running the module as a script with `--write`.

### Confidence Cascade
`CriterionGrader(judge_model_config=DecisionModelConfig(...), escalation=EscalationConfig(judges, threshold, per_criterion=None))` puts one decision model first and LLM judges behind it (`EscalationConfig` fields and validation: [Type Catalog](types.md)). The decision model judges every criterion in its one request per item (unchanged); only the criteria it is unsure of reach the LLMs, and a cascade has exactly one shape (no multi-stage or reverse cascades, no soft fusion of probabilities with LLM votes).

- **Construction.** The primary must be exactly one decision-model judge, `judge_model_config=DecisionModelConfig(...)` or `judges=[JudgeSpec(DecisionModelConfig(...), ...)]`, else `ValueError` ("escalation needs exactly one primary judge, a decision model ..., got 'default' (an LLM)"). The grader keeps its **own validated copy** of the config, `_escalation = dataclasses.replace(escalation)`, which runs `EscalationConfig.__init__` again (non-empty `JudgeSpec`s of LLMs, thresholds in [0, 1]): the config's frozen fields still hold a `judges` list and a `per_criterion` dict that can change in place, so a config emptied, given a decision-model judge or an out-of-range threshold since it was built is refused with that `ValueError`, and a change made after the grader is built never reaches it — `_escalation_judges`, `threshold_for`, the unknown-name check and the manifest all read the one copy, so the manifest describes the judges and thresholds the grader uses. `judge_id`s must be unique across the decision model and the escalation judges (`ValueError` naming the repeats via `_repeated_judge_ids`, which the panel warning shares; a bare `LLMConfig` escalation judge is `"escalation"`, the `judge_model_config=` judge `"default"`). Escalation judges live in `_escalation_judges` (a property: the copy's `judges`, `[]` without a cascade), **not** `_judges`, so `judge()`'s per-judge fan-out never runs them on every criterion. Every other per-judge concern covers both lists: the client map (`_clients`), `_prepare_examples` (an escalation judge gets the examples it would get without the cascade, per criterion or, under `llm_calls="per_item"`, as whole training items), the LLM-only settings (the "every judge is a decision model" test counts escalation judges, so a cascade accepts `few_shot_config`/`training_data` and `llm_calls="per_item"`, and never warns about `system_prompt`/`multi_choice_system_prompt`/`shuffle_options`/`llm_calls`), `_serialize_grader_config` (the `escalation` manifest key, [Reproducibility & Seed Coordination](reproducibility.md)), and the `judge_ids` property (`_judges` then `_escalation_judges`), which `EvalRunner` uses for its detailed progress (behind the `hasattr(grader, "_judges")` gate: a `CriterionGrader`'s `judge_ids`, any other grader's `_judges`, and none for a grader without `_judges`). The cascade state has class-level defaults (`_escalation = None`, `_escalation_names_warned = False`), so a `CriterionGrader` whose `__init__` never ran — a test double that skips `super().__init__()`, or a grader unpickled from a version without the cascade — grades and runs through `evaluate()` with no cascade (its manifest has no `escalation` key). The response-format `ValueError` still applies (the primary is a decision model). `is_ensemble` stays `len(_judges) > 1`: a cascade is not an ensemble.
- **Escalated set (`judge()`).** Once the decision model has judged the effective rubric, criterion *i* is escalated iff `_escalates(report, escalation.threshold_for(criterion))`: `report.is_error` (any category: a whole-request failure escalates every criterion, an inexpressible criterion or an unusable answer escalates that one), `report.is_na` (`CANNOT_ASSESS`, which only `binary_framing="choice"` can return, or a multi-choice NA option; an abstention escalates however confident), or `confidence is None or confidence < threshold` (strict: a confidence equal to the threshold stands). `EscalationConfig.threshold_for(criterion)` looks `per_criterion` up by criterion **name**; unnamed criteria, and names without an override, use `threshold`.
- **Escalation calls (`_judge_escalated_criteria`).** An escalation judge is called as the grader's `llm_calls` says, exactly as it would be in a grader without the cascade; this bullet describes the default, per criterion, and the next the `per_item` branch. Each escalation judge runs `_judge_single_criterion` on the escalated criteria only — every judge and criterion concurrently — each under its **original** `criterion_idx` in the effective rubric, the index that keys `_derive_shuffle_rng` and few-shot selection. An escalation judge's prompt for criterion *i* therefore equals the prompt a non-cascade `CriterionGrader(judges=[JudgeSpec(llm, "escalation")], seed=S)` sends for criterion *i* (same `seed`, same `judge_id`), its query, reference submission, shuffled multi-choice options and few-shot examples included (`tests/decision/test_decision_cascade.py` compares the captured prompts). Nothing escalated → no escalation call; exactly one decision-model request per item however many criteria escalate. Guidelines reach escalation prompts like any LLM prompt.
- **Escalation calls under `llm_calls="per_item"`.** For an item with any escalated criterion, each escalation judge makes **one** full-rubric `_judge_rubric_in_one_call` — every criterion of the effective rubric, in rubric order, under the same ids, option permutations and item-level few-shot examples (drawn for its `judge_id`) — the call a non-cascade `CriterionGrader(judges=[JudgeSpec(llm, "escalation")], seed=S, llm_calls="per_item")` makes for the item, so its prompts are equal (`test_the_escalated_results_are_the_non_cascade_calls` in `tests/escalation/test_per_item_cascade.py`; `TestCascade` in `tests/graders/test_per_item_few_shot.py`). It keeps the results at the escalated indices only (`None` elsewhere, `role="escalation"`), discarding its judgments of the other criteria, and puts the call's usage and cost on the **first escalated** result (`dataclasses.replace`, whatever that criterion's outcome). Nothing escalated → no call. A failed call therefore fails only the escalated criteria's votes (`TestFailures`), and an answer failing alone fails a vote only where its criterion escalated. **Why the full rubric:** under `per_item` a judge's verdict on a criterion is what its full-rubric call answers, so an escalated criterion gets the verdict the judge gives without the cascade, and a `per_item` LLM run holds exactly the verdicts the live cascade's calls produce, which keeps `replay_escalation` exact; a call over the escalated criteria alone would be another judge, whose prompt depended on what the decision model was unsure of. The cost: the call answers every criterion even when one escalated, so it pays less than per-criterion escalation when several criteria of an item escalate or the submission is long, and more when one does. Each escalation judge makes at most one call per item (`TestCalls`).
- **Carrier.** `JudgeCriterionResults.criterion_results: list[CriterionResult | None]` is always full-length, and `role: Literal["primary", "escalation"] = "primary"` marks the judge's part. `judge()` returns `[primary, *escalation_results]`; an escalation judge's carrier holds `None` wherever it did not judge (all `None` when nothing escalated, so its `judge_scores` entry exists on every item). `reports` / `total_usage` / `total_cost` skip `None` cells. Private types: nothing public changes.
- **Aggregation.** `aggregate` reads the escalated set off the carriers (the indices where an `"escalation"`-role judge has a result — no second field that could disagree), collects each criterion's votes from the non-`None` cells in judge order, and marks the primary's vote `superseded=True` exactly on escalated criteria. The final verdict aggregates **only the non-superseded votes** with the grader's `aggregation` / `ordinal_aggregation` / `nominal_aggregation` (and the escalation `JudgeSpec` weights), and `final_reason` (`_join_vote_reasons`) and `error` (`_aggregate_error`) are computed over the same votes: an escalated criterion's reason is the LLM explanations, and a decision-model failure stays on its superseded vote. The report has `escalated=True` and votes `[decision model (superseded), *escalation judges]` in `votes` (binary) or `multi_choice_votes` (multi-choice). A criterion not escalated keeps the decision model's vote as its only vote (`final_reason=None`, `agreement=1.0`). The `agreement` validator counts only non-superseded votes. Without a cascade nothing is superseded and every value is exactly as before.
- **Escalation-judge failures** route exactly as any LLM judge's (`_failed_judgment_result`): `infrastructure`/`parse` abstain, `unknown` gives the worst case (`_binary_worst_verdict` / `worst_scored_option`), aggregated like any vote. When every escalation vote abstained, the criterion abstains (`CANNOT_ASSESS` / `na=True`, counted in `cannot_assess_count`, scored under the configured `CannotAssessStrategy`) with `error` from `_aggregate_error` over the non-superseded votes: set when every one of them failed, `None` when the judges genuinely answered `CANNOT_ASSESS` / the NA option (a judgment, not a failure). **Never a fallback to the decision model's vote**: it was judged insufficient, and the failure stays visible in `error`. When every criterion escalated and every escalation vote on each failed, every criterion report `is_error` and the item has no score (`"Every criterion's judgment failed: ..."`, *Score Calculation* below), whether the decision model's request failed (which escalates every criterion; `test_an_item_whose_every_judgment_failed_keeps_its_pairs_and_replays` in `tests/escalation/test_escalation_stats.py`) or it judged every criterion with too little confidence (`test_a_billed_item_counts_in_the_cost_when_every_judgment_failed`, same file); in the latter case its own `judge_scores` entry keeps its score, since not every one of its votes failed. When the escalation judges answered what a failed request escalated, the item is judged (`error` `None`, scored from their verdicts; `test_a_decision_model_whose_request_failed_has_no_score` in `tests/decision/test_decision_cascade.py`).
- **`judge_scores`.** A primary judge's entry is `score_reports` over its own verdicts on every criterion, superseded ones included (the decision model's own score, equal to a standalone decision-model grader's), and `None` when every one of its votes failed (`_every_judgment_failed` over its reports: a failed request, which escalated every criterion) or none of its verdicts is left to score; every escalation judge's entry is `None` **by role**, on every item, even one where every criterion escalated.
- **Usage and cost.** Summed over every carrier: the decision model's request (its cost only when `input_cost_per_token` is set) plus each escalation call's usage and cost (under `llm_calls="per_item"`, one call per escalation judge on the item, on its first escalated result). The item report is then assembled by the module function `_ensemble_evaluation_report` (score and `raw_score` over the final verdicts, `mean_agreement`, `cannot_assess_count`, and the `"Every criterion's judgment failed: ..."` error with no score when every criterion's judgment failed), which the offline replay shares (*Offline Cascade Replay, Diagnostics and Calibration* below).
- **Unknown `per_criterion` names.** `CriterionGrader._check_escalation_names(rubrics, where) -> bool` warns (`UserWarning`, attributed by `_caller_stacklevel` to the code that asked for grading) about `per_criterion` names that match no criterion of any of `rubrics`; they set no threshold. The check itself is the module function `_warn_unknown_threshold_names(per_criterion, rubrics, *, source, where)` (`source="EscalationConfig.per_criterion"` here), shared with the offline replay. `judge()` checks the rubric being graded **once per grader** (flag `_escalation_names_warned`, set only after the warning is issued, so a warnings-as-errors filter raises on every call). The two batch paths, `EvalRunner.run` and `fill_ground_truth`, instead grade inside `with _escalation_names_checked(grader, dataset):`, which (for a `CriterionGrader`) checks once, before grading, against every item's rubric (`get_item_rubric`; "any item's rubric"; the items a resumed run or `fill_ground_truth(force=False)` does not grade again included, since a name one of them has is no typo), and returns a context that sets the context variable `_ESCALATION_NAMES_CHECKED` for the items' grading (tasks started inside inherit it; reset on exit), which `judge()` reads to skip its per-rubric check: with per-item rubrics (HealthBench) a name absent from one item's rubric but present in another's never warns, so a warnings-as-errors filter cannot fail (and `fill_ground_truth` silently drop) the items that lack it. The check runs at the call, not on entering the context, so the warning is attributed to the caller rather than to a `contextlib` frame. The batch's check leaves the grader's own direct-call warning unspent.

### Offline Cascade Replay, Diagnostics and Calibration
`src/autorubric/escalation.py` measures a cascade at a threshold without running it there: `replay_escalation` rebuilds the cascade's `EvalResult` from two recorded runs with **no calls**, `escalation_stats` summarizes a live or replayed cascade run as an `EscalationPoint`, and `calibrate_escalation` measures replays over a threshold sweep as an `EscalationCurve`, whose `best` picks a point (types: [Type Catalog](types.md)). A replay reuses the live cascade's own code, so the two cannot drift: the rule `_escalates`, the lookup `_threshold_for` (which `EscalationConfig.threshold_for` delegates to), the threshold validation `_check_thresholds` (which `EscalationConfig.__init__` calls), the unknown-name warning `_warn_unknown_threshold_names`, the item-report assembly `_ensemble_evaluation_report` and `score_reports`.

- **Replay.** `replay_escalation(dm_result, llm_result, escalation, *, per_criterion=None, cannot_assess_config=None, normalize=True, llm_calls="per_criterion") -> EvalResult` (`llm_calls`: *How the LLM run was called* below). `escalation` is a float threshold (with an optional `per_criterion`) or an `EscalationPoint` (its `threshold` and `per_criterion`; passing `per_criterion` too, or a point without a threshold such as an `escalation_stats` point, → `ValueError`); thresholds are validated as `EscalationConfig` validates them, the messages naming `escalation`/`per_criterion` or `EscalationPoint.threshold`/`EscalationPoint.per_criterion`. Items are paired by `item_idx` (output in index order). For each criterion the decision model's recorded vote is turned back into its `CriterionReport` (`_judged_report`, the inverse of `aggregate`'s vote construction) and the criterion is escalated iff `_escalates(report, _threshold_for(criterion, threshold, per_criterion))`, exactly the live rule. `per_criterion` names that match no criterion of the replayed items (the union of their graded criteria, as `EvalRunner` checks a live run) warn as a live cascade does.
- **Reports: the runs' recorded aggregates.** A kept criterion is the decision-model run's `EnsembleCriterionReport` unchanged (its one vote, the final verdict aggregated from it). An escalated criterion is the LLM run's report of it with the votes `[decision model's vote, superseded=True, *the LLM votes]` and `escalated=True` (`_escalated_report`): its final verdict, `final_reason`, `error` and `agreement` are the LLM run's. That is exactly what a live cascade builds, because it aggregates only the non-superseded votes, which are the LLM run's votes in the same judge order with the same judge weights; the aggregation settings (`aggregation`, `ordinal_aggregation`, `nominal_aggregation`) that decided them are therefore the LLM run's, a condition of the same kind as the `seed` and `judge_id`s. Reusing the recorded output of `CriterionGrader`'s aggregation needs neither an aggregation re-implementation nor settings parameters (an in-memory `EvalResult` records no grader config), and a replay can never disagree with the run it reads. Each item report is assembled by `_ensemble_evaluation_report`; scores come from `score_reports` under `cannot_assess_config`/`normalize` (defaults as `CriterionGrader`'s). `judge_scores`: the decision model's entry is recomputed as `score_reports` over its own verdicts, superseded ones included, under the replay's scoring settings (equal to the decision-model run's entry when the settings match), and is `None` when every one of its votes failed (`_every_judgment_failed`), as live; each LLM judge's is `None` by role. Whether a decision-model-run item has votes decides its replay, not its `ItemResult.error` (`_has_votes(item_result)`: criterion reports recorded, `report.report is not None`, even an empty list, so an item graded against an empty rubric is not taken for one whose grading raised). An item whose grading raised has none and stays failed, with its recorded report, `error` and duration (its `item` from `_recorded_item`), as a live cascade would have failed it. An item every decision-model judgment of which failed carries an `ItemResult.error` (`"Every criterion's judgment failed: ..."`) but keeps its failed votes, and is replayed like any other: its failed votes escalate, as a live cascade escalates them. A replayed item's `ItemResult.error` is its replayed report's `error`, as `EvalRunner` records it, so such an item is judged when the LLM run answered any of its criteria and fails when the LLM run's votes on every criterion failed too (`test_an_item_whose_every_judgment_failed_keeps_its_pairs_and_replays` in `tests/escalation/test_escalation_stats.py`).
- **Exactness.** The replay equals the live cascade in every report field but `token_usage`/`completion_cost` (so `compute_metrics(..., per_judge=True)` is equal too) when each run was graded by a `CriterionGrader` configured as the cascade for everything that stage uses, over the same items and rubrics (guidelines included), and the replay's `cannot_assess_config`/`normalize` are the cascade's. The decision-model run: one judge, the cascade's decision model (config, `judge_id`, weight). The LLM run: the escalation judges (`judges=escalation.judges`: configs, `judge_id`s — `"escalation"` for a bare `LLMConfig` — and weights) with every setting they use as the cascade's: `seed` (`CriterionGrader.seed`, generated when not given), `llm_calls`, `shuffle_options`, `system_prompt`, `multi_choice_system_prompt`, `training_data`/`few_shot_config`, and the default response formats (a cascade cannot have others). Both: the cascade's `auto_na_option` and aggregation settings. Recipe for `CriterionGrader(judge_model_config=dm, escalation=escalation, seed=S)` with otherwise default settings: `CriterionGrader(judge_model_config=dm)` and `CriterionGrader(judges=escalation.judges, seed=S)`; for a cascade that also has `llm_calls="per_item"`, the LLM run's grader has it too, and so does the `replay_escalation` call (for the estimates). Only the graded criteria are checked (an `EvalResult` records no grader config, so the docstrings are the only safeguard for the rest). With only another `seed` or `judge_id` the replay is equal in distribution only (shuffled multi-choice options and few-shot examples differ); with another prompt setting (`llm_calls`, `shuffle_options`, a system prompt, few-shot settings) the prompts themselves differ and the replay is not the cascade's run. Under `llm_calls="per_item"` the same exactness is pinned by `TestReplayEqualsTheLiveCascade` in `tests/escalation/test_per_item_cascade.py` (every threshold, `per_criterion` overrides, one judge and panels under other aggregation settings, shuffled multi-choice criteria, a rubric per item, saved experiments); since a per-item call is billed whole, the replay's cost estimate there is the live cost itself, up to summation order. Pinned by `tests/escalation/test_replay_escalation.py`: a live cascade and the two separate runs on scripted clients (`tests/escalation/cascade_runs.py`, `conftest.py`: the real `DecisionModelClient` on a scripted SDK client, LLM answers hashed from the prompt), for one LLM judge (priced and unpriced), two-judge panels under `majority`/`weighted`/`unanimous`, few-shot examples, non-default scoring, experiments loaded with `from_experiment` (both, or one with the other live, either way round: pairing skips the absent submission, the replay keeps the live run's items via `_recorded_item`, and the same-data warning fires), a rubric per item, shuffled multi-choice criteria and a `per_criterion` override; the escalation judges' prompts are a sub-multiset of the LLM run's.
- **Validation (`ValueError`).** `llm_calls` outside `LLMCalls`, by `_check_llm_calls` with the grader's message (checked after the thresholds, before the runs are paired). The same `item_idx` set in both results, each index once; the same recorded submission where both recorded one (`from_experiment` records `""`); the same graded criteria (`EnsembleCriterionReport.criterion`, NA options added by `auto_na_option` included) on every item the decision model has votes on (`_has_votes`; an item whose decision-model grading raised is not checked). `dm_result`: one judge on every item with votes, the same one throughout, one non-superseded vote per criterion that is a decision model's (`_is_decision_model_vote`: `probabilities` and `confidence` set, unless the vote has an `error`, so an item every judgment of which failed passes), no `escalated` report. `llm_result`: votes on every item (`_checked_llm_judge_ids` refuses only an item with none, i.e. whose grading raised; an item every LLM judgment of which failed keeps its failed votes and is accepted), every judge's vote on every criterion (in `judge_scores` order), no decision-model, superseded or escalated votes, the same judges on every item (a cascade has one set of escalation judges). The decision model's `judge_id` must not be an LLM judge's (as in a live cascade). Each is pinned in `TestRequirements` (`tests/escalation/test_replay_escalation.py`), among them a decision-model judge renamed on one item (`item 4 was judged by 'x', earlier items by 'default'`) and an LLM panel with a judge missing from one item.
- **Estimates and how they are marked.** Only per-item cost and time are recorded, so per item `completion_cost = decision-model cost + LLM cost × share` (`share` = the share of the item's LLM calls, per judge, that a live cascade would make, in the unit of *How the LLM run was called* below — with the default `llm_calls="per_criterion"`, the item's escalated criteria over its criteria; `None` unless positive, as in a live report) and `duration_seconds = decision-model duration + LLM duration × share`; the run's `total_duration_seconds` is the two runs' totals with the LLM one pro-rated by the run's escalated share (pooled: by default escalated criteria over the criteria the LLM run judged, not the mean of the items' shares; pinned on the per-item dataset, 3/7 against 7/18). The criteria of an item whose decision-model grading raised (no votes) count in that denominator with none escalated (`_replayed_item` returns the LLM run's calls for it, `_llm_run_calls(0, len(_llm_criteria(llm_item)), llm_calls)`: `len(_llm_criteria(llm_item))` judged pairs per criterion, one call per item): the LLM run's total includes its time on that item, which a live cascade never spends, since it sends the item to no LLM judge; so the run total agrees with the items' own estimates (pinned: 14 of 35 with a first item whose grading raised, not 14 of 30). `token_usage` (per item and `total_token_usage`) is `None`: it cannot be split by criterion. `total_completion_cost` sums every replayed item's estimate, a failed item's included, as `EvalRunner` totals a run ([Key Conventions](conventions.md)). The result is marked in its `experiment_name`, `EvalResult`'s one descriptive field: `"replay of decision-model run '<name>' and LLM run '<name>' (estimated cost and time)"` (`_run_name`; `"an unnamed … run"` for a `None` name); `experiment_dir` is `None`, as no experiment directory exists; no field is added to any type. `started_at`/`completed_at` are the replay's time. The length penalty is not re-applied (compare with runs graded without one; criterion-level metrics are unaffected). The result is an ordinary `EvalResult`: `compute_metrics`, `escalation_stats` and the checkpoint format (`ItemResult.to_dict` → `EvalResult.from_experiment`) take it unchanged (tested).
- **How the LLM run was called (`llm_calls`).** `replay_escalation` and `calibrate_escalation` take a keyword-only `llm_calls: LLMCalls = "per_criterion"` stating how the LLM run's judges were called, which sets the unit in which a replay divides that run's per-item cost and time: the LLM **call**. `_llm_run_calls(n_escalated, n_criteria, llm_calls) -> (cascade_calls, llm_run_calls)` gives an item's calls per judge that a live cascade would make and that the LLM run made: per criterion `(n_escalated, n_criteria)`; per item `(int(n_escalated > 0), int(n_criteria > 0))` — so an item with an empty rubric counts `(0, 0)` (neither run calls on it; its replayed cost stays `None`, as live) and an item whose decision-model grading raised `(0, 1)` (the LLM run called, the cascade would not). `_replayed_item` returns these two counts beside the item, the item's share is their ratio (`0.0` for no call), and `replay_escalation` sums them into the run share, one formula for both units:

| Estimate | `llm_calls="per_criterion"` (default) | `llm_calls="per_item"` |
| --- | --- | --- |
| Item cost | DM cost + LLM cost × (escalated / criteria) | DM cost, plus the LLM cost in full when any criterion escalated |
| Item duration | DM duration + LLM duration × (escalated / criteria) | DM duration, plus the LLM duration in full when any criterion escalated |
| Run duration | DM total + LLM total × (escalated pairs / the LLM run's pairs) | DM total + LLM total × (items with an escalated criterion / the LLM run's items with any criterion) |

- **`llm_calls` is a declared fact that changes only the estimates.** It is not checked: an `EvalResult` records no grader configuration (the manifest's `llm_calls` key, [Reproducibility & Seed Coordination](reproducibility.md), is not read), so, like the other exactness conditions, the caller states it, and for an exact replay it is the cascade's `llm_calls`. The replayed reports are the same whatever it says (verdicts, errors, `experiment_name`), `token_usage` stays `None` (per item it would rest on this unchecked fact), and a wrong value biases only `cost_usd` and `compute_seconds` in `escalation_stats`, on which neither `EscalationCurve.best` nor the per-criterion fit selects. Invalid values → `ValueError` from `_check_llm_calls`, the grader's message. Pinned by `TestEstimatedCostAndTime`, `TestCalibrate` and `TestTheKeyword` in `tests/escalation/test_per_item_cascade.py` (per-item run share 2/3 against the per-criterion 3/7 on the per-item dataset; a decision-model-raised item counted in the denominator only, 6 of 7; an empty-rubric item in neither).
- **Same-data warning.** `_calibration_fingerprint(items)` is a SHA-256 over each item's own `submission`, `prompt` and `reference_submission` and its criteria's `requirement`s, in order — not `_compute_dataset_hash`, which covers only a dataset's name, prompt and sizes and so collides for equal halves of `split_train_test`. A replay computes it over its paired items (`_replayed_fingerprint`: the recorded `DataItem`, `_recorded_item`, and the graded criteria, whose requirements grading keeps) and warns (`UserWarning`, attributed by `_caller_stacklevel`) when an `EscalationPoint`'s `calibration_fingerprint` equals it: a threshold chosen and evaluated on the same pairs is optimistic. Results loaded with `from_experiment` record no submission, so they never match: calibrating on loaded runs and replaying the chosen point on the same loaded runs goes unrecognized (a known limit, stated in the `replay_escalation`, `calibrate_escalation`, `EscalationCurve` and `EscalationPoint.calibration_fingerprint` docstrings; a fingerprint without submissions would collide for equal `split_train_test` halves, and a "check could not be made" warning would fire on every legitimate held-out replay of loaded runs).
- **Diagnostics.** `escalation_stats(result, dataset, *, metric="criterion_accuracy") -> EscalationPoint` pools (item, criterion) pairs from the `escalated`/`superseded` flags, so it needs no shared rubric (per-item heterogeneous datasets, where `compute_metrics` takes its pooled path). It covers items in both `result` and `dataset` (`_covered_items`, in `item_idx` order, as `compute_metrics`); an item whose grading raised has no pairs (no votes: `_has_votes`), while an item whose every criterion's judgment failed keeps its pairs (`test_an_item_whose_every_judgment_failed_keeps_its_pairs_and_replays`), read by the rules below: failed decision-model votes escalated and count in `escalation_rate` only (a failed vote is no prediction), and where the decision model judged but every escalation vote failed, the final verdict only stands in for the failed calls, whatever their category, so the pair is in neither escalated accuracy, as `metric`, read off `compute_metrics`, leaves the item out as errored. The pairs come from `_cascade_pairs(items, dataset)` (each graded item's criterion reports with the decision model's vote and the label; the rubric-length `ValueError`), which the per-criterion calibration shares. `_decision_model_vote` checks the cascade shape (`ValueError` otherwise): a kept criterion has exactly one non-superseded vote, an escalated one a first vote that is the only superseded one, and that vote is a decision model's (so a decision-model-only run reads as a cascade that escalated nothing, while an LLM-only run or a panel is refused). A pair is *labelled* when the item's ground truth resolves (`resolve_ground_truth` against `get_item_rubric`) and does not abstain (`_labels`/`_abstains`: not `CANNOT_ASSESS`, not an NA option), as under `compute_metrics`' default `cannot_assess="exclude"`/`na_mode="exclude"`. Accuracy is exact match (binary verdict, selected option index) pooled over binary and multi-choice labelled pairs. The decision model's predictions are read as `compute_metrics(per_judge=True)` reads a judge's (`_vote_prediction`): an errored vote is no prediction, and neither is an abstention, so a decision-model failure or abstention (escalated at any threshold) counts in `escalation_rate` but in no accuracy: there is no decision-model answer to measure, or to compare the fallback's with. The fallback's predictions are the escalated pairs' final verdicts, read as the run's aggregate metrics read them (`_final_prediction`): an abstaining final verdict is no prediction, and neither is one that stands in for the escalation judges' failed calls (`is_error`, e.g. the worst case of `unknown` failures), which the aggregate leaves out as a failed cell ([Metrics](metrics.md)). `dm_accuracy_kept` is over the kept labelled pairs the decision model answered. `dm_accuracy_escalated` and `fallback_accuracy_escalated` are both over the *deferred* pairs — escalated labelled pairs the decision model answered, i.e. escalated for their confidence — whose final verdict is a prediction, so they compare the two judges on the same pairs. There, escalating gains right verdicts exactly when the fallback's accuracy beats the decision model's, the condition a cascade needs (the fallback beats the decision model where it defers); a deferred pair whose final verdict abstains, or stands in for failed calls, leaves both, and leaves a metric that leaves such verdicts out, such as `criterion_accuracy`, which then rises when the decision model was wrong on it. Measuring the fallback over every escalated pair would mix in the forced escalations (decision-model failures and abstentions), which have no decision-model answer and escalate at every threshold, so the two accuracies would cover different pairs and could point the wrong way. `escalation_rate` is over all pairs, labelled or not; accuracies over empty sets are `None`. `metric` is `compute_metrics(result, dataset)` read by attribute name or callable (`_metric_value`: a number — any `numbers.Real` but a `bool`, so NumPy scalars such as `float32`/`int64` count — recorded as a `float`, or `None`, else `ValueError`; a NaN, e.g. a NumPy mean over no values, is read as `None`, the library's undefined); `compute_metrics`' own errors propagate. `cost_usd` is `aggregate_completion_cost` over every covered item's report, failed items included (a failed item can have been billed; `test_a_billed_item_counts_in_the_cost_when_every_judgment_failed`); `compute_seconds` the sum of the items' `duration_seconds`, failed items included — exact for a live run, sums of estimates for a replay. `threshold`, `per_criterion` and `calibration_fingerprint` are `None`. Pinned by `tests/escalation/test_escalation_stats.py` (a hand-built run fixing every definition — an item whose ground truth does not resolve (an option the criterion lacks) reads as one without ground truth, as `compute_metrics` skips it; an escalated criterion with two superseded votes is refused — and live vs replayed cascades on a shared-rubric and a per-item dataset, where the live cascade's `dm_accuracy_escalated` and `fallback_accuracy_escalated` are 4/6 and 3/6: its 7 forced escalations measured by neither, and the stand-ins of the terse item's two failed LLM calls (a rate-limited call's NA option, a crashed call's worst case, which equals the truth) leaving both; `TestTheDeferredPairs`: with decision-model failures the fallback's six wrong forced verdicts stay out, so a cascade that pays (6/14 → 8/14) reads fallback 1.0 against the decision model's 0.5, where measuring the fallback over every escalated pair gave 0.4; a deferred pair the fallback abstains on, or whose escalation calls failed even with a worst case that equals the label (`test_a_deferred_pair_whose_escalation_calls_failed_is_in_neither`), is in neither accuracy).
- **Calibration.** `calibrate_escalation(dataset, dm_result, llm_result, *, thresholds=None, metric="criterion_accuracy", per_criterion=False, min_pairs_per_criterion=30, cannot_assess_config=None, normalize=True, llm_calls="per_criterion") -> EscalationCurve` makes no calls. `llm_calls` (checked by `_check_llm_calls`, after `min_pairs_per_criterion`) is passed to every replay and so sets only each point's estimated `cost_usd`/`compute_seconds` (*How the LLM run was called* above): the points' other fields, and the point `best` picks, are the same either way, with and without per-criterion fitting (`TestCalibrate` in `tests/escalation/test_per_item_cascade.py`, where under `per_item` the point at the live cascade's threshold costs what the live cascade did, up to rounding). Neither `EscalationPoint` nor `EscalationCurve` records it (nor the scoring settings), so `replay_escalation(dm, llm, point)` estimates as the calibration did only when given the same `llm_calls`. For each threshold of the sweep (default `_DEFAULT_THRESHOLDS` = `i / 50` for `i` in 0..50, i.e. 0.00, 0.02, …, 1.00; given thresholds keep their order, each checked by `_check_thresholds` with messages naming `thresholds[i]`; an empty sweep → `ValueError`) it runs `replay_escalation` with `cannot_assess_config`/`normalize` (every replay, the fit's included, goes through one closure, `measured`) and measures the replay with `escalation_stats` (so `metric` is read off `compute_metrics(replay, dataset)` by `_metric_value`), then fills in the point's `threshold` (a `float`), `per_criterion` and `calibration_fingerprint`. Every point therefore equals `escalation_stats(replay_escalation(dm_result, llm_result, point), dataset)` with its configuration filled in, and the point at a live cascade's threshold reads as the live run's `escalation_stats` but for the estimated `cost_usd`/`compute_seconds` (tested). The fingerprint is `_calibration_fingerprint` over the calibration items — the dataset's items the runs graded (`_covered_items(dm_result, dataset)`: each `DataItem` with its `get_item_rubric` criteria, in `item_idx` order) — which equals `_replayed_fingerprint` of the same runs: `replay_escalation(dm, llm, curve.best())` on the calibration runs warns, on the runs of another `split_train_test` part it does not. Taking it from the dataset, which always holds the submissions, keeps results loaded with `from_experiment` (no submissions) from ever matching falsely. `per_criterion` must be a `bool` (a mapping is refused: thresholds by name go to `replay_escalation`), `min_pairs_per_criterion` a positive int (`_is_positive_int`); `replay_escalation`'s and `escalation_stats`' errors propagate. The docstrings state the cost (no calls, but `llm_result` is a full LLM grading of every criterion of the calibration items), the same-data caveat (a point chosen and measured on the same pairs is optimistic; measure it on held-out items) and the exactness condition (`replay_escalation`'s, *Exactness* above: each run graded by a `CriterionGrader` configured as the cascade for that stage — for the LLM run `judges=escalation.judges` with the cascade's `seed`, `llm_calls`, `shuffle_options`, system prompts, few-shot settings, `auto_na_option` and aggregation settings — and the cascade's scoring settings: without them score-level metrics — `score_rmse`, `score_pearson`, `bias`, … — read replays scored by `CannotAssessConfig()`/`normalize=True`, not the cascade's run; criterion-level metrics do not read scores).
- **The metric.** Higher is better (negate a lower-is-better metric in a callable). The default `criterion_accuracy` pools pairs otherwise than the point's accuracies, and differently on `compute_metrics`' two paths (both described in the `EscalationPoint` docstring). On the per-criterion path (`_criterion_level_scalars`; a shared rubric, or per-item rubrics that are all the same) it reads the binary pairs alone when there are any (a `CANNOT_ASSESS` on either side dropped under `cannot_assess="exclude"`), else the multi-choice pairs with an NA prediction or label counted as one more option. On a per-item heterogeneous dataset `compute_metrics` takes `_compute_per_item_pooled_metrics`, whose run-level fields are pooled over rubric points: `criterion_accuracy` is the exact accuracy over the points of every scale (binary and multi-choice together), leaving out a point whose prediction abstains (`n_abstain`) and counting one whose label abstains (`CANNOT_ASSESS`, an NA label) as a miss; `mean_kappa` is the binary points' kappa, so the default metric is defined there; a metric of one scale type needs a callable reading `pooled_by_scale` (tested).
- **The selection rule, `EscalationCurve.best(max_escalation_rate=None, tolerance=0.0)`.** Among the points with `escalation_rate <= max_escalation_rate` (inclusive; every point without a budget) and a defined `metric` (`None` and NaN are passed over), find the best metric; among those within `tolerance` of it — `metric >= best - tolerance` or `math.isclose(best - metric, tolerance)` (default `rel_tol`, no `abs_tol`), so a gap equal to the tolerance up to rounding counts (`0.4 - 0.35` is `0.05000000000000004`) while `tolerance=0` stays exact — return the least escalating. Ties: the higher metric, then the lower `threshold` (on new items a lower threshold never escalates more), then the earlier point. A `None` `escalation_rate` (a run with no pairs) is outside any budget and ranks last; a `None` `threshold` ranks after numeric ones. With escalation judges called per criterion, fewer escalated pairs mean fewer LLM calls, so `tolerance` trades metric for calls; under `llm_calls="per_item"` they make one call per item with any escalated criterion, so escalating fewer pairs can save no call at all, and the `EscalationCurve` docstring says to compare the points' `cost_usd`/`compute_seconds` before giving up metric for it. `ValueError` for an empty curve, no point within the budget (the message gives the lowest rate), none within it with a metric, `tolerance` not a number >= 0 (`math.inf` allowed: the least escalating point with a metric), `max_escalation_rate` not in [0, 1]. The rule has one implementation, `_selected(candidates, max_escalation_rate, tolerance)` over `(escalation_rate, metric, threshold)` tuples, shared by `best` and the per-criterion fit. `EscalationCurve.to_dataframe()` imports pandas lazily, as `MetricsResult.to_dataframe` does: a row per point, the `EscalationPoint` fields as columns (`per_criterion` a dict or `None`; an empty curve keeps the columns).
- **Per-criterion fitting (`per_criterion=True`).** `_fitted_thresholds` counts each criterion *name*'s labelled pairs over `_cascade_pairs(_covered_items(dm_result, dataset), dataset)` (the calibration pairs, the same in every replay; pooled across items, since a live cascade looks thresholds up by name; unnamed criteria are skipped, as they always follow the global threshold; names in order of first appearance). A name with at least `min_pairs_per_criterion` labelled pairs (inclusive) is fitted; thinner names follow the global threshold and are named in a `UserWarning` (`_warn_global_threshold`: `'<name>' (<n> labelled pairs)` and the reason; attributed by `_caller_stacklevel`; one warning per reason). **The fit is coordinate-wise on the run's own `metric`**: it starts from `start`, the global threshold `_selected` picks at its defaults (no budget, no tolerance) on the unfitted sweep's points; then, for each fitted name in turn, it measures the replay at `start` with `{**fitted, name: t}` for every `t` of the sweep and keeps `sweep[_selected((escalation_rate, metric, t) …)]`. A threshold decides only its own criterion's pairs, so only that name's pairs vary within a step, and the run's escalation rate orders the candidates as the name's own would. The current configuration is a candidate (the name at `start`), so no step lowers the metric: the point at `start` with the fits measures at least as high as without them, and so does `best` at its defaults. Selecting by the run's metric (rather than by a per-criterion accuracy) is what makes the fit serve the metric `best` ranks: a per-criterion ratio of right to predicted pairs can rise while the pooled `criterion_accuracy` falls, when the fallback abstains on escalated pairs (the predicted pairs shrink); on the per-criterion path `criterion_accuracy` reads only binary pairs when a rubric has any (a multi-choice criterion's threshold then cannot move it, and the fit escalates it least) and counts NA as an option on a rubric without binary criteria, while on the pooled path it reads every scale's points, so every criterion's threshold can move it (*The metric.* above); and any `metric` (a `MetricsResult` attribute or callable) is fitted as given. If `metric` is `None` at every point of the unfitted sweep, there is no start: every eligible name is warned about and nothing is fitted. The curve's points are one per swept global threshold, each with `per_criterion` = the fitted thresholds (the same contents at every point, a copy each; `None` when nothing was fitted, so an all-thin calibration equals the global one), measured on `replay_escalation(dm, llm, threshold, per_criterion=fitted)`: exactly what `replay_escalation(dm, llm, point)` replays and `EscalationConfig(judges, point.threshold, per_criterion=point.per_criterion)` runs live. `best`'s budget and tolerance therefore trade on the criteria that follow the global threshold. Cost: the unfitted sweep, one sweep per fitted name, and one sweep with the fits (each a replay plus `compute_metrics`; about 50 ms per replay at 300 items × 7 criteria).

### Score Calculation
A **single scoring core** — `score_reports(reports, config, normalize=True)` in `scoring.py` — is the source of truth for weighted-criterion scoring, shared by all three scorers: the live grader (`CriterionGrader._calculate_score_from_reports`), `Rubric.compute_score` (ground-truth / expected scores — parses verdicts into `CriterionReport`s, delegates), `RubricDataset.compute_weighted_score` (delegates to `Rubric.compute_score`). Every path builds `CriterionReport`s and runs the same core, so they agree exactly across every `CannotAssessStrategy` x {binary, multi-choice} x {+/- weight}.

```python
# Positive criteria: MET earns weight, UNMET earns 0
# Negative criteria: MET subtracts weight, UNMET contributes 0
weighted_sum = sum(report.score_value * report.weight for non-abstained reports)
#   + sum(_abstain_contribution(report, config) for abstained reports)  # NA / CANNOT_ASSESS
score = clamp(weighted_sum / total_positive_weight, 0, 1)  # if normalized
# Negative-weight-only fallback (no positive weight): 1 + weighted_sum / total_negative_weight
# No criterion left to score (no reports, or SKIP excluded every one): None, normalized or raw
# Length penalty subtracted after base calculation (a score-less report is returned unchanged)
```

**No score, never a fabricated `0.0` (#18).** `score_reports` returns `float | None`: `None`, normalized or raw, when no criterion is left to score — there are no reports (an empty rubric), or `SKIP` excluded every one (every criterion abstained: binary `CANNOT_ASSESS` or a multi-choice NA option). It counts the criteria it scores (`n_scored`), so zero-weight criteria still count: when only they are left the score is `0.0` (the final `return 0.0`, commented "only zero-weight criteria were scored"). `ZERO`, `PARTIAL` and `FAIL` keep abstentions in the score, so abstentions never leave them without a number (an empty report list still does). The grader then reports `score`/`raw_score`/`llm_raw_score` `None` with `error=None`: this is no failed grade, unless every criterion's judgment failed (next paragraph) ([Abstention Handling](abstention.md)); `Grader.grade` returns a report with no score unchanged instead of applying the length penalty. Ground truth follows the same rule: `Rubric.compute_score` and `RubricDataset.compute_weighted_score` return `float | None` (`None` when every label abstains under `SKIP`), as do `CriterionGrader._calculate_score_from_reports` and the `score` callable `_ensemble_evaluation_report` and the replay take (`Callable[[list[CriterionReport], bool], float | None]`).

**An item whose every criterion's judgment failed has no score.** Separately, `_ensemble_evaluation_report` asks `_every_judgment_failed(ensemble_reports)` (`scoring.py`: at least one report, each `is_error`; an `EnsembleCriterionReport` is one only when every vote aggregated on it failed, so in a cascade an escalated criterion counts as failed when its escalation votes all failed, even where the decision model judged it). When every criterion's judgment failed, the item's verdicts only stand in for failed calls, so the report gets no score — `score`, `raw_score` and `llm_raw_score` `None`, whatever the `CannotAssessStrategy`, instead of a number built from the stand-ins (before #18: `0.0` under `SKIP`, the worst case for `unknown` failures, a number under `ZERO`/`PARTIAL`/`FAIL`) — and `error` = `"Every criterion's judgment failed: <first criterion error>"`, plus `" (and 1 other error)"` / `" (and N other errors)"` counting the other distinct criterion errors (`dict.fromkeys` over the reports' non-`None` `error`s, in rubric order; `test_the_error_of_an_item_nothing_judged_names_the_first_failure`). Each criterion report keeps its stand-in verdict and its own `error`. The report is identical for either judge kind (a decision model's failed request yields the report an LLM grader whose every call failed yields) and is shared by `CriterionGrader.aggregate` and the offline replay. Per judge, `CriterionGrader.aggregate` sets a primary judge's `judge_scores` entry to `None` when `_every_judgment_failed(judge_result.reports)` (it judged nothing on the item, whatever its stand-ins would score), and `score_reports` makes it `None` when none of the judge's verdicts is left to score; an escalation judge's is `None` by role, and a cascade's decision model that judged keeps its score even on an item that fails. Where the item's error goes next (`EvalRunner`, `compute_metrics`): [Abstention Handling](abstention.md).

`CannotAssessStrategy` applies uniformly to binary CANNOT_ASSESS and multi-choice NA via `_abstain_contribution`: `SKIP` excludes the criterion from **both** numerator and denominator; `ZERO`/`PARTIAL`/`FAIL` keep it in the denominator with a weight-sign-aware contribution. `FAIL` uses the score-minimizing realizable outcome — `Criterion.worst_scored_option()` for multi-choice (same canonical worst case as the `unknown`-error path and metrics `na_mode="as_unmet"`), UNMET for positive weight (0) / MET for negative weight for binary. (The legacy `Rubric._apply_cannot_assess_strategy` was removed when `compute_score` was routed through the core — it had a SKIP double-subtraction bug, both excluding the abstained criterion *and* subtracting its weight from the denominator, that the core fixes.)
