### Grading Flow
1. `Rubric.grade()` delegates to grader's `grade()` method, adding `guidelines=self.guidelines` only when the rubric has guidelines (see *Rubric guidelines* below)
2. `CriterionGrader` treats a single judge (`judge_model_config=`, or its deprecated alias `llm_config=` — see [Key Conventions](conventions.md)) as an "ensemble of 1" with `judge_id="default"`. At the start of `judge()` the rubric is normalized **once** to an *effective rubric*: with `auto_na_option=True` (default) every multi-choice criterion is guaranteed an NA abstain option via `Criterion.with_guaranteed_na_option()` (structural analog of binary CANNOT_ASSESS; see [Multi-Choice Criteria](multi-choice.md)). Normalization is pure (no RNG), same length/order (so `criterion_idx` and the shuffle RNG key stay aligned), never mutates the user's rubric. Effective options ride through `CriterionReport.options`, shared by prompt building, verdict mapping, scoring, and aggregation. `auto_na_option=False` ⇒ forced-choice (no injection); never strips an author NA option.
   - **Judge identity: repeated `judge_id`s warn.** A `judge_id` keys the client maps (`_clients`/`_decision_clients`, last write wins), the few-shot examples (`_criterion_examples`/`_multi_choice_examples`), the shuffle and few-shot RNGs (`_derive_shuffle_rng`), `judge_scores` and the per-judge metrics, so `judges=` with a repeated id conflates those judges: same-kind judges all call the model of the last of them (two kinds keep separate clients), and all share one `judge_scores` key and per-judge metrics entry and identical option shuffles and few-shot examples; `replay_escalation` refuses such a run as `llm_result` (its votes outnumber its `judge_scores` keys). Construction still accepts it and grades exactly as before, but warns `FutureWarning("judge_ids should be unique; repeated: 'x'. ...")` naming each repeat once, sorted (`_repeated_judge_ids`, shared with the cascade's `ValueError`), `stacklevel=2`, after the cascade checks (a cascade's primary is one judge, so a cascade never warns). A repeat becomes a `ValueError` in the next major version, as in a cascade. Why `FutureWarning` rather than `DeprecationWarning`: [Key Conventions](conventions.md). Tests: `tests/graders/test_duplicate_judge_ids.py` (the warning, and grading unchanged as it describes) and `tests/decision/test_decision_ensemble.py` (a repeat across kinds).
3. `judge()` gathers one `_judge_all_criteria_for_judge` per judge (parallel across judges), which dispatches on the judge's kind, `isinstance(judge.llm_config, DecisionModelConfig)`: an LLM judge makes concurrent calls, one per criterion, via `asyncio.gather()` over `_judge_single_criterion` (unchanged); a decision-model judge makes **one request per item** for the whole rubric (see *Decision-Model Judges in `CriterionGrader`* below). Either way the judge returns one `CriterionResult` per criterion of the effective rubric, in order, and everything downstream (`aggregate`, `score_reports`, `judge_scores`, the length penalty in `Grader.grade`) is shared. A cascade then runs its escalation judges on the escalated criteria only (see *Confidence Cascade* below)
4. Binary criteria use `binary_response_format` (default: `CriterionJudgment`); multi-choice criteria use the symmetric `multi_choice_response_format` (default: `MultiChoiceJudgment`). Meta-rubric evals override both — `MetaCriterionJudgment` (binary) and `MultiChoiceMetaJudgment` (multi-choice) — each adding a structured `affected_criteria` field. Both formats are LLM-only: either one with any decision-model judge → `ValueError` at construction (see *Decision-Model Judges in `CriterionGrader`* below)
5. If the response includes a non-empty `affected_criteria`, grader injects `[Affects: #1, #3]` into the reason string. Applied symmetrically to binary and multi-choice success paths via the shared `_inject_affected_criteria()` helper (error paths never inject). Both success paths then pass the tagged reason through the shared `_require_llm_reason()`, which enforces that an LLM judge's reason is a string: a null `explanation` (possible only with a custom response format that makes it optional) raises `ValueError`, which `classify_grading_error()` routes as `parse` (→ `CANNOT_ASSESS` / the NA option, see *Judge-call failure routing* below), exactly as the report's own `str` validation did before `reason` widened to `str | None`. Like that validation it checks the reason as stored, after tagging, so a tagged null explanation stays the accepted string `"None [Affects: ...]"`. The read order matches the code before the widening, where the null check was the report's own validation and so ran after every read: the binary path reads `explanation` (and tags it), then `criterion_status`, then runs the null check; the multi-choice path reads and range-checks `selected_option`, then reads `explanation`, then runs the check. A custom-format judgment missing a field therefore fails as `unknown` on the first missing field in that order (its recorded `error` text names that field), and a null `explanation` is a `parse` failure only when the verdict field is readable; the binary order is pinned by `test_binary_judgment_missing_a_field_fails_on_the_first_one_read` in `tests/graders/test_error_routing.py`.
6. Aggregates votes using strategy (majority/weighted/unanimous/any). For binary criteria `majority` is an **unweighted head-count** (> 50% of judges), distinct from `weighted` (summed judge weights). Multi-choice criteria aggregate via two **independent** knobs — `ordinal_aggregation` and `nominal_aggregation` — that binary `aggregation` never touches (values + axis in [Multi-Choice Criteria](multi-choice.md)). Each vote is built from its judge's `CriterionReport`, copying `reason`, `error`, `reasoning`, `probabilities` and `confidence` (and `superseded=True` for a cascade's decision-model vote on an escalated criterion; only non-superseded votes are aggregated, see *Confidence Cascade* below). `EnsembleCriterionReport.final_reason` comes from the shared `_join_vote_reasons(votes)` (binary `_aggregate_votes` and both multi-choice returns of `_aggregate_multi_choice_votes`, including the all-NA path): each vote renders as `"judge_id: reason"`, joined with `" | "`, **skipping votes whose `reason is None`** by an identity check (not truthiness), so an LLM vote with an empty explanation still renders as `"judge_id: "` exactly as before; the result is `None` when no vote carried a reason. The fixed reasons are unchanged and returned whatever the votes' reasons: `"No votes"` (empty vote list, binary and multi-choice) and the binary `"All judges could not assess"` (every vote `CANNOT_ASSESS`), so `final_reason is None` only when no vote carried a reason, not whenever none did.
7. Returns `EnsembleEvaluationReport`

**Rubric guidelines.** `Rubric.guidelines` (free text for every criterion; [Type Catalog](types.md)) reaches every judge without touching the abstract `Grader` API. Every grading path goes through `Rubric.grade` — `EvalRunner._grade_item` and `fill_ground_truth` via `get_item_rubric(idx).grade(...)`, so a per-item rubric brings its own guidelines (or none) and never inherits the dataset rubric's; the improvement loop via `rubric.grade(...)`.
- **Absent means `None`.** Blank text means no guidelines everywhere: `_normalize_guidelines` (`utils.py`: `None`/blank → `None`, other text verbatim, non-`str` → `TypeError`) is applied by `Rubric`, `Grader.grade`, `CriterionGrader.judge`, the four user-prompt builders (via `_guidelines_block`) and `build_state`.
- **`Rubric.grade`** calls `grader.grade(to_grade=, rubric=, query=, reference_submission=)` exactly as before when the rubric has no guidelines, and adds `guidelines=` only when it has them — and only if `grader.grade` accepts it; a `grade` override with the old signature is called without them, and warns (below), as a legacy `judge` does.
- **`Grader.grade(..., *, guidelines=None)`** (keyword-only) forwards them to `judge` as `guidelines=` only if `judge` accepts that keyword — a `guidelines` parameter that can be passed by keyword, or `**kwargs` (`_accepts_guidelines`; positional-only does not count, an unreadable signature counts as not accepting). Otherwise, and whenever there are none, `judge(to_grade, rubric, query, reference_submission)` is called positionally exactly as before (the call goes through a `cast` to `Callable[..., Awaitable[Any]]`, since the abstract signature does not declare the keyword). The abstract `judge`/`aggregate` signatures are unchanged, so existing subclasses (e.g. the experiments' decision-model grader, the stub in `tests/eval/test_error_report_none_score.py`) keep working. The length-penalty path rebuilds the report exactly as before — no new report fields.
- **Checked once per grader instance** by `_takes_guidelines(grader, method_name)` (`graders/base.py`, shared by both levels): `inspect.signature` runs once and the result is cached **on the instance, not the class**, because the method is looked up through the instance (an instance attribute — wrapper, test double — can replace the class's) and the warning is per instance too. The entry (`_guidelines_support`, keyed by method name) remembers the implementation it describes (`__func__` of a bound method), so a method replaced later is re-inspected. It lives in the instance `__dict__` (`_instance_dict`: only a writable `dict`), which works without a `Grader.__init__` call and bypasses any `__setattr__` override; an object without one is inspected on every call.
- **Legacy warning.** `_warn_ignores_guidelines` issues `UserWarning("<GraderClass> ignores rubric guidelines")` **once per grader instance** (flag `_guidelines_warned` in the instance `__dict__`), and never when the rubric has no guidelines. The flag is set only after `warnings.warn` returns, so under a warnings-as-errors filter (`-W error`, `filterwarnings = error`) the warning raises on every call, as Python's own warning registry makes it, rather than once and then grading without the guidelines unannounced. `_caller_stacklevel()` attributes it to the first frame outside `_INTERNAL_DIRS` — the autorubric package and asyncio: the user's `rubric.grade`/`grader.grade` line, or, for items graded in `evaluate`'s tasks (no user frame above the event loop), the line that started the loop (e.g. `asyncio.run(...)`); `warnings.warn`'s `skip_file_prefixes` does this only from Python 3.12.
- **`CriterionGrader.judge(..., *, guidelines=None)`** normalizes once, then threads them (keyword-only) through `_judge_all_criteria_for_judge` to both judge kinds. **LLM judges:** `build_user_prompt`, `build_few_shot_user_prompt`, `build_multi_choice_user_prompt` and `build_multi_choice_few_shot_user_prompt` take a keyword-only `guidelines: str | None = None`; when set, the user prompt **starts** with `GUIDELINES_BLOCK` (`prompts.py`: `<guidelines>\n{guidelines}\n\nThese guidelines apply to every criterion. The criterion text governs; the guidelines clarify how to apply it.\n</guidelines>`), then a blank line — how the builders separate every block — then the unchanged prompt (embedded as `guidelines_text`, like `query_text`/`reference_text`). Identical for every criterion of an item, it extends the prefix a provider's automatic prompt caching reuses; the precedence rule lives in the block, not the system prompts, so system prompts are untouched, prompts without guidelines stay byte-identical (response caches valid), and a custom `system_prompt` still gets the rule. **Decision models:** the state's first field (*Decision-Model Framing* below).

**Judge-call failure routing.** On a failed judge call the grader calls `classify_grading_error()`. `infrastructure`/`parse` failures → `CANNOT_ASSESS` (binary) or `na=True` (multi-choice), so under the default `CannotAssessStrategy.SKIP` they leave the scoring denominator and do NOT penalize the submission. Only `unknown` errors keep the conservative worst-case verdict: UNMET for positive weight, MET for negative; for multi-choice, the score-minimizing scored (non-NA) option via `Criterion.worst_scored_option()`, never an NA option. An infra/parse abstain points `na=True` at a **genuine** NA option (`criterion.na_option_index`, guaranteed by default auto-injection). With `auto_na_option=False` and no author NA option there is none to point at, so it is a **genuine no-option abstain**: `na=True` with `selected_index=None`/`selected_label=None` — never `na=True` against a scored option, still excluded under SKIP. Decision-model (TypeSafe SDK) failures are classified by the SDK's own exception types, ahead of the `ValueError` rule, by `_classify_typesafe_error` in `llm.py`: `TypeSafeAPIResponseValidationError` (the answer did not validate), `TypeSafeBadRequestError` (400) and `TypeSafeUnprocessableEntityError` (422, e.g. a state over the model's input limit) → `parse`; every other `TypeSafeError` — authentication, permission, not found, rate limit, 5xx, and `TypeSafeAPIConnectionError` / `TypeSafeAPITimeoutError`, which subclass `TypeSafeError` directly, not `TypeSafeAPIError` → `infrastructure`. Both abstain; only the recorded prefix differs. The branch looks `typesafe_sdk` up in `sys.modules` and never imports it: an SDK exception can only exist once the SDK was imported, so a core install without the SDK pays nothing. The category-prefixed message (`"infrastructure: ..."`) is stored on `JudgeVote.error` (binary) / `MultiChoiceJudgeVote.error` (multi-choice). `EnsembleCriterionReport.error` is set only when EVERY contributing vote errored (mixed → genuine verdict, `error is None`), derived via the shared helper `_aggregate_error(votes)` used by both paths (per-vote `.error` is the single source). The `is_error` property on `CriterionReport`/`EnsembleCriterionReport`/`JudgeVote`/`MultiChoiceJudgeVote` distinguishes error-induced from genuine verdicts without string-matching `reason`. Every failure report, for either judge kind, comes from the single module helper `_failed_judgment_result(criterion, judge_id, error, *, shuffle_order=None)`: it classifies, logs the warning (`"Error evaluating criterion ..."` / `"Error evaluating multi-choice criterion ..."`, naming the judge and category), picks the verdict above, and builds the report with `reason="Judge call failed (<category>): <error>"`, the category-prefixed `error`, `usage`/`cost` `None`, and, for multi-choice, the `shuffle_order` the judge was shown. Each criterion kind's report is built with exactly the fields the LLM paths always passed (pydantic's fields-set included), so the LLM path is unchanged; a decision model's failure reports are therefore identical to an LLM judge's for the same exception (pinned by `tests/decision/test_decision_grader.py`).

**Extended-thinking trace preservation.** `LLMClient.generate()` injects the judge's verbose deliberation trace into `judgment.reasoning` (only when thinking is enabled). The grader copies `judgment.explanation` → `CriterionReport.reason` (concise conclusion) **and** `judgment.reasoning` → `CriterionReport.reasoning` (the deliberation it was distilled from) at both binary and multi-choice success constructions, via `getattr(judgment, "reasoning", None)` (tolerates custom `binary_response_format` models lacking the field). Ensemble aggregation forwards each judge's `cr.report.reasoning` → `JudgeVote.reasoning` / `MultiChoiceJudgeVote.reasoning` (alongside the `error` copy). Error-path reports carry `reasoning=None`. There is **no** top-level `EvaluationReport`/`EnsembleEvaluationReport.reasoning` and **no** aggregated `EnsembleCriterionReport.reasoning` — concatenating per-judge traces has no clean semantics, so per-vote granularity is the carrier (unlike `error`, whose all-failed aggregation transfers).

**Provider schema vs parsing schema (`reasoning`-strip).** Because `judgment.reasoning` is *injected* from the provider's separate thinking channel and never read from the model's JSON output, the `reasoning` field is dead weight in the schema sent over the wire. Under OpenAI/Groq **strict** structured output, every property is forced into `required`, so leaving `reasoning` in the provider schema makes models that follow the prompt (which only asks for `criterion_status`/`selected_option` + `explanation`) — e.g. **Llama and Qwen on Groq** — fail schema validation and collapse every verdict to `CANNOT_ASSESS`. `LLMClient.generate()` therefore routes `response_format` through `_provider_response_format()` (in `llm.py`), which, for any response model carrying a `reasoning` field, sends litellm a json-schema dict with `reasoning` removed from `properties`/`required` (built via `litellm.utils.type_to_response_format_param`); **parsing still uses the full Pydantic model**, so reasoning injection when thinking is enabled is unaffected. Models without a `reasoning` field (custom `binary_response_format`s) and any unexpected litellm shape fall through unchanged — no behavior change for OpenAI/Anthropic/Gemini (verdicts identical with and without the strip).

**Few-shot examples and their reasons (LLM judges).** With `training_data`, `_prepare_examples` draws every criterion's examples once per LLM judge at construction, each draw from `_derive_shuffle_rng(few_shot_seed, FEW_SHOT_DOMAIN, criterion_idx, judge_id)` ([Reproducibility & Seed Coordination](reproducibility.md)). Binary criteria: `_select_examples_for_criterion` groups the training items by verdict and, with `FewShotConfig.balance_verdicts` and more than one verdict present, picks across the groups (`_balanced_selection` → `_balanced_pick`), else takes the first `n_examples` of one shuffle; it returns `FewShotExample`s. Multi-choice criteria: `_select_multi_choice_examples` groups by option index (labels mapped by `_label_to_option_index`) and picks the same way, returning `(submission, selected_index, reason)` tuples, which each call re-indexes to its shuffled option order. On all four paths an example's reason is its item's `DataItem.ground_truth_reasons[criterion_idx]`, read by `_ground_truth_reason(item, criterion_idx)` (`None` when the item has no reasons); reading it draws no randomness, so reasons never change which items are drawn or in what order. `build_few_shot_user_prompt` / `build_multi_choice_few_shot_user_prompt` add `<reason>...</reason>` after an example's `<verdict>` / `<selected_label>` only when `include_reason=True` and the reason is non-empty: with `include_reason=False`, or with no reasons in the training data, every prompt (and so every response-cache key) is byte-identical to one built without reasons. Pinned through the prompts the grader sends by `tests/graders/test_few_shot_reasons.py`; the few-shot grader golden (`include_reason=True`, a pool without reasons) is unchanged.

**Prompt text: one source, byte-identical.** The binary verdict definitions are named constants in `prompts.py` — `MET_DEFINITION`, `UNMET_DEFINITION`, `CANNOT_ASSESS_DEFINITION`, and for negative criteria `NEGATIVE_MET_DEFINITION` / `NEGATIVE_UNMET_DEFINITION` — and `GRADER_SYSTEM_PROMPT_DEFAULT` is built from them (an f-string for the instructions, concatenated with a plain string for the brace-bearing response format and examples), so any other framing of a binary criterion reuses the exact LLM wording. Prompts must stay byte-identical when a feature is unused, because `LLMClient._cache_key` hashes both prompts (and providers cache prefixes). `tests/test_prompt_goldens.py` pins this against goldens captured from the pre-refactor library in `tests/golden/prompts/`: every prompt constant, every user-prompt builder over representative inputs (binary ±weight, ordinal/nominal with NA, few-shot, reference, thinking/output, query present/absent), and the exact calls a fixed-seed `CriterionGrader` sends (single judge, ensemble, few-shot, forced-choice unshuffled — which also pins shuffling and few-shot selection). Run the module as a script with `--write` to regenerate deliberately. The same module pins rubric guidelines against those goldens, with no files of their own: with guidelines, every builder case and every captured grader call (graded through `Rubric.grade`) must be a literal `GUIDELINES_BLOCK` followed by the golden prompt, with the golden system prompt; with `guidelines=None` or blank text, exactly the golden. The decision-model framing text (next section) is separate constants — `DECISION_MODEL_TASK_INSTRUCTION`, `DECISION_MODEL_THINKING_OUTPUT_TASK_INSTRUCTION`, `DECISION_MODEL_GUIDELINES_INSTRUCTION`, `DECISION_MODEL_REFERENCE_INSTRUCTION`, `DECISION_MODEL_CRITERION_PREFIX` — that no LLM prompt uses, so adding them left every LLM prompt byte-identical; its binary outcomes reuse the verdict-definition constants above, so the two judge kinds cannot drift.

### Decision-Model Framing and Answer Mapping
A decision model (`DecisionModelConfig`, see [Type Catalog](types.md)) grades an item with **one request for the whole rubric**: a shared `state` plus one typed question per criterion of the *effective rubric*. The pure, synchronous helpers in `decision.py` build the request and map the response; `CriterionGrader` sends it (next section).

- **State (`build_state(to_grade, *, query=None, reference_submission=None, guidelines=None)`).** Field names mirror the LLM user prompt's XML tags; optional fields appear only when present — non-empty, the rule `build_user_prompt` applies; for `guidelines`, not blank (`_normalize_guidelines`) — in the order `guidelines`, `input`, `reference_submission`, then `submission`. The guidelines go verbatim, once per request whatever the criterion count (billed once), and, being state, into the response cache key; a rubric without guidelines sends exactly the state it did before guidelines existed. When `to_grade` holds a `<thinking>`/`<output>` **section** (an opening marker followed by its closing marker, case-insensitive; `Grader.grade` flattens a `{"thinking", "output"}` dict into such sections), `thinking` and `output` from `parse_thinking_output` replace `submission`, both always (`thinking` possibly `""`). Detection is `_has_thinking_output_sections` in `utils.py`, which shares the compiled `_THINKING_SECTION`/`_OUTPUT_SECTION` patterns with `parse_thinking_output`, so "has a section" means exactly "`parse_thinking_output` recovers one"; plain text (stray or unclosed markers included) goes out unchanged as `submission`.
- **Questions (`build_questions(rubric, config, state) -> (questions, errors)`; single criterion: `build_question`).** One question per criterion of the effective rubric (NA options already guaranteed by `_effective_criterion`), id `question_id(criterion_idx)` = `"c{criterion_idx}"` — the index that also keys shuffling and few-shot selection, so ids are unique for unnamed or duplicate-named criteria. The question type is `_question_kind(criterion, config)`, the single source that `answer_to_report` checks answers against. Requirement and labels are **verbatim**; only structure differs:

| Criterion | Framing | Question |
| --- | --- | --- |
| binary | `binary_framing="noul"` | `Noul(instructions=requirement)` |
| binary | `"noul_framed"` (default) | `Noul(instructions=framed, criteria={"true": MET_DEFINITION, "false": UNMET_DEFINITION})` |
| binary | `"choice"` | `Choice(instructions=framed, criteria={"MET": MET_DEFINITION, "UNMET": UNMET_DEFINITION, "CANNOT_ASSESS": CANNOT_ASSESS_DEFINITION})` |
| multi-choice | nominal, or ordinal with `ordinal_framing="choice"` (default) | `Choice(instructions=requirement, criteria={label: None ...})`, NA option included |
| multi-choice | ordinal with `ordinal_framing="score"` | `Score(instructions=requirement, criteria=[non-NA labels, in order])` |

A negative weight selects `NEGATIVE_MET_DEFINITION`/`NEGATIVE_UNMET_DEFINITION` (the `"true"`/MET outcome is still "the thing is present"). The **framed** instructions (`_framed_instructions`) are a task sentence, then one context sentence per optional state field the judgment depends on, then `DECISION_MODEL_CRITERION_PREFIX` + the requirement, which always comes **last**, so no fixed text follows (and blurs into) a requirement that has no guaranteed terminal punctuation. With no optional field this is exactly the template the motivating experiments used: ``"Determine whether this criterion is satisfied by the `submission`. Criterion: {requirement}"``. Context sentences follow the state-field order: `guidelines` adds `DECISION_MODEL_GUIDELINES_INSTRUCTION` (``"Apply the `guidelines`; the criterion text governs."``, the precedence rule of `GUIDELINES_BLOCK`), then a `reference_submission` its sentence — e.g. ``"<task> Apply the `guidelines`; the criterion text governs. Use the `reference_submission` ... Criterion: {requirement}"``. A `thinking`/`output` state swaps in `DECISION_MODEL_THINKING_OUTPUT_TASK_INSTRUCTION` (``"...satisfied by the `output`; the `thinking` is context only."`` — approximating the LLM rule "evaluate only `<output>` unless the criterion is about reasoning"); a `reference_submission` adds `DECISION_MODEL_REFERENCE_INSTRUCTION` with `{judged}` = `submission` or `output` (the LLM judge's calibrate-don't-compare rule). Clauses apply **only to framed binary questions**: bare `noul` and multi-choice questions see extra fields only through the state. Only which state keys exist shapes a question, never their values; every backticked name in framed instructions is a state key (both pinned by tests). Question objects are the SDK's `Noul`/`Choice`/`Score`, built through `_import_typesafe_sdk()`.

- **Inexpressible criteria.** Questions are built before anything is sent. A criterion a question cannot express — repeated `Choice` labels (keys are labels; the message names them, e.g. an author label equal to the auto-injected `CANONICAL_NA_OPTION` label), more than 255 `Choice` options (`_MAX_CHOICE_OPTIONS`), or outside 2–10 non-NA `Score` levels (`_MIN_SCORE_LEVELS`/`_MAX_SCORE_LEVELS`) — is **left out of `questions`** and gets its own `ValueError` in `errors` (keyed by criterion index, message naming `c{idx}` and the criterion name); `classify_grading_error` routes it as `parse`. The rest still go out in the single request under their original ids; an empty `questions` means no request. These limits are the System One API's; the SDK itself only validates non-empty questions and Score criteria, which they subsume.
- **Answers (`answer_to_report(criterion, criterion_idx, answers, config) -> CriterionReport`).** Reads the answer under `question_id(criterion_idx)`:
  - **Noul** `p`: `p > decision_threshold` → MET, `p < t` → UNMET, **`p == t` → `_binary_worst_verdict(weight)`** (the ensemble tie rule: UNMET for weight ≥ 0, MET for < 0; now defined in `types.py` beside `CriterionVerdict` and imported by `criterion_grader`, so the two cannot drift). `probabilities = {"MET": p, "UNMET": 1 - p}`.
  - **Binary Choice**: `CriterionVerdict(choice)`; `CANNOT_ASSESS` is an abstention. Keys `"MET"`, `"UNMET"`, `"CANNOT_ASSESS"` in that order, whatever order the endpoint used.
  - **Multi-choice Choice**: the option whose label **equals** the choice (exact match); the NA option → `na=True`. Keys `str(i)` for every option, NA included.
  - **Score** `s`: level `round(s)` clamped to `[0, K−1]` (`_snapped_level`: `min(max(round(s), 0), K - 1)`), mapped to its original option index. `round` is Python's half-to-even with **no tolerance band** — 0.5 → 0, 1.5 → 2, 2.5 → 2, and 1.5000000001 → 2 — whatever the criterion's weight sign: this is not an ensemble tie, and the ensemble tie rule (`worst_option_among`) is deliberately not applied. Half-to-even rounds halves down as often as up, so it adds no systematic bias toward either end of the scale, where the worst case would always round down on a positive-weight ladder; it is also exactly how the recorded decision-model runs snapped (see *Fidelity* below). Keys `str(i)` for the non-NA options only (NA absent, not `0.0`). Never `na`.
  - The report copies the criterion's fields and sets `reason=None`, `reasoning=None` (no explanation, see [Key Conventions](conventions.md)), `shuffle_order=None`; a multi-choice `value` is always `options[selected_index].value`, never the fractional score. Probabilities are the endpoint's own (not renormalized; they sum to 1 only approximately when rounded).
  - `confidence = selection_confidence(p_selected, K)` = `clamp((K·p − 1)/(K − 1), 0, 1)` for the **selected** outcome, `K` = 2 (Noul), 3 (binary Choice), the option count incl. NA (multi-choice Choice), the non-NA level count (Score). For a Choice's most probable option it equals TypeSafe's reported confidence (within the two-decimal rounding of the reported probabilities); at `decision_threshold=0.5` a Noul's is `2·|p − 0.5|`; a snapped Score level or a Noul verdict under another threshold can fall to `0.0` ("no support for the verdict issued").
  - A missing answer id, an answer of the wrong type, a choice not offered, probabilities that do not cover exactly the offered outcomes or are not numbers in [0, 1], a non-finite `noul`/`score` → `ValueError` naming the criterion → `parse`, for that criterion only.
- **Fidelity to recorded decision-model runs.** `tests/decision/test_decision_recorded.py` pins the builders and the mapping against `tests/decision/fixtures/recorded_jev.json`, derived offline from recorded Jev runs of a reference grader: its questions for two rubrics (binary criteria, and ordinal criteria that carry their NA option) under all six framing combinations with a state of `input` + `submission`, and raw answers with the outcomes it recorded (pytest ids name the rubric, framing and criterion, e.g. `fed_turn-score-interesting-1`). **On those rubrics and that state** the grader differed from the library only at an exact Noul tie — `p == threshold` was MET — which the library resolves by the worst-case rule above; it snapped Score answers with Python's `round`, as the library does, so every recorded Score outcome is reproduced, halves included (the fixture holds halves that round down, 0.5, and up, 1.5). Beyond them its requests differed, so a re-run of such a run through the library would send different questions: under `ordinal_framing="score"` it posed a **nominal** criterion as a `Score` over the non-NA labels too (the library always poses a nominal criterion as a `Choice`, NA option included); it sent a criterion's options as given, where the library's effective rubric adds the NA option under `auto_na_option=True`; its framed instructions had no reference-submission sentence (the library adds `DECISION_MODEL_REFERENCE_INSTRUCTION` when the state has a `reference_submission`); it sent a structured submission flattened into `submission` (the library sends `thinking` + `output`, with `DECISION_MODEL_THINKING_OUTPUT_TASK_INSTRUCTION`); and it had no rubric guidelines (the library sends them as the first state field, with `DECISION_MODEL_GUIDELINES_INSTRUCTION` in framed instructions).

### Decision-Model Judges in `CriterionGrader`
A `DecisionModelConfig` is accepted wherever a judge config is — `CriterionGrader(judge_model_config=...)`, its deprecated alias `llm_config=`, and `JudgeSpec(...)` in `judges=` — alone or mixed with LLM judges in one ensemble (types: [Type Catalog](types.md)).

- **Clients.** Construction builds each judge's client into one of two maps keyed by `judge_id`: `_clients` (`LLMClient`, LLM judges only) and `_decision_clients` (`DecisionModelClient`). Building a `DecisionModelClient` imports the SDK and resolves and checks the API key, base URL and extra headers, so a missing SDK (`ImportError`), a missing key or one the SDK would reject, a resolved base URL (`api_base` or `TYPESAFE_BASE_URL`) no request could use (`_check_base_url`: whitespace, not absolute http(s), credentials, query or fragment, or a request URL the SDK's HTTP stack refuses, e.g. an invalid IDNA name), an `extra_headers` name or value the HTTP/1.1 layer refuses or a header the SDK sets itself (`_check_extra_headers`, `_SDK_OWNED_HEADERS`), or an environment in which `httpx2` cannot build an HTTP client (TLS or proxy settings such as a missing `SSL_CERT_FILE`) fails at construction with `ValueError`, never as a per-item abstention or worst case. An environment that breaks only after construction fails each request as `TypeSafeAPIConnectionError`, an `infrastructure` abstention, never the `unknown` worst case ([Key Conventions](conventions.md)).
- **One request per item (`_judge_all_criteria_with_decision_model`).** `build_state(to_grade, query=, reference_submission=, guidelines=)` once (the rubric's guidelines, from `judge(..., guidelines=)`, as the state's first field) — `to_grade` is the string `judge()` receives, which `Grader.grade` has already flattened from a `{"thinking", "output"}` dict into `<thinking>`/`<output>` sections, so such a submission goes out as `state["thinking"]` + `state["output"]` and a plain one unchanged as `state["submission"]` — then `build_questions(effective_rubric, client.config, state)` once, then **exactly one** `client.system_one(state, questions)`, carrying every expressible criterion under `c{criterion_idx}`; **none** when no criterion is expressible. Answers map back through `answer_to_report`, one `CriterionResult` per criterion, in rubric order. No `shuffle_options`, no system prompt, no few-shot examples, no response format reach the request.
- **Failure scope.** Each failed criterion gets its report from `_failed_judgment_result` (above), so routing is the LLM judge's: `infrastructure`/`parse` abstain (`CANNOT_ASSESS` / `na=True`, category-prefixed `error`), `unknown` → the conservative worst case.
  - An **inexpressible** criterion (its `build_questions` error) is left out of the request and fails alone as `parse` — with its own error even when the request itself fails.
  - A **failed request** (any exception from `system_one`, e.g. a `TypeSafeError` routed by `_classify_typesafe_error`, or an unknown exception) fails every criterion posed in it with the request's exception; criteria are **never re-sent one at a time**, and the SDK's own retries (`max_retries`) are the only retries.
  - A **missing or unusable answer** (`answer_to_report` raises) fails only its criterion (`parse` for its `ValueError`; any other exception is `unknown`, as for an LLM judgment).
- **Billing.** The request's `token_usage(response)` and `completion_cost(response)` ride on the item's **first** `CriterionResult` (index 0, whatever its outcome); the rest carry `None`, so `JudgeCriterionResults.total_usage`/`total_cost` — and hence `aggregate`'s `token_usage`/`completion_cost` — are exact per-item totals. The state is billed once per request whatever the criterion count. With no `input_cost_per_token` the cost is unknown (`None`): `aggregate` adds nothing for it, as for an LLM whose price litellm does not know, so a report whose judges are all unpriced decision models has `completion_cost=None` (never a fabricated `0.0`); a mixed ensemble reports only the priced part. A cache hit reports the stored usage and the cost at the configured price.
- **Votes.** A decision model's `CriterionReport` carries `probabilities`/`confidence` and `reason=None`, which `aggregate` copies onto its `JudgeVote`/`MultiChoiceJudgeVote` like any field; `_join_vote_reasons` skips its `None` reason, so a decision-model-only criterion has `final_reason=None`. `judge_scores[judge_id]` is its own `score_reports` score.
- **Mixed ensembles.** Decision-model and LLM `JudgeSpec`s mix freely in `judges=`: per item, each decision model makes one request and each LLM judge one call per criterion (`tests/decision/test_decision_ensemble.py` counts both over an `evaluate()` run). Downstream a decision-model vote is one more vote: it aggregates exactly as an LLM vote with the same verdict under every `aggregation` (`majority`/`weighted`/`unanimous`/`any`) and every `ordinal_aggregation`/`nominal_aggregation`; its abstentions (a Choice `CANNOT_ASSESS`, a multi-choice NA) are set aside by the same assessable-vote filters; `judge_scores` has an entry per judge; `agreement` and `mean_agreement` count every vote; and in the metrics layer the panel is an ordinary full panel (Fleiss' κ, Krippendorff's α, per-judge metrics). The test pins all of this by comparing each mixed panel with an all-LLM *mirror* panel whose LLM stands in for the decision model with the same verdicts: every aggregation outcome, score, `judge_scores`/`agreement` value and the whole `compute_metrics` result (bootstrap included) are equal; only `probabilities`/`confidence` (present on the decision model's votes) and `final_reason` (its `None` reason skipped) differ. A `judge_id` repeated in any panel, mixed or not, warns (`FutureWarning`, *Judge identity* under item 2 of *Grading Flow* above): across kinds each judge keeps its own client, but `judge_scores` and the per-judge metrics still conflate them; a cascade refuses repeats (*Confidence Cascade* below).
- **Settings checked at construction, before any client is built** (so a configuration error is reported as one, even where no client could be built):
  - **Few-shot examples are LLM-only.** `few_shot_config` or `training_data` when every judge is a decision model → `ValueError` ("few-shot examples apply to LLM judges only"). With at least one LLM judge, `_prepare_examples` selects examples for the LLM judges alone (each judge's selection is keyed on its own `judge_id`, so leaving decision models out changes no LLM judge's examples), and the decision-model request is byte-identical to one from a grader without few-shot.
  - **Response formats need a generative judge.** `binary_response_format` or `multi_choice_response_format` (any non-`None` value) with **any** decision-model judge → `ValueError` naming the decision-model `judge_id`s ("... cannot be combined with decision-model judges ('jev'): a response format describes a generated judgment, which only an LLM judge produces"). LLM-only graders accept them as before. Meta-rubric evaluation, which passes `MetaCriterionJudgment`/`MultiChoiceMetaJudgment`, rejects a decision model itself, earlier and with its own message ([Key Conventions](conventions.md)).
  - **LLM-only prompt settings.** `system_prompt`, `multi_choice_system_prompt` and `shuffle_options` shape LLM prompts only; a decision model's request has no system prompt and keeps the rubric's option order. In a mixed ensemble the LLM judges use them unchanged, and the decision-model request is identical with and without them. When **every** judge is a decision model, each setting that **differs from its default** issues one `UserWarning` ("<name> applies to LLM judges only; this grader has none (every judge is a decision model), so it has no effect", attributed to the caller's line with `stacklevel=2`); a grader with any LLM judge — a mixed ensemble, or a cascade, whose escalation judges are LLMs — never warns. "Differs from its default" means a non-`None` `system_prompt`/`multi_choice_system_prompt` (`None` means no prompt) or `shuffle_options=False`. `shuffle_options=True`, passed or not, never warns: it is the default and what a decision model does anyway (its question keeps the rubric's order), so the rule needs no record of which arguments were passed and `CriterionGrader.__init__` is a plain method (`inspect.signature`, `inspect.getfullargspec`, `__kwdefaults__` all read its own keyword-only parameters and plain `True` default). `_shuffle_options` (`is True` by default) and the manifest's `shuffle_options` are exactly as before.

### Confidence Cascade
`CriterionGrader(judge_model_config=DecisionModelConfig(...), escalation=EscalationConfig(judges, threshold, per_criterion=None))` puts one decision model first and LLM judges behind it (`EscalationConfig` fields and validation: [Type Catalog](types.md)). The decision model judges every criterion in its one request per item (unchanged); only the criteria it is unsure of reach the LLMs, and a cascade has exactly one shape (no multi-stage or reverse cascades, no soft fusion of probabilities with LLM votes).

- **Construction.** The primary must be exactly one decision-model judge, `judge_model_config=DecisionModelConfig(...)` or `judges=[JudgeSpec(DecisionModelConfig(...), ...)]`, else `ValueError` ("escalation needs exactly one primary judge, a decision model ..., got 'default' (an LLM)"). The grader keeps its **own validated copy** of the config, `_escalation = dataclasses.replace(escalation)`, which runs `EscalationConfig.__init__` again (non-empty `JudgeSpec`s of LLMs, thresholds in [0, 1]): the config's frozen fields still hold a `judges` list and a `per_criterion` dict that can change in place, so a config emptied, given a decision-model judge or an out-of-range threshold since it was built is refused with that `ValueError`, and a change made after the grader is built never reaches it — `_escalation_judges`, `threshold_for`, the unknown-name check and the manifest all read the one copy, so the manifest describes the judges and thresholds the grader uses. `judge_id`s must be unique across the decision model and the escalation judges (`ValueError` naming the repeats via `_repeated_judge_ids`, which the panel warning shares; a bare `LLMConfig` escalation judge is `"escalation"`, the `judge_model_config=` judge `"default"`). Escalation judges live in `_escalation_judges` (a property: the copy's `judges`, `[]` without a cascade), **not** `_judges`, so `judge()`'s per-judge fan-out never runs them on every criterion. Every other per-judge concern covers both lists: the client map (`_clients`), `_prepare_examples` (an escalation judge gets the examples it would get without the cascade), the LLM-only settings (the "every judge is a decision model" test counts escalation judges, so a cascade accepts `few_shot_config`/`training_data` and never warns about `system_prompt`/`multi_choice_system_prompt`/`shuffle_options`), `_serialize_grader_config` (the `escalation` manifest key, [Reproducibility & Seed Coordination](reproducibility.md)), and the `judge_ids` property (`_judges` then `_escalation_judges`), which `EvalRunner` uses for its detailed progress (behind the `hasattr(grader, "_judges")` gate: a `CriterionGrader`'s `judge_ids`, any other grader's `_judges`, and none for a grader without `_judges`). The cascade state has class-level defaults (`_escalation = None`, `_escalation_names_warned = False`), so a `CriterionGrader` whose `__init__` never ran — a test double that skips `super().__init__()`, or a grader unpickled from a version without the cascade — grades and runs through `evaluate()` with no cascade (its manifest has no `escalation` key). The response-format `ValueError` still applies (the primary is a decision model). `is_ensemble` stays `len(_judges) > 1`: a cascade is not an ensemble.
- **Escalated set (`judge()`).** Once the decision model has judged the effective rubric, criterion *i* is escalated iff `_escalates(report, escalation.threshold_for(criterion))`: `report.is_error` (any category: a whole-request failure escalates every criterion, an inexpressible criterion or an unusable answer escalates that one), `report.is_na` (`CANNOT_ASSESS`, which only `binary_framing="choice"` can return, or a multi-choice NA option; an abstention escalates however confident), or `confidence is None or confidence < threshold` (strict: a confidence equal to the threshold stands). `EscalationConfig.threshold_for(criterion)` looks `per_criterion` up by criterion **name**; unnamed criteria, and names without an override, use `threshold`.
- **Escalation calls (`_judge_escalated_criteria`).** Each escalation judge runs `_judge_single_criterion` on the escalated criteria only — every judge and criterion concurrently — each under its **original** `criterion_idx` in the effective rubric, the index that keys `_derive_shuffle_rng` and few-shot selection. An escalation judge's prompt for criterion *i* therefore equals the prompt a non-cascade `CriterionGrader(judges=[JudgeSpec(llm, "escalation")], seed=S)` sends for criterion *i* (same `seed`, same `judge_id`), its query, reference submission, shuffled multi-choice options and few-shot examples included (`tests/decision/test_decision_cascade.py` compares the captured prompts). Nothing escalated → no escalation call; exactly one decision-model request per item however many criteria escalate. Guidelines reach escalation prompts like any LLM prompt.
- **Carrier.** `JudgeCriterionResults.criterion_results: list[CriterionResult | None]` is always full-length, and `role: Literal["primary", "escalation"] = "primary"` marks the judge's part. `judge()` returns `[primary, *escalation_results]`; an escalation judge's carrier holds `None` wherever it did not judge (all `None` when nothing escalated, so its `judge_scores` entry exists on every item). `reports` / `total_usage` / `total_cost` skip `None` cells. Private types: nothing public changes.
- **Aggregation.** `aggregate` reads the escalated set off the carriers (the indices where an `"escalation"`-role judge has a result — no second field that could disagree), collects each criterion's votes from the non-`None` cells in judge order, and marks the primary's vote `superseded=True` exactly on escalated criteria. The final verdict aggregates **only the non-superseded votes** with the grader's `aggregation` / `ordinal_aggregation` / `nominal_aggregation` (and the escalation `JudgeSpec` weights), and `final_reason` (`_join_vote_reasons`) and `error` (`_aggregate_error`) are computed over the same votes: an escalated criterion's reason is the LLM explanations, and a decision-model failure stays on its superseded vote. The report has `escalated=True` and votes `[decision model (superseded), *escalation judges]` in `votes` (binary) or `multi_choice_votes` (multi-choice). A criterion not escalated keeps the decision model's vote as its only vote (`final_reason=None`, `agreement=1.0`). The `agreement` validator counts only non-superseded votes. Without a cascade nothing is superseded and every value is exactly as before.
- **Escalation-judge failures** route exactly as any LLM judge's (`_failed_judgment_result`): `infrastructure`/`parse` abstain, `unknown` gives the worst case (`_binary_worst_verdict` / `worst_scored_option`), aggregated like any vote. When every escalation vote abstained, the criterion abstains (`CANNOT_ASSESS` / `na=True`, counted in `cannot_assess_count`, scored under the configured `CannotAssessStrategy`) with `error` from `_aggregate_error` over the non-superseded votes: set when every one of them failed, `None` when the judges genuinely answered `CANNOT_ASSESS` / the NA option (a judgment, not a failure). **Never a fallback to the decision model's vote**: it was judged insufficient, and the failure stays visible in `error`.
- **`judge_scores`.** A primary judge's entry is `score_reports` over its own verdicts on every criterion, superseded ones included (the decision model's own score, equal to a standalone decision-model grader's); every escalation judge's entry is `None` **by role**, on every item, even one where every criterion escalated.
- **Usage and cost.** Summed over every carrier: the decision model's request (its cost only when `input_cost_per_token` is set) plus each escalation call's usage and cost. The item report is then assembled by the module function `_ensemble_evaluation_report` (score and `raw_score` over the final verdicts, `mean_agreement`, `cannot_assess_count`), which the offline replay shares (*Offline Cascade Replay, Diagnostics and Calibration* below).
- **Unknown `per_criterion` names.** `CriterionGrader._check_escalation_names(rubrics, where) -> bool` warns (`UserWarning`, attributed by `_caller_stacklevel` to the code that asked for grading) about `per_criterion` names that match no criterion of any of `rubrics`; they set no threshold. The check itself is the module function `_warn_unknown_threshold_names(per_criterion, rubrics, *, source, where)` (`source="EscalationConfig.per_criterion"` here), shared with the offline replay. `judge()` checks the rubric being graded **once per grader** (flag `_escalation_names_warned`, set only after the warning is issued, so a warnings-as-errors filter raises on every call). The two batch paths, `EvalRunner.run` and `fill_ground_truth`, instead grade inside `with _escalation_names_checked(grader, dataset):`, which (for a `CriterionGrader`) checks once, before grading, against every item's rubric (`get_item_rubric`; "any item's rubric"; the items a resumed run or `fill_ground_truth(force=False)` does not grade again included, since a name one of them has is no typo), and returns a context that sets the context variable `_ESCALATION_NAMES_CHECKED` for the items' grading (tasks started inside inherit it; reset on exit), which `judge()` reads to skip its per-rubric check: with per-item rubrics (HealthBench) a name absent from one item's rubric but present in another's never warns, so a warnings-as-errors filter cannot fail (and `fill_ground_truth` silently drop) the items that lack it. The check runs at the call, not on entering the context, so the warning is attributed to the caller rather than to a `contextlib` frame. The batch's check leaves the grader's own direct-call warning unspent.

### Offline Cascade Replay, Diagnostics and Calibration
`src/autorubric/escalation.py` measures a cascade at a threshold without running it there: `replay_escalation` rebuilds the cascade's `EvalResult` from two recorded runs with **no calls**, `escalation_stats` summarizes a live or replayed cascade run as an `EscalationPoint`, and `calibrate_escalation` measures replays over a threshold sweep as an `EscalationCurve`, whose `best` picks a point (types: [Type Catalog](types.md)). A replay reuses the live cascade's own code, so the two cannot drift: the rule `_escalates`, the lookup `_threshold_for` (which `EscalationConfig.threshold_for` delegates to), the threshold validation `_check_thresholds` (which `EscalationConfig.__init__` calls), the unknown-name warning `_warn_unknown_threshold_names`, the item-report assembly `_ensemble_evaluation_report` and `score_reports`.

- **Replay.** `replay_escalation(dm_result, llm_result, escalation, *, per_criterion=None, cannot_assess_config=None, normalize=True) -> EvalResult`. `escalation` is a float threshold (with an optional `per_criterion`) or an `EscalationPoint` (its `threshold` and `per_criterion`; passing `per_criterion` too, or a point without a threshold such as an `escalation_stats` point, → `ValueError`); thresholds are validated as `EscalationConfig` validates them, the messages naming `escalation`/`per_criterion` or `EscalationPoint.threshold`/`EscalationPoint.per_criterion`. Items are paired by `item_idx` (output in index order). For each criterion the decision model's recorded vote is turned back into its `CriterionReport` (`_judged_report`, the inverse of `aggregate`'s vote construction) and the criterion is escalated iff `_escalates(report, _threshold_for(criterion, threshold, per_criterion))`, exactly the live rule. `per_criterion` names that match no criterion of the replayed items (the union of their graded criteria, as `EvalRunner` checks a live run) warn as a live cascade does.
- **Reports: the runs' recorded aggregates.** A kept criterion is the decision-model run's `EnsembleCriterionReport` unchanged (its one vote, the final verdict aggregated from it). An escalated criterion is the LLM run's report of it with the votes `[decision model's vote, superseded=True, *the LLM votes]` and `escalated=True` (`_escalated_report`): its final verdict, `final_reason`, `error` and `agreement` are the LLM run's. That is exactly what a live cascade builds, because it aggregates only the non-superseded votes, which are the LLM run's votes in the same judge order with the same judge weights; the aggregation settings (`aggregation`, `ordinal_aggregation`, `nominal_aggregation`) that decided them are therefore the LLM run's, a condition of the same kind as the `seed` and `judge_id`s. Reusing the recorded output of `CriterionGrader`'s aggregation needs neither an aggregation re-implementation nor settings parameters (an in-memory `EvalResult` records no grader config), and a replay can never disagree with the run it reads. Each item report is assembled by `_ensemble_evaluation_report`; scores come from `score_reports` under `cannot_assess_config`/`normalize` (defaults as `CriterionGrader`'s). `judge_scores`: the decision model's entry is recomputed as `score_reports` over its own verdicts, superseded ones included, under the replay's scoring settings (equal to the decision-model run's entry when the settings match); each LLM judge's is `None` by role. A decision-model-run item that failed (`ItemResult.error`) stays failed.
- **Exactness.** The replay equals the live cascade in every report field but `token_usage`/`completion_cost` (so `compute_metrics(..., per_judge=True)` is equal too) when each run was graded by a `CriterionGrader` configured as the cascade for everything that stage uses, over the same items and rubrics (guidelines included), and the replay's `cannot_assess_config`/`normalize` are the cascade's. The decision-model run: one judge, the cascade's decision model (config, `judge_id`, weight). The LLM run: the escalation judges (`judges=escalation.judges`: configs, `judge_id`s — `"escalation"` for a bare `LLMConfig` — and weights) with every setting they use as the cascade's: `seed` (`CriterionGrader.seed`, generated when not given), `shuffle_options`, `system_prompt`, `multi_choice_system_prompt`, `training_data`/`few_shot_config`, and the default response formats (a cascade cannot have others). Both: the cascade's `auto_na_option` and aggregation settings. Recipe for `CriterionGrader(judge_model_config=dm, escalation=escalation, seed=S)` with otherwise default settings: `CriterionGrader(judge_model_config=dm)` and `CriterionGrader(judges=escalation.judges, seed=S)`. Only the graded criteria are checked (an `EvalResult` records no grader config, so the docstrings are the only safeguard for the rest). With only another `seed` or `judge_id` the replay is equal in distribution only (shuffled multi-choice options and few-shot examples differ); with another prompt setting (`shuffle_options`, a system prompt, few-shot settings) the prompts themselves differ and the replay is not the cascade's run. Pinned by `tests/escalation/test_replay_escalation.py`: a live cascade and the two separate runs on scripted clients (`tests/escalation/cascade_runs.py`, `conftest.py`: the real `DecisionModelClient` on a scripted SDK client, LLM answers hashed from the prompt), for one LLM judge (priced and unpriced), two-judge panels under `majority`/`weighted`/`unanimous`, few-shot examples, non-default scoring, experiments loaded with `from_experiment` (both, or one with the other live, either way round: pairing skips the absent submission, the replay keeps the live run's items via `_recorded_item`, and the same-data warning fires), a rubric per item, shuffled multi-choice criteria and a `per_criterion` override; the escalation judges' prompts are a sub-multiset of the LLM run's.
- **Validation (`ValueError`).** The same `item_idx` set in both results, each index once; the same recorded submission where both recorded one (`from_experiment` records `""`); the same graded criteria (`EnsembleCriterionReport.criterion`, NA options added by `auto_na_option` included) on every item the decision model graded. `dm_result`: one judge on every item, the same one throughout, one non-superseded vote per criterion that is a decision model's (`_is_decision_model_vote`: `probabilities` and `confidence` set, unless the vote has an `error`), no `escalated` report. `llm_result`: no failed item, every judge's vote on every criterion (in `judge_scores` order), no decision-model, superseded or escalated votes, the same judges on every item (a cascade has one set of escalation judges). The decision model's `judge_id` must not be an LLM judge's (as in a live cascade). Each is pinned in `TestRequirements` (`tests/escalation/test_replay_escalation.py`), among them a decision-model judge renamed on one item (`item 4 was judged by 'x', earlier items by 'default'`) and an LLM panel with a judge missing from one item.
- **Estimates and how they are marked.** Only per-item cost and time are recorded, so per item `completion_cost = decision-model cost + LLM cost × share` (`share` = the item's escalated criteria over its criteria; `None` unless positive, as in a live report) and `duration_seconds = decision-model duration + LLM duration × share`; the run's `total_duration_seconds` is the two runs' totals with the LLM one pro-rated by the run's escalated share (pooled: escalated criteria over the criteria the LLM run judged, not the mean of the items' shares; pinned on the per-item dataset, 3/7 against 7/18). The criteria of an item whose decision-model grading failed count in that denominator with none escalated (`_replayed_item` returns `len(_llm_criteria(llm_item))` judged pairs for it): the LLM run's total includes its time on that item, which a live cascade never spends, since it sends the item to no LLM judge; so the run total agrees with the items' own estimates (pinned: 14 of 35 with a failed first item, not 14 of 30). `token_usage` (per item and `total_token_usage`) is `None`: it cannot be split by criterion. The result is marked in its `experiment_name`, `EvalResult`'s one descriptive field: `"replay of decision-model run '<name>' and LLM run '<name>' (estimated cost and time)"` (`_run_name`; `"an unnamed … run"` for a `None` name); `experiment_dir` is `None`, as no experiment directory exists; no field is added to any type. `started_at`/`completed_at` are the replay's time. The length penalty is not re-applied (compare with runs graded without one; criterion-level metrics are unaffected). The result is an ordinary `EvalResult`: `compute_metrics`, `escalation_stats` and the checkpoint format (`ItemResult.to_dict` → `EvalResult.from_experiment`) take it unchanged (tested).
- **Same-data warning.** `_calibration_fingerprint(items)` is a SHA-256 over each item's own `submission`, `prompt` and `reference_submission` and its criteria's `requirement`s, in order — not `_compute_dataset_hash`, which covers only a dataset's name, prompt and sizes and so collides for equal halves of `split_train_test`. A replay computes it over its paired items (`_replayed_fingerprint`: the recorded `DataItem`, `_recorded_item`, and the graded criteria, whose requirements grading keeps) and warns (`UserWarning`, attributed by `_caller_stacklevel`) when an `EscalationPoint`'s `calibration_fingerprint` equals it: a threshold chosen and evaluated on the same pairs is optimistic. Results loaded with `from_experiment` record no submission, so they never match: calibrating on loaded runs and replaying the chosen point on the same loaded runs goes unrecognized (a known limit, stated in the `replay_escalation`, `calibrate_escalation`, `EscalationCurve` and `EscalationPoint.calibration_fingerprint` docstrings; a fingerprint without submissions would collide for equal `split_train_test` halves, and a "check could not be made" warning would fire on every legitimate held-out replay of loaded runs).
- **Diagnostics.** `escalation_stats(result, dataset, *, metric="criterion_accuracy") -> EscalationPoint` pools (item, criterion) pairs from the `escalated`/`superseded` flags, so it needs no shared rubric (per-item heterogeneous datasets, where `compute_metrics` takes its pooled path). It covers items in both `result` and `dataset` (`_covered_items`, in `item_idx` order, as `compute_metrics`); a failed item has no pairs. The pairs come from `_cascade_pairs(items, dataset)` (each graded item's criterion reports with the decision model's vote and the label; the rubric-length `ValueError`), which the per-criterion calibration shares. `_decision_model_vote` checks the cascade shape (`ValueError` otherwise): a kept criterion has exactly one non-superseded vote, an escalated one a first vote that is the only superseded one, and that vote is a decision model's (so a decision-model-only run reads as a cascade that escalated nothing, while an LLM-only run or a panel is refused). A pair is *labelled* when the item's ground truth resolves (`resolve_ground_truth` against `get_item_rubric`) and does not abstain (`_labels`/`_abstains`: not `CANNOT_ASSESS`, not an NA option), as under `compute_metrics`' default `cannot_assess="exclude"`/`na_mode="exclude"`. Accuracy is exact match (binary verdict, selected option index) pooled over binary and multi-choice labelled pairs. The decision model's predictions are read as `compute_metrics(per_judge=True)` reads a judge's (`_vote_prediction`): an errored vote is no prediction, and neither is an abstention, so a decision-model failure or abstention (escalated at any threshold) counts in `escalation_rate` but in no accuracy: there is no decision-model answer to measure, or to compare the fallback's with. The fallback's predictions are the escalated pairs' final verdicts, read as the run's aggregate metrics read them (`_final_prediction`): an abstaining final verdict is no prediction, a worst case decided by `unknown` failures is one. `dm_accuracy_kept` is over the kept labelled pairs the decision model answered. `dm_accuracy_escalated` and `fallback_accuracy_escalated` are both over the *deferred* pairs — escalated labelled pairs the decision model answered, i.e. escalated for their confidence — whose final verdict does not abstain, so they compare the two judges on the same pairs. There, escalating gains right verdicts exactly when the fallback's accuracy beats the decision model's, the condition a cascade needs (the fallback beats the decision model where it defers); a deferred pair whose final verdict abstains leaves both, and leaves an abstention-excluding metric such as `criterion_accuracy`, which then rises when the decision model was wrong on it. Measuring the fallback over every escalated pair would mix in the forced escalations (decision-model failures and abstentions), which have no decision-model answer and escalate at every threshold, so the two accuracies would cover different pairs and could point the wrong way. `escalation_rate` is over all pairs, labelled or not; accuracies over empty sets are `None`. `metric` is `compute_metrics(result, dataset)` read by attribute name or callable (`_metric_value`: a number — any `numbers.Real` but a `bool`, so NumPy scalars such as `float32`/`int64` count — recorded as a `float`, or `None`, else `ValueError`; a NaN, e.g. a NumPy mean over no values, is read as `None`, the library's undefined); `compute_metrics`' own errors propagate. `cost_usd` is `aggregate_completion_cost` over the graded items' reports; `compute_seconds` the sum of the items' `duration_seconds`, failed items included — exact for a live run, sums of estimates for a replay. `threshold`, `per_criterion` and `calibration_fingerprint` are `None`. Pinned by `tests/escalation/test_escalation_stats.py` (a hand-built run fixing every definition — an item whose ground truth does not resolve (an option the criterion lacks) reads as one without ground truth, as `compute_metrics` skips it; an escalated criterion with two superseded votes is refused — and live vs replayed cascades on a shared-rubric and a per-item dataset, where the live cascade's `dm_accuracy_escalated` and `fallback_accuracy_escalated` are both 4/7: its 7 forced escalations measured by neither, a rate-limited LLM call's NA final verdict leaving both, a crashed call's worst case counted; `TestTheDeferredPairs`: with decision-model failures the fallback's six wrong forced verdicts stay out, so a cascade that pays (6/14 → 8/14) reads fallback 1.0 against the decision model's 0.5, where measuring the fallback over every escalated pair gave 0.4; a deferred pair the fallback abstains on is in neither accuracy).
- **Calibration.** `calibrate_escalation(dataset, dm_result, llm_result, *, thresholds=None, metric="criterion_accuracy", per_criterion=False, min_pairs_per_criterion=30, cannot_assess_config=None, normalize=True) -> EscalationCurve` makes no calls. For each threshold of the sweep (default `_DEFAULT_THRESHOLDS` = `i / 50` for `i` in 0..50, i.e. 0.00, 0.02, …, 1.00; given thresholds keep their order, each checked by `_check_thresholds` with messages naming `thresholds[i]`; an empty sweep → `ValueError`) it runs `replay_escalation` with `cannot_assess_config`/`normalize` (every replay, the fit's included, goes through one closure, `measured`) and measures the replay with `escalation_stats` (so `metric` is read off `compute_metrics(replay, dataset)` by `_metric_value`), then fills in the point's `threshold` (a `float`), `per_criterion` and `calibration_fingerprint`. Every point therefore equals `escalation_stats(replay_escalation(dm_result, llm_result, point), dataset)` with its configuration filled in, and the point at a live cascade's threshold reads as the live run's `escalation_stats` but for the estimated `cost_usd`/`compute_seconds` (tested). The fingerprint is `_calibration_fingerprint` over the calibration items — the dataset's items the runs graded (`_covered_items(dm_result, dataset)`: each `DataItem` with its `get_item_rubric` criteria, in `item_idx` order) — which equals `_replayed_fingerprint` of the same runs: `replay_escalation(dm, llm, curve.best())` on the calibration runs warns, on the runs of another `split_train_test` part it does not. Taking it from the dataset, which always holds the submissions, keeps results loaded with `from_experiment` (no submissions) from ever matching falsely. `per_criterion` must be a `bool` (a mapping is refused: thresholds by name go to `replay_escalation`), `min_pairs_per_criterion` a positive int (`_is_positive_int`); `replay_escalation`'s and `escalation_stats`' errors propagate. The docstrings state the cost (no calls, but `llm_result` is a full LLM grading of every criterion of the calibration items), the same-data caveat (a point chosen and measured on the same pairs is optimistic; measure it on held-out items) and the exactness condition (`replay_escalation`'s, *Exactness* above: each run graded by a `CriterionGrader` configured as the cascade for that stage — for the LLM run `judges=escalation.judges` with the cascade's `seed`, `shuffle_options`, system prompts, few-shot settings, `auto_na_option` and aggregation settings — and the cascade's scoring settings: without them score-level metrics — `score_rmse`, `score_pearson`, `bias`, … — read replays scored by `CannotAssessConfig()`/`normalize=True`, not the cascade's run; criterion-level metrics do not read scores).
- **The metric.** Higher is better (negate a lower-is-better metric in a callable). The default `criterion_accuracy` pools pairs otherwise than the point's accuracies, and differently on `compute_metrics`' two paths (both described in the `EscalationPoint` docstring). On the per-criterion path (`_criterion_level_scalars`; a shared rubric, or per-item rubrics that are all the same) it reads the binary pairs alone when there are any (a `CANNOT_ASSESS` on either side dropped under `cannot_assess="exclude"`), else the multi-choice pairs with an NA prediction or label counted as one more option. On a per-item heterogeneous dataset `compute_metrics` takes `_compute_per_item_pooled_metrics`, whose run-level fields are pooled over rubric points: `criterion_accuracy` is the exact accuracy over the points of every scale (binary and multi-choice together), leaving out a point whose prediction abstains (`n_abstain`) and counting one whose label abstains (`CANNOT_ASSESS`, an NA label) as a miss; `mean_kappa` is the binary points' kappa, so the default metric is defined there; a metric of one scale type needs a callable reading `pooled_by_scale` (tested).
- **The selection rule, `EscalationCurve.best(max_escalation_rate=None, tolerance=0.0)`.** Among the points with `escalation_rate <= max_escalation_rate` (inclusive; every point without a budget) and a defined `metric` (`None` and NaN are passed over), find the best metric; among those within `tolerance` of it — `metric >= best - tolerance` or `math.isclose(best - metric, tolerance)` (default `rel_tol`, no `abs_tol`), so a gap equal to the tolerance up to rounding counts (`0.4 - 0.35` is `0.05000000000000004`) while `tolerance=0` stays exact — return the least escalating. Ties: the higher metric, then the lower `threshold` (on new items a lower threshold never escalates more), then the earlier point. A `None` `escalation_rate` (a run with no pairs) is outside any budget and ranks last; a `None` `threshold` ranks after numeric ones. `ValueError` for an empty curve, no point within the budget (the message gives the lowest rate), none within it with a metric, `tolerance` not a number >= 0 (`math.inf` allowed: the least escalating point with a metric), `max_escalation_rate` not in [0, 1]. The rule has one implementation, `_selected(candidates, max_escalation_rate, tolerance)` over `(escalation_rate, metric, threshold)` tuples, shared by `best` and the per-criterion fit. `EscalationCurve.to_dataframe()` imports pandas lazily, as `MetricsResult.to_dataframe` does: a row per point, the `EscalationPoint` fields as columns (`per_criterion` a dict or `None`; an empty curve keeps the columns).
- **Per-criterion fitting (`per_criterion=True`).** `_fitted_thresholds` counts each criterion *name*'s labelled pairs over `_cascade_pairs(_covered_items(dm_result, dataset), dataset)` (the calibration pairs, the same in every replay; pooled across items, since a live cascade looks thresholds up by name; unnamed criteria are skipped, as they always follow the global threshold; names in order of first appearance). A name with at least `min_pairs_per_criterion` labelled pairs (inclusive) is fitted; thinner names follow the global threshold and are named in a `UserWarning` (`_warn_global_threshold`: `'<name>' (<n> labelled pairs)` and the reason; attributed by `_caller_stacklevel`; one warning per reason). **The fit is coordinate-wise on the run's own `metric`**: it starts from `start`, the global threshold `_selected` picks at its defaults (no budget, no tolerance) on the unfitted sweep's points; then, for each fitted name in turn, it measures the replay at `start` with `{**fitted, name: t}` for every `t` of the sweep and keeps `sweep[_selected((escalation_rate, metric, t) …)]`. A threshold decides only its own criterion's pairs, so only that name's pairs vary within a step, and the run's escalation rate orders the candidates as the name's own would. The current configuration is a candidate (the name at `start`), so no step lowers the metric: the point at `start` with the fits measures at least as high as without them, and so does `best` at its defaults. Selecting by the run's metric (rather than by a per-criterion accuracy) is what makes the fit serve the metric `best` ranks: a per-criterion ratio of right to predicted pairs can rise while the pooled `criterion_accuracy` falls, when the fallback abstains on escalated pairs (the predicted pairs shrink); on the per-criterion path `criterion_accuracy` reads only binary pairs when a rubric has any (a multi-choice criterion's threshold then cannot move it, and the fit escalates it least) and counts NA as an option on a rubric without binary criteria, while on the pooled path it reads every scale's points, so every criterion's threshold can move it (*The metric.* above); and any `metric` (a `MetricsResult` attribute or callable) is fitted as given. If `metric` is `None` at every point of the unfitted sweep, there is no start: every eligible name is warned about and nothing is fitted. The curve's points are one per swept global threshold, each with `per_criterion` = the fitted thresholds (the same contents at every point, a copy each; `None` when nothing was fitted, so an all-thin calibration equals the global one), measured on `replay_escalation(dm, llm, threshold, per_criterion=fitted)`: exactly what `replay_escalation(dm, llm, point)` replays and `EscalationConfig(judges, point.threshold, per_criterion=point.per_criterion)` runs live. `best`'s budget and tolerance therefore trade on the criteria that follow the global threshold. Cost: the unfitted sweep, one sweep per fitted name, and one sweep with the fits (each a replay plus `compute_metrics`; about 50 ms per replay at 300 items × 7 criteria).

### Score Calculation
A **single scoring core** — `score_reports(reports, config, normalize=True)` in `scoring.py` — is the source of truth for weighted-criterion scoring, shared by all three scorers: the live grader (`CriterionGrader._calculate_score_from_reports`), `Rubric.compute_score` (ground-truth / expected scores — parses verdicts into `CriterionReport`s, delegates), `RubricDataset.compute_weighted_score` (delegates to `Rubric.compute_score`). Every path builds `CriterionReport`s and runs the same core, so they agree exactly across every `CannotAssessStrategy` x {binary, multi-choice} x {+/- weight}.

```python
# Positive criteria: MET earns weight, UNMET earns 0
# Negative criteria: MET subtracts weight, UNMET contributes 0
weighted_sum = sum(report.score_value * report.weight for non-abstained reports)
#   + sum(_abstain_contribution(report, config) for abstained reports)  # NA / CANNOT_ASSESS
score = clamp(weighted_sum / total_positive_weight, 0, 1)  # if normalized
# Negative-weight-only fallback (no positive weight): 1 + weighted_sum / total_negative_weight
# Length penalty subtracted after base calculation
```

With nothing left in the denominator — every criterion excluded under `SKIP`, as when every judgment of an item failed on infrastructure/parse errors — the core returns `0.0`, and the grader reports that score with `error=None`, for either judge kind (a decision model's failed request yields the same report as an LLM grader whose every call failed). The metrics layer scores such an item like any other, as it always has for LLM graders; only an item whose grading raised counts as errored ([Abstention Handling](abstention.md)).

`CannotAssessStrategy` applies uniformly to binary CANNOT_ASSESS and multi-choice NA via `_abstain_contribution`: `SKIP` excludes the criterion from **both** numerator and denominator; `ZERO`/`PARTIAL`/`FAIL` keep it in the denominator with a weight-sign-aware contribution. `FAIL` uses the score-minimizing realizable outcome — `Criterion.worst_scored_option()` for multi-choice (same canonical worst case as the `unknown`-error path and metrics `na_mode="as_unmet"`), UNMET for positive weight (0) / MET for negative weight for binary. (The legacy `Rubric._apply_cannot_assess_strategy` was removed when `compute_score` was routed through the core — it had a SKIP double-subtraction bug, both excluding the abstained criterion *and* subtracting its weight from the denominator, that the core fixes.)
