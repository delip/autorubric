# AutorubricLM Data Ingestion Policy

How to convert an external dataset into a `RubricGenerationDataset` for AutorubricLM training.

IMPORTANT: Read the RubricGenerationDataset schema in `src/autorubric/generation/dataset.py` before converting a dataset.

## Directory layout

```
data/autorubriclm/
├── raw/<dataset>/          # Untouched upstream files + provenance note
├── scripts/convert_<dataset>.py
├── converted/<dataset>.json   # One RubricGenerationDataset per source
└── splits/                    # Final merged train/val/test (produced by merge_and_split.py)
```

Every dataset flows through three stages: **raw → convert → merge**. The conversion script is the authoritative record of every decision made during ingestion. Keep it self-contained and deterministic (fixed seed for any randomness).

## The target schema

Each converted dataset is a `RubricGenerationDataset` containing `RubricGenerationExample` objects. An example is one (input, output) training pair:

**Input** — what the model sees at inference time:

- `grading_problem_description` — the full grading task specification
- `reference_response` — optional gold-standard answer
- `responses` — optional sample submissions showing the quality range
- `target_criteria_count` — optional soft target
- `criterion_mix` — optional hint ("binary", "ordinal", "nominal", "heterogeneous")

**Output** — what the model should produce:

- `criteria` — a `list[Criterion]`, each with `name`, `weight`, `requirement`, and optionally `options` / `scale_type`

**Metadata** — for traceability, not training:

- `id` — auto-generated content hash if omitted
- `source_dataset`, `domain`, `language`, `is_human_authored`

## General principles

### Frame the grading problem, not just the task

`grading_problem_description` must describe a *grading* task, not just paste the raw prompt. The model is learning to produce rubrics, so the input should read like a request for a rubric. Prefix the original task statement with context such as "Grade student responses to the following college-level chemistry exam question:" or "Evaluate the quality of a chatbot response to the following user query:". The framing should convey the domain, the expected response format (essay, code, short answer, dialogue turn, etc.), and who the respondents are.

### Normalise weights to sum to 100

Source datasets express weights in wildly different units: raw point values, Likert scales, categorical labels (Essential/Important/Optional), or no weights at all. Normalise positive weights to sum to 100 in the converted output. This gives the model a consistent scale to learn against. Negative weights (penalties) are normalised by the same factor but are *not* included in the sum-to-100 target.

For datasets without explicit weights, assign uniform weights (100 / num_criteria). If the dataset provides categorical importance labels (e.g., Essential/Important/Optional), map them to a fixed ratio (e.g., 3:2:1) before normalising. Document the mapping in the conversion script.

### Preserve the original requirement text

`Criterion.requirement` should use the upstream criterion description verbatim whenever it is adequate. Do not rephrase, summarise, or editorialize unless the original text is genuinely ambiguous or incoherent (and document why). Short machine-friendly identifiers go in `Criterion.name`.

### Set `is_human_authored` honestly

- `True` — criteria were written or validated by humans (e.g., TA-graded rubrics, expert-authored benchmarks)
- `False` — criteria were generated by an LLM without human review
- `"unknown"` — you cannot determine provenance from the source documentation

This field matters for training data weighting. When in doubt, use `"unknown"`.

### Include sample responses when available

The `responses` field gives the model examples of the quality range the rubric must discriminate between. When the source dataset contains graded submissions, include a small stratified sample (e.g., 3 per score tercile, ~9 total) showing low/mid/high quality. This teaches the model what kinds of responses the rubric will encounter.

Do not include the full set of submissions — that belongs in `RubricDataset` for evaluation, not in the generation training data. Do not truncate or summarise individual responses; include them verbatim or omit them.

### One example per rubric, not per submission

A `RubricGenerationExample` represents one grading problem → one rubric. If a source dataset has 300 student responses to the same question, that is one example with the question as input and the rubric as output. The student responses are *samples* in the `responses` field, not separate examples.

Datasets with per-instance rubrics (e.g., BiGGen-Bench, WildBench) are the exception: each instance genuinely has a different rubric, so each instance becomes its own example.

## Common gotchas

### Negative / flag columns are not criteria

Many grading datasets include columns like "Incorrect", "Blank", "Contains error" alongside the actual rubric criteria. These flag columns indicate error patterns or degenerate submissions. They are not criteria in the Criterion schema sense. Use them for *filtering* (exclude blank submissions) but do not convert them into criteria unless they represent a genuine penalty dimension with meaningful weight.

### Inferred weights need sanity checks

When weights must be inferred (e.g., via regression on scores), validate the result. Check that R² is reasonable (>0.9 for well-structured rubrics). Inspect the inferred weights for negative values (which may indicate multicollinearity or annotation artifacts). Report the R² in the script's stdout so it is visible during conversion.

Low R² is not always a bug — it may reflect holistic grading shortcuts, manual adjustments, or annotation inconsistencies in the source data. Document the cause and decide whether those examples should be included, flagged, or excluded.

### Partial-credit and multi-level criteria

Some datasets use Likert scales (1–5), partial credit (full/partial/no), or categorical labels. Map these to the appropriate Criterion structure:

- **Ordinal scales** (e.g., 1–5 Likert) → `options` with explicit `value` fields (0.0 to 1.0), `scale_type="ordinal"`
- **Nominal categories** (e.g., error types) → `options` with `scale_type="nominal"`
- **Binary with partial credit** (full/partial/none) → either split into separate binary criteria or use ordinal options. The choice depends on whether the partial level has a distinct semantic meaning.

Set `criterion_mix` on the example to reflect the actual mix: `"binary"` if all criteria are binary, `"heterogeneous"` if the rubric mixes types.

### Encoding issues and non-ASCII

Source CSVs and JSONs often have encoding problems: stray `Â` from UTF-8/Latin-1 mismatches, smart quotes, non-breaking spaces. Open files with explicit `encoding="utf-8"` and inspect the output for garbled characters. Fix encoding issues in the conversion script, not by modifying the raw data.

### Deduplication is the caller's responsibility

`RubricGenerationDataset.merge()` concatenates without deduplicating. The `id` field (a content hash) makes deduplication trivial downstream. Conversion scripts should not worry about cross-dataset duplicates, but should ensure that *within* a single converted dataset there are no duplicate examples (e.g., the same question appearing twice from different CSV rows).

### Pairwise / preference data needs reframing

Some datasets (Prometheus 2 Preference Collection, OpenRubrics) are structured as pairwise comparisons (response A vs. B). These do not map directly to the generation schema. You need to extract the underlying rubric from the preference annotation and pair it with the original task prompt. The individual responses can go in the `responses` field if they illustrate the quality range, but the pairwise label itself is not part of the generation training signal.

### Checklist datasets are a degenerate case

Datasets like WildBench and WildChecklists use YES/NO checklists with uniform or importance-weighted items. These are valid binary-criterion rubrics and can be ingested directly. Tag them with `criterion_mix="binary"`. If importance weights are available, use them; otherwise assign uniform weights. Be aware that large checklist datasets will dominate the training mix if not downsampled — balance against ordinal/nominal/heterogeneous examples.

## Conversion script conventions

Every conversion script should:

1. Live at `data/autorubriclm/scripts/convert_<dataset>.py`
2. Read from `data/autorubriclm/raw/<dataset>/` (or from elsewhere in the repo if the raw data predates this layout)
3. Write a single `RubricGenerationDataset` JSON to `data/autorubriclm/converted/<dataset>.json`
4. Use a fixed random seed for any sampling or shuffling
5. Print per-example diagnostics (criteria count, weight sum, R² if inferred, sample counts)
6. Verify round-trip serialization (`to_json` → `from_json` → assert equality)
7. Be runnable standalone: `python data/autorubriclm/scripts/convert_<dataset>.py`

Keep the script self-contained. Reuse the raw-data reader patterns from existing scripts, but do not create shared library code for conversion — each dataset has idiosyncratic quirks and the scripts are clearer when they are independent.

## Provenance

Every `raw/<dataset>/` directory should contain a short note (README, PROVENANCE.md, or comment in the conversion script) recording:

- Where the data was downloaded from (URL, HuggingFace dataset ID, etc.)
- The license
- The download date
- The paper citation if applicable
- Any known issues or limitations
